## Kubernetes Answers

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. Pods managed by a Deployment have no stable identity. A **StatefulSet** manages stateful applications, providing stable, unique network identifiers and persistent storage to each pod (e.g., database primary/replica).

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
A ClusterIP Service exposes a stable internal IP address within the cluster. It uses `kube-proxy` (which typically runs iptables or IPVS rules on each node) to intercept traffic destined for the Service's ClusterIP and forward it to one of the healthy backing Pods selected via the Service's selector.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It is a cluster resource representing the actual storage capacity (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace resource that requests a specific amount and access mode of storage.
*   **StorageClass:** A class of storage that defines "how" the PV should be provisioned (e.g., fast SSD, standard HDD). It allows for dynamic provisioning.
*   **Relationship:** A PVC requests storage based on a StorageClass. The StorageClass instructs the provisioner to create a PV, which the PVC then binds to, allowing a Pod to mount the storage.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
1.  **Check Logs:** Use `kubectl logs <pod-name>` to see the application-level error causing the crash.
2.  **Check Events/Status:** Use `kubectl describe pod <pod-name>` to check the `Events` section for scheduling failures, image pull errors, or OOMKilled status.
3.  **Check Configuration:** Verify the Pod/Deployment YAML for correct image names, environment variables, and resource requests/limits.
4.  **Check Readiness/Liveness Probes:** If probes are configured, check if the application is failing the health checks, causing Kubernetes to restart it.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS acts as the cluster's internal DNS service. It resolves service names (e.g., `my-service.my-namespace.svc.cluster.local`) to the corresponding ClusterIPs and handles internal name resolution. If CoreDNS pods are down, internal DNS resolution fails; pods cannot find other services by name, leading to application connection failures.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-phase process:
1.  **Filtering (Predicates):** The scheduler first filters out nodes that *cannot* run the pod based on hard constraints. Examples include: checking if the node has sufficient allocatable CPU/Memory, checking for required Taints/Tolerations, or checking Node Affinity rules.
2.  **Scoring (Priorities):** From the remaining viable nodes, the scheduler scores them based on soft preferences. The node with the highest score is chosen.
    *   **Factors:** 1. Resource utilization (preferring nodes with less load). 2. Node Affinity/Anti-Affinity rules. 3. Topology spread constraints (spreading pods across different failure domains like zones).

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
*   **Scheduling:** The pod *will likely not* be scheduled immediately because the total requested memory (3.5GB + 256Mi) exceeds the available allocatable memory on the node (4GB). The scheduler checks against *requests*, not limits, for initial placement.
*   **Runtime Behavior:** If it were scheduled, and it uses 600Mi, it will exceed its defined `limits.memory` (512Mi). Kubernetes will terminate the container with an **OOMKilled** (Out Of Memory Killed) status.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
1.  **External LB:** The external Load Balancer (managed by the cloud provider or bare metal) receives the external traffic and forwards it to the NodePort exposed by the Ingress Controller Pods.
2.  **Ingress Controller:** The NGINX controller pod receives the traffic. It inspects the host/path headers against the defined Ingress rules and routes the request internally to the correct Kubernetes Service.
3.  **Service:** The Service (ClusterIP) receives the request. It uses its selector to find the backing Pods.
4.  **Endpoints:** The Service object maintains an Endpoints object, which is dynamically updated by the Kubelet to list the actual IP addresses of the healthy application Pods.
5.  **kube-proxy/iptables:** `kube-proxy` on the node intercepts the traffic destined for the Service ClusterIP and uses its configured iptables/IPVS rules to perform load balancing, forwarding the packet directly to one of the healthy Pod IPs.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A **NetworkPolicy** defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints.
*   **Default Behavior:** If no NetworkPolicy exists in a namespace, all traffic is allowed (the default behavior is "allow all").
*   **Applying a Policy:** When a NetworkPolicy is applied, the default behavior *changes* to "deny all" ingress and egress traffic for the selected pods, unless explicitly allowed by a rule within that policy.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old Pods with new Pods while keeping the desired number of replicas running. It allows zero-downtime deployments by managing the transition.
*   **Recreate:** Terminates all existing Pods of the application, waits for them to terminate, and then creates all new Pods.
*   **When to choose Recreate:** When the application is highly stateful, requires a clean shutdown sequence, or when the new version is fundamentally incompatible with the old version and a brief outage is acceptable.

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A **Namespace** is a mechanism to partition cluster resources (like Pods, Services, ConfigMaps) into virtual clusters within a single physical cluster. It provides scope and isolation.
*   **Default Namespaces:** `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
`kubectl describe pod <name>` provides a detailed status report on the pod's lifecycle and configuration.
1.  **Events:** A chronological log of actions taken on the pod (e.g., scheduling, pulling image, failing readiness checks).
2.  **Detailed Status Conditions:** Specific reasons for pending, running, or failed states (e.g., `Reason: ImagePullBackOff`).
3.  **Container/Volume Details:** Detailed information about resource requests, limits, and mounted volumes.

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A **ConfigMap** is an API object used to store non-confidential configuration data in key-value pairs, allowing configuration to be injected into Pods without rebuilding the image.
1.  **As Environment Variables:** Injecting keys/values directly into the container's environment variables.
2.  **As Mounted Files:** Mounting the ConfigMap as a volume inside the container, where each key becomes a file in the specified directory.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Exposes the Service on an internal IP address only, reachable from within the cluster.
*   **NodePort:** Exposes the Service on a static port on *every* Node's IP address. Traffic can reach the service via `<NodeIP>:<NodePort>`.
*   **LoadBalancer:** Exposes the Service externally using a cloud provider's load balancer (e.g., AWS ELB, GCP LB). The cloud provider provisions and manages the external IP.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A **DaemonSet** ensures that a copy of a Pod runs on *every* (or a selected subset of) eligible nodes in the cluster.
*   **Use Case:** When you need a service that must run locally on every node, such as a node-level log collector (Fluentd/Logstash agent), a monitoring agent (Prometheus Node Exporter), or a network plugin.

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints:** A property applied to a Node that repels Pods. They act as a "no entry" sign.
*   **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching Taint.
*   **Difference from Affinity:** Affinity (NodeAffinity) is a *preference* or *requirement* for placement (e.g., "prefer nodes with GPU"). Taints/Tolerations are a *hard exclusion/inclusion* mechanism.
*   **Use Case (Taint/Toleration):** Isolating a GPU node by tainting it (`dedicated=gpu:NoSchedule`), and only allowing GPU-requiring Pods to tolerate that taint.
*   **Use Case (Affinity):** Ensuring a database Pod is always scheduled on nodes within the same availability zone as its primary data store.

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An **Operator** is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers.
*   **Difference from Controller:** A standard controller reacts to the current state vs. the desired state (e.g., "If replica count < 3, create one"). An Operator encapsulates *human operational knowledge* (e.g., "When a primary database fails, promote the replica, update the connection string, and reconfigure the cluster").
*   **Problem Solved:** It automates complex, multi-step, domain-specific operational tasks that go beyond simple declarative state management.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
*   **Consistency Model:** etcd uses a strong consistency model based on the Raft consensus algorithm. This ensures that all committed writes are replicated across a majority of nodes before being acknowledged.
*   **Quorum Loss:** If the quorum (majority) of etcd nodes is lost (e.g., 2 out of 3 nodes fail), the cluster cannot achieve consensus. All write operations will fail, and the control plane (API Server) will become read-only or completely unavailable, leading to cluster instability.
*   **Recovery (2/3 lost):** If 2 out of 3 nodes are permanently lost, the cluster is irrecoverably broken because a majority cannot be formed. Recovery requires restoring the etcd cluster from a backup taken *before* the failure, and then reintroducing the nodes.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
*   **RBAC Flow:** RBAC defines *who* (Subject) can do *what* (Verb/Resource) on *which* resources.
    *   **Role:** Defines permissions scoped to a specific Namespace.
    *   **ClusterRole:** Defines permissions scoped across the entire cluster.
    *   **RoleBinding:** Binds a Role to a Subject (User/Group) within a specific Namespace.
    *   **ClusterRoleBinding:** Binds a ClusterRole to a Subject across the entire cluster.
*   **Manifests (Read-only Pods/Logs in 'dev'):**
    ```yaml
    # 1. Define the permissions (Role)
    apiVersion: rbac.authorization.k8s.io/v1
    kind: Role
    metadata:
      namespace: dev
      name: pod-reader
    rules:
    - apiGroups: [""]
      resources: ["pods"]
      verbs: ["get", "list", "watch"]
    - apiGroups: [""]
      resources: ["pods/log"]
      verbs: ["get"]

    ---
    # 2. Bind the permissions to a user/group (RoleBinding)
    apiVersion: rbac.authorization.k8s.io/v1
    kind: RoleBinding
    metadata:
      name: dev-reader-binding
      namespace: dev
    subjects:
    - kind: User
      name: developer-user # Replace with actual user/group
      apiGroup: rbac.authorization.k8s.io
    roleRef:
      kind: Role
      name: pod-reader
      apiGroup: rbac.authorization.k8s.io
    ```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
*   **The Problem (ndots):** The `ndots` setting dictates how many leading dots a hostname must have before the system attempts a search domain lookup. If `ndots` is set too low (or defaults to 1), and the pod tries to resolve an external domain like `google.com`, the system first tries to resolve it against the cluster's search domains (e.g., `svc.cluster.local`), which fails, forcing a query to the upstream DNS server, leading to unnecessary lookups and latency.
*   **The Fix (dnsConfig):** By using `dnsConfig` in the Pod spec, you can explicitly override the DNS settings. You can set `options` to specify the `ndots` value (e.g., `ndots: 5`) to tell the pod's resolver to only use search domains if the hostname has at least 5 dots, thus forcing direct queries for external domains.

## Development Answers

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines two divergent branches by creating a new "merge commit." It preserves the exact history of both branches.
*   **Rebase:** Rewrites history by moving the entire feature branch's commits to start *after* the tip of the target branch. It creates a linear, cleaner history.
*   **Avoid Rebasing:** You should **never** rebase commits that have already been pushed to a shared, public repository, as this rewrites history and causes major synchronization issues for collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered delivery. It uses a three-way handshake to establish a connection and guarantees packet delivery via acknowledgments and retransmissions. (Protocols: HTTP/1.1, FTP).
*   **UDP (User Datagram Protocol):** Connectionless, unreliable, fast. It sends packets without establishing a connection or guaranteeing delivery order. (Protocols: DNS, VoIP/SIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A **race condition** occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data.
*   **Example (Counter Increment):** If two threads try to increment a shared counter variable (`count = count + 1`) simultaneously, the operation is not atomic. Thread A reads `count` (e.g., 10), Thread B reads `count` (10). Thread A calculates 11 and writes it back. Thread B calculates 11 and writes it back. The counter should be 12, but it ends up as 11 because one update was lost.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is very fast.
*   **Asymmetric Encryption (Public Key Cryptography):** Uses a pair of keys: a public key (shared widely for encryption) and a private key (kept secret for decryption). It is computationally intensive.
*   **TLS Usage:** TLS uses both. First, the client and server use **asymmetric encryption** (via RSA or ECDH) to securely exchange a unique, ephemeral **symmetric session key**. Once the session key is established, all subsequent bulk data transfer is encrypted using the much faster **symmetric encryption**.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A container image is built from a series of read-only layers. Each instruction in a Dockerfile (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one.
*   **Caching Effect:** Docker caches the result of each layer. If a layer's instruction and its inputs (files) have not changed since the last build, Docker reuses the cached layer, significantly speeding up builds.
*   **Best Practices:** Place instructions that change infrequently (like installing OS packages: `RUN apt-get update && apt-get install -y ...`) near the top. Place instructions that change frequently (like copying application code: `COPY . /app`) near the bottom to maximize cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Application Logs (Deep Dive):** Check the application logs for specific exceptions, connection timeouts, or resource exhaustion errors that correlate with the 503s.
2.  **Resource Utilization (Metrics):** Check CPU, Memory, and I/O metrics for the service pods. High utilization often leads to throttling or inability to respond.
3.  **Service Mesh/Ingress Logs:** Check the ingress controller/service mesh logs to see if the request is even reaching the application, or if the load balancer is prematurely marking the pod as unhealthy.
4.  **Dependency Health:** Check the health and latency of any downstream services (databases, caches, external APIs) the API relies on, as these are common causes of intermittent 503s.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
*   **CAP Theorem:** States that a distributed data store can only guarantee two out of three properties simultaneously: **Consistency** (every read receives the most recent write), **Availability** (every request receives a response, without guarantee that it is the most recent write), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the system).
*   **CP Example (Consistency over Availability):** Traditional relational databases (like PostgreSQL clusters configured for strong consistency). If the network partitions, the system will refuse writes/reads on the minority side to prevent data divergence.
*   **AP Example (Availability over Consistency):** Cassandra or DynamoDB. If a partition occurs, nodes continue to accept reads and writes, potentially serving stale data, ensuring the service remains available.

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of an *existing* single server instance. (Easier, but has physical limits).
*   **Horizontal Scaling (Scaling Out):** Adding *more* instances (replicas) of the application behind a load balancer. (More resilient, virtually limitless).
*   **Patterns for Horizontal Scaling:** Statelessness (ensuring no session data is tied to a specific instance), Microservices architecture, and using a Load Balancer/Service Mesh.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An **environment variable** is a dynamic named value that can affect the way running processes will behave on a computer.
*   **Persistence:** To make it persist across shell sessions, you must add the export command to a shell startup file, such as `~/.bashrc` or `~/.zshrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays.
    *   *Advantage:* Extremely fast parsing speed, native support in JavaScript environments.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure.
    *   *Advantage:* Superior readability for complex configuration files (like Kubernetes manifests).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
A **REST API** (Representational State Transfer) is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources.
*   **GET:** Retrieves a resource or a collection of resources (Safe and Idempotent).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource.
*   **PUT:** Replaces an entire resource at a known URI (Idempotent).
*   **DELETE:** Removes a specified resource (Idempotent).

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
**Version pinning** is the practice of specifying an exact version number for every dependency in a project's manifest file (e.g., `package@1.2.3` instead of `package@^1.2.0`).
*   **Importance:** It ensures **reproducible builds**. Without pinning, a dependency manager might pull in a newer, potentially breaking version of a library when you rebuild the project months later, leading to "it worked on my machine" bugs.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled Language:** Source code is translated entirely into machine code (an executable binary) *before* runtime by a compiler. This results in faster execution. (Examples: C++, Go).
*   **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. This allows for greater portability but is generally slower. (Examples: Python, JavaScript).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Reverse Proxy:** Sits *in front* of one or more web servers. It intercepts client requests and forwards them to the appropriate backend server. The client never knows the backend server's identity.
*   **Forward Proxy:** Sits *in front* of the client. It acts as an intermediary for the client to access the internet, often used to mask the client's identity or enforce corporate filtering.
*   **Servers/Use Cases:**
    *   **NGINX:** Used for SSL termination, load balancing across multiple application servers.
    *   **HAProxy:** Used for high-performance TCP/HTTP load balancing, often used in complex multi-tier architectures.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A **deadlock** is a situation where two or more competing actions are waiting for the other to finish, resulting in a permanent standstill.
The four necessary conditions (Coffman conditions) are:
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4.  **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
**Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. There is a window of inconsistency.
*   **Cassandra Handling:** Cassandra uses mechanisms like **read repair** and **anti-entropy repair** (e.g., hinted handoffs) to propagate writes across replicas asynchronously.
*   **Tunable Consistency Levels:** Users specify how many replicas must respond successfully for a read or write operation to succeed. Examples include:
    *   `ONE`: Only one replica needs to respond (fastest, least consistent).
    *   `QUORUM`: A majority of replicas must respond (balances speed and consistency).
    *   `ALL`: All replicas must respond (slowest, most consistent).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
**mTLS** requires *both* the client and the server to present and validate cryptographic certificates during the TLS handshake, ensuring both parties are authenticated.
*   **Handshake Process:**
    1.  Client initiates connection.
    2.  Server sends its certificate to the client.
    3.  Client verifies the server's certificate against its trusted CAs.
    4.  **Client sends its certificate to the server.**
    5.  Server verifies the client's certificate against its trusted CAs.
    6.  If both validations pass, they proceed to exchange keys and establish the symmetric session.
*   **Use Case:** Service-to-service communication in a zero-trust network architecture (e.g., within a service mesh like Istio).

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an underlying array.
*   **Collision Resolution:** When two different keys hash to the same index:
    *   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hashed to that index.
    *   **Open Addressing:** If a slot is full, the algorithm probes for the next available slot in the array itself (e.g., linear probing, quadratic probing).
*   **Time Complexity:**
    *   **Average Case (Good Hash Function):** $O(1)$ for insertion, lookup, and deletion.
    *   **Worst Case (All keys collide):** $O(n)$ for all operations (effectively degrading to searching a linked list).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
The **Circuit Breaker** pattern prevents a service from repeatedly trying to execute an operation against a failing remote service, thus preventing resource exhaustion and cascading failures.
*   **States:**
    *   **Closed:** Normal operation. Requests pass through. If failures exceed a threshold, the breaker trips to Open.
    *   **Open:** Requests are immediately rejected without attempting the remote call (failing fast). After a timeout, the breaker moves to Half-Open.
    *   **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.
*   **Relation to Retries/Backoff:** Circuit breakers act as a *macro* failure defense. Retry policies and exponential backoff are *micro* defenses applied *within* the Closed state to handle transient errors before the breaker trips.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data *before* modification, preventing other transactions from reading or writing it until the lock is released. (High safety, lower concurrency).
    *   *Example:* Using `SELECT ... FOR UPDATE` in SQL.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locks. Before committing, the system checks if the data has been modified by another transaction since it was read. If it has, the transaction fails and must be retried. (High concurrency, requires retry logic).
    *   *Example:* Using a version column (e.g., `version_number`) in the table; the `UPDATE` statement includes a `WHERE version_number = [original_version]`.
