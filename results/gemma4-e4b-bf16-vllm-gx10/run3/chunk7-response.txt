## Application Architecture Answers

**AA1**
A **monolith** is a single, tightly coupled, indivisible unit where all business logic (UI, business services, data access) resides in one codebase and runs as one process. **Microservices** decompose an application into a collection of small, independent, loosely coupled services, each running its own process and communicating via lightweight mechanisms (like APIs).

Three concrete problems microservices introduce that monoliths don't have:
1. **Distributed Complexity:** Managing network latency, service discovery, and inter-service communication failures.
2. **Operational Overhead:** Deploying, monitoring, and managing dozens or hundreds of independent services instead of one application.
3. **Data Consistency:** Ensuring transactional integrity across multiple, independently managed databases (distributed transactions).

**AA2**
**Synchronous communication** requires the calling service to wait for an immediate response from the called service before proceeding. It is request-response based. *Example Technology: REST/HTTP.*
**Asynchronous communication** involves sending a message or event without waiting for an immediate response. The sender continues its work, and the receiver processes the message when it is available. *Example Technology: Kafka or RabbitMQ.*

**AA3**
An **API Gateway** acts as a single entry point for all clients, handling cross-cutting concerns like authentication, rate limiting, request routing, and protocol translation before forwarding requests to the appropriate backend microservice. A **Reverse Proxy** sits in front of one or more servers, primarily to forward client requests to the correct internal server, often handling SSL termination and load balancing.

An API Gateway *can* replace a reverse proxy entirely, but it is usually more than that. A reverse proxy's core function (routing/load balancing) is a subset of the API Gateway's functionality. The API Gateway adds crucial business-logic layers (security policies, throttling, request aggregation) that a basic reverse proxy lacks.

**AA4**
The **Saga pattern** is a sequence of local transactions where each transaction updates the database within a single service and publishes an event to trigger the next step. If any step fails, the Saga executes compensating transactions to undo the preceding changes, maintaining data consistency across the distributed system.

*   **Choreography-based Sagas:** Services communicate by producing and consuming events without a central coordinator. Each service knows what to do based on the events it receives. *Appropriate when:* the workflow is simple, decentralized, and services are highly autonomous.
*   **Orchestration-based Sagas:** A dedicated service (the Orchestrator) manages the workflow, telling each participant service what local transaction to execute via commands. *Appropriate when:* the workflow is complex, long-running, or requires centralized visibility and control over the sequence.

**AA5**
**CQRS (Command Query Responsibility Segregation)** separates the model used for updating data (Commands) from the model used for reading data (Queries). Commands change state; Queries retrieve state.

It is often paired with **Event Sourcing (ES)** because ES stores the state of an entity not as its current snapshot, but as a sequence of immutable domain events. The read model (Query side) is then built by projecting these events into a highly optimized, denormalized structure (e.g., a specific SQL table or document store).

This combination solves the problem of **read/write scaling mismatch** inherent in traditional CRUD. In CRUD, the same database structure must efficiently handle complex writes (updates) and complex reads (reporting/filtering). CQRS/ES allows you to optimize the write model for transactional integrity and the read model for specific query performance needs, often using entirely different data stores.

**AA6**
The **Circuit Breaker pattern** prevents an application from repeatedly trying to execute an operation that is likely to fail (e.g., calling a remote service that is down or overloaded).

The three states are:
1. **Closed:** Requests pass through normally. If failures exceed a threshold, the breaker trips to Open.
2. **Open:** Requests are immediately rejected without attempting the remote call, failing fast. After a timeout, the breaker moves to Half-Open.
3. **Half-Open:** A limited number of test requests are allowed through. If they succeed, the breaker closes; if they fail, it returns to Open.

It differs from a simple retry with backoff because a retry assumes the failure is transient and temporary. The Circuit Breaker assumes the failure is systemic (the downstream service is unhealthy) and stops traffic entirely to allow the service time to recover, preventing resource exhaustion on both sides. They are used together: the Circuit Breaker prevents overwhelming a failing service, and the retry mechanism handles transient network hiccups *before* the breaker trips.

**AA7**
| Model | Cost | Security | Operational Complexity | Noisy-Neighbor Risk |
| :--- | :--- | :--- | :--- | :--- |
| **1. Shared DB, Shared Schema** | Lowest | Lowest (Requires strict application-level enforcement) | Lowest | Highest (One bad query affects all tenants) |
| **2. Shared DB, Separate Schema** | Low | Medium (Schema separation provides logical isolation) | Medium (Need schema migration tooling) | Medium (Resource contention on the DB instance) |
| **3. Separate DB per Tenant** | Highest | Highest (Strongest isolation boundary) | Highest (Managing N databases) | Lowest (Resource isolation is physical/logical) |

**Trade-offs Summary:**
*   **Cost:** Model 1 $\ll$ Model 2 $<$ Model 3.
*   **Security:** Model 3 $>$ Model 2 $>$ Model 1.
*   **Operational Complexity:** Model 1 $\ll$ Model 2 $<$ Model 3.
*   **Noisy-Neighbor Risk:** Model 3 $\ll$ Model 2 $<$ Model 1.

**AA8**
**Strong Consistency** guarantees that once a write operation is acknowledged, all subsequent read operations, regardless of which replica they hit, will return that updated value immediately. **Eventual Consistency** guarantees that if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value, but there is a window where reads may return stale data.

To prevent overselling inventory (a critical business invariant), **Strong Consistency** is required for the inventory decrement operation.
*   **Consistency Model:** Strong Consistency (or Linearizability).
*   **Data Store:** A strongly consistent, transactional database (e.g., PostgreSQL with strong ACID guarantees, CockroachDB, or a distributed ledger).
*   **Patterns:** Use pessimistic locking or atomic database transactions during the checkout/inventory update process. For high scale, use distributed consensus algorithms (like Raft or Paxos) provided by the data store to ensure all nodes agree on the inventory count before confirming the sale.

**AA9**
A **sidecar proxy** is a small, dedicated proxy container deployed alongside every instance of a service container within the same deployment unit (e.g., a Kubernetes Pod). It intercepts all inbound and outbound network traffic for the main application container.

In an **Istio deployment**, Envoy is the proxy that runs as the sidecar. Istio's **Control Plane** (e.g., Istiod) configures these Envoy proxies. The Control Plane pushes configuration (routing rules, security policies, traffic splitting) down to the data plane proxies (Envoy).

**Data Plane vs Control Plane:**
*   **Data Plane:** The set of proxies (Envoy) that actually handles the traffic, enforces policies, and performs the work (e.g., routing, mTLS encryption/decryption).
*   **Control Plane:** The management layer (Istiod) that configures and manages the data plane proxies.

**mTLS between sidecars** solves the problem of **untrusted network hops** in a dynamic environment. Application-level TLS requires the application code to manage certificates, key rotation, and handshake logic. Sidecar mTLS, managed by the service mesh, automatically handles mutual authentication (both client and server prove identity using certificates) for *every* service-to-service call, ensuring that only authenticated and authorized services can communicate, regardless of the underlying network configuration.

**AA10**
The **Strangler Fig pattern** is an incremental migration strategy where a new system (the microservices) is built around a legacy system (the monolith). Over time, new functionality is built in the microservices, and traffic is gradually rerouted away from the monolith until the monolith can be "strangled" and retired.

**Migration Strategy (Monolith $\rightarrow$ Microservices):**
1.  **Identify Seams:** Identify a bounded context within the monolith that is relatively self-contained (e.g., User Profile Management).
2.  **Build New Service:** Implement the User Profile functionality as a new, independent .NET 8 microservice.
3.  **Implement Facade/Routing:** Place an API Gateway in front of the monolith. Configure the Gateway to route all requests for `/api/users/*` to the new microservice, while all other requests continue to hit the monolith.
4.  **Data Synchronization (if necessary):** If the new service needs data owned by the monolith, implement a mechanism (like Change Data Capture or event publishing from the monolith) to keep the new service's data store synchronized initially.
5.  **Strangulation:** Once the new service is stable and handles all traffic for that domain, the corresponding code path in the monolith is deprecated and eventually removed. Repeat for the next bounded context.

**AA11**
The **12-Factor App methodology** is a set of best practices for building modern, cloud-native, portable, and resilient software-as-a-service applications.

Six factors and their importance:
1.  **Codebase:** One codebase tracked in revision control, many deploys. *Why:* Enables CI/CD and rapid iteration.
2.  **Dependencies:** Explicitly declare and isolate dependencies. *Why:* Ensures environment consistency across development, staging, and production.
3.  **Config:** Store configuration in the environment. *Why:* Decouples configuration from code, allowing the same artifact to run in different environments (e.g., Dev vs Prod).
4.  **Backing Services:** Treat backing services (databases, caches, message queues) as attached resources. *Why:* Allows swapping out implementations (e.g., switching from Redis to Memcached) without changing core code.
5.  **Build, Release, Run:** Strictly separate these stages. *Why:* Allows for immutable artifacts; the same build artifact can be deployed to multiple environments with different configurations.
6.  **Processes:** Execute the application as one or more stateless processes. *Why:* Essential for horizontal scaling; any instance can handle any request.

**AA12**
| Feature | Event-Driven (Kafka) | Request-Driven (REST/gRPC) |
| :--- | :--- | :--- |
| **Coupling** | Loose (Temporal and spatial decoupling) | Tight (Synchronous dependency) |
| **Scalability** | Excellent (Consumers scale independently based on topic load) | Good (Requires load balancing, but scaling is coupled to request volume) |
| **Debugging Complexity** | High (Tracing flow across asynchronous boundaries is hard) | Low (Direct call stack tracing is straightforward) |
| **Ordering Guarantees** | Guaranteed within a partition/topic | Guaranteed by the request/response sequence |
| **Failure Handling** | Built-in resilience via message retention; consumers retry processing. | Requires explicit implementation (retries, circuit breakers) on the client side. |

**When to Choose:**
*   **Event-Driven:** Choose when the system needs to react to state changes across multiple services (e.g., Order Placed $\rightarrow$ Inventory Decremented $\rightarrow$ Email Sent). Ideal for high throughput, decoupling, and long-running processes.
*   **Request-Driven:** Choose when an immediate response is required to complete a user workflow (e.g., "Get User Details," "Submit Login Credentials"). Ideal for synchronous user interactions.

**AA13**
A **load balancer** is a device or software that distributes incoming network traffic across a group of backend servers (a server farm or pool) to ensure no single server becomes a bottleneck, thereby maximizing throughput and availability.

*   **Layer 4 (Transport Layer):** Operates at the TCP/UDP level. It makes routing decisions based on IP addresses and port numbers. It is "dumb" regarding the content of the request.
*   **Layer 7 (Application Layer):** Operates at the HTTP/HTTPS level. It inspects the actual content of the request (headers, URLs, cookies) to make routing decisions.

**Layer 7 Use Case:** Routing traffic based on the URL path (e.g., sending `/api/v1/users` to Service A and `/api/v2/billing` to Service B, even if they share the same IP/port).

**AA14**
A **message queue** (e.g., RabbitMQ) is a point-to-point or publish/subscribe system designed for reliable message delivery. Messages are typically consumed and *removed* from the queue once successfully processed by a consumer.

A **log-based message broker** (e.g., Kafka) functions as a distributed, immutable commit log. Messages are *persisted* and retained for a configurable period, allowing multiple consumers to read the same message stream at different times or speeds.

**When to Pick Which:**
*   **Message Queue:** Pick when you need guaranteed, single consumption of a task (e.g., "Process this payment request once").
*   **Log-Based Broker:** Pick when you need replayability, stream processing, or when multiple independent services need to react to the same stream of events (e.g., "Log every user click event for analytics and real-time monitoring").

**AA15**
A **container** (e.g., Docker) is a lightweight, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings. It shares the host operating system's kernel.

A **Virtual Machine (VM)** virtualizes the entire hardware stack, including the kernel. Each VM runs its own complete Guest OS on top of a hypervisor.

Containers are popular for microservices because they offer **high density** (many more containers than VMs on the same hardware) and **fast startup times** because they don't need to boot an entire OS. They provide process isolation without the heavy overhead of hardware emulation.

**AA16**
A **stateless service** does not retain any session-specific data between requests. Every request from a client to the service must contain all the necessary information for the service to fulfill it.
A **stateful service** retains data or context across multiple requests (e.g., user session data, in-memory caches).

Stateless services are easier to scale horizontally because any incoming request can be routed to *any* available instance, as no instance holds unique session information that would need to be maintained or synchronized across the cluster.

*   **Stateless Example:** A REST API endpoint that processes a simple calculation based on input parameters.
*   **Stateful Example:** A traditional session server that stores user login state in its local memory.

**AA17**
An **ORM (Object-Relational Mapper)** is a programming technique that allows developers to interact with a relational database using the paradigm of object-oriented programming (i.e., manipulating objects in code) rather than writing raw SQL queries.

*   **Popular ORMs:** Hibernate (Java), Entity Framework (.NET).
*   **Trade-offs:**
    *   **ORM Pros:** Increased developer productivity, database portability (less vendor lock-in), type safety.
    *   **ORM Cons:** Performance overhead (due to abstraction layers), the "N+1 query problem," and difficulty mapping complex, non-relational business logic to rigid relational structures. Raw SQL offers maximum performance tuning and control.

**AA18**
The **Bulkhead pattern** isolates components of an application so that the failure or resource exhaustion in one component does not cascade and bring down the entire system. It partitions resources (like thread pools or connection pools) into isolated compartments, much like watertight compartments in a ship.

It relates to resource isolation by ensuring that if one service dependency becomes slow or fails, it only consumes the resources allocated to its specific bulkhead, leaving resources available for other, healthy services.

**Implementation Example:** If Service A calls Service B and Service C, you would implement two separate, limited thread pools (bulkheads) for the outbound calls: one pool dedicated to Service B and another dedicated to Service C. If Service B starts timing out and consuming all threads in its pool, Service C's calls can still proceed using its dedicated pool.

**AA19**
| Feature | Operational Transformation (OT) | Conflict-free Replicated Data Types (CRDTs) |
| :--- | :--- | :--- |
| **Consistency Guarantees** | Strong (Requires centralized coordination/server authority) | Eventual (Converges mathematically without coordination) |
| **Latency** | Higher (Requires round-trip communication to the central server for transformation) | Lower (Operations can be applied locally immediately) |
| **Complexity** | High (Complex transformation algorithms are difficult to implement correctly) | Medium (Requires careful selection of the correct data structure) |
| **Offline Support** | Poor (Requires synchronization with the central server upon reconnection) | Excellent (Operations are commutative and associative; they can be applied in any order later) |

**Choice:** I would choose **CRDTs**. For a system that *must* support offline editing, the ability of CRDTs to merge concurrent, unordered operations deterministically without a central authority is paramount. OT fundamentally relies on a central server to order and transform operations correctly.

**AA20**
**Challenges in Polyglot Tracing:**
1.  **Context Propagation:** Ensuring the unique trace ID and span ID are passed correctly across service boundaries, especially when services use different languages or communication protocols.
2.  **Sampling:** Deciding which requests to trace. Head-based sampling decides at the entry point (e.g., trace 1 in 100 requests). Tail-based sampling waits until the entire trace is complete to decide whether to keep it, which is more accurate but requires more infrastructure.
3.  **Storage/Querying:** Storing high-volume trace data efficiently and providing tools (like Jaeger or Tempo) to reconstruct the flow across potentially hundreds of services.
4.  **Asynchronous Messaging:** The biggest challenge. When a request hits Kafka, the original trace context must be injected into the message headers. The consumer service must then extract this context and start a *new child span* linked to the original trace ID.

**Ensuring Trace Continuity via Kafka:** The producer service must inject the current trace context (e.g., using W3C Trace Context headers) into the Kafka message headers before publishing. The consumer service must be instrumented to read these headers upon consumption, extract the trace ID, and use it to create a new span that is explicitly marked as a child of the producer's span, thus maintaining the continuity of the trace across the asynchronous boundary.

## On-Premise Infrastructure Architecture Answers

**OP1**
A **Type 1 (Bare-Metal) Hypervisor** runs directly on the host hardware, managing the hardware resources and allocating them to guest VMs. It has near bare-metal performance because there is no intervening host OS. *Examples: VMware ESXi, Microsoft Hyper-V (when run directly).*
A **Type 2 (Hosted) Hypervisor** runs as an application *on top of* a conventional host operating system. It relies on the host OS to manage hardware access. *Examples: VMware Workstation, Oracle VirtualBox.*

**OP2**
**SAN (Storage Area Network):** A dedicated, high-speed network that provides block-level storage access to servers. The server sees the storage as a local disk volume. *Use Case: High-performance transactional databases.* *Protocols: Fibre Channel (FC), iSCSI.*
**NAS (Network Attached Storage):** A file-level storage device accessible over the standard network. The server mounts the storage as a network share. *Use Case: File sharing, backups, home directories.* *Protocols: NFS, SMB/CIFS.*

**OP3**
**3-Tier Architecture:**
1.  **Access Layer:** Connects end-user devices (PCs, phones) to the network. Handles basic connectivity.
2.  **Distribution Layer:** Aggregates traffic from the Access layer. Provides policy enforcement, routing, and redundancy between access blocks.
3.  **Core Layer:** The high-speed backbone of the network. Its sole job is fast, reliable packet switching between distribution blocks.

**Leaf-Spine Preference:** The 3-tier model creates bottlenecks and limits east-west traffic (server-to-server communication) because traffic must often traverse up to the Distribution layer and back down. The **Leaf-Spine** architecture creates a non-blocking, predictable, low-latency fabric. Every Leaf switch connects to every Spine switch, ensuring that any two endpoints are separated by a maximum of two hops (Leaf $\rightarrow$ Spine $\rightarrow$ Leaf), solving the scalability and latency issues of the traditional hierarchy.

**OP4**
**Architecture Design:**
*   **Node Count:** Minimum 3 nodes for quorum in a cluster.
*   **Quorum:** Achieved via Corosync/Pacemaker consensus mechanisms. A majority (N/2 + 1) must agree on the cluster state.
*   **Fencing (STONITH):** Essential. If a node fails, fencing mechanisms (e.g., IPMI power cycling, network isolation) must be used to ensure the failed node cannot corrupt shared storage by holding stale locks.
*   **Shared Storage Options:** **Ceph** is preferred for modern, software-defined clusters as it provides distributed storage natively. iSCSI/NFS can be used, but Ceph integrates better with the cluster management.
*   **Node Failure:** If one node fails, the remaining nodes maintain quorum (assuming $\ge 3$ nodes). The cluster manager detects the failure, and the services/VMs running on the failed node are automatically migrated (live migration if possible, or restarted) onto the remaining healthy nodes, utilizing the shared storage pool.

**OP5**
**VLAN Trunking:** The process of allowing traffic from multiple VLANs to traverse a single physical link (trunk port) between network devices (switches).
**802.1Q Tagging:** The standard protocol used for trunking. It inserts a 4-byte tag into the Ethernet frame header, which contains a specific **VLAN ID (VID)**, allowing the receiving switch to know which VLAN the frame belongs to, even though it traveled over a single physical wire.

**Linux Configuration (Single NIC, 3 VLANs):**
1.  Create the physical interface (e.g., `eth0`).
2.  Create logical VLAN interfaces using `ip link add link eth0 name eth0.10 type vlan id 10`.
3.  Repeat for VLAN 20 (`eth0.20`) and VLAN 30 (`eth0.30`).
4.  Assign IP addresses and bring up each logical interface (`ip addr add ...` and `ip link set up`).

**OP6**
*   **RAID 1 (Mirroring):** Duplicates data across two or more drives. High read performance, 50% capacity loss. Excellent fault tolerance (can lose N-1 drives).
*   **RAID 5 (Striping with Parity):** Stripes data across drives and distributes parity information. Can tolerate one drive failure. Good balance of capacity and fault tolerance.
*   **RAID 6 (Striping with Dual Parity):** Stripes data and distributes two independent parity blocks. Can tolerate two drive failures. Higher write penalty than RAID 5.
*   **RAID 10 (Mirroring + Striping):** Stripes data across mirrored sets. Offers excellent read/write performance and high fault tolerance (as long as failures are not in the same mirrored pair).
*   **RAID Z2 (ZFS):** ZFS's implementation of RAID 6. Provides dual parity protection.

**Choice for Database Server (6 drives):** **RAID 10**. While RAID 6 offers better capacity utilization, RAID 10 provides superior, predictable **I/O performance** (crucial for databases) and excellent fault tolerance, as the failure of two drives in different mirrored pairs is survivable.

**OP7**
**DNS Architecture Design:**
1.  **Internal Resolvers (Recursive):** Internal DNS servers (e.g., Windows DNS servers) act as recursive resolvers for internal clients. They query authoritative servers for external domains and use forwarders to reach external DNS servers.
2.  **Authoritative Servers:** These servers hold the actual zone files for the organization's domains (e.g., `corp.local`).
3.  **DMZ Servers:** These servers host the public-facing records (e.g., `www.company.com`) and are authoritative for the public zone.
4.  **Split-Horizon DNS:** The internal resolvers are configured to serve different records based on the client's source IP address. Internal clients resolve to internal IPs; external queries resolve to public IPs.
5.  **DNSSEC:** Applied only to the external (public) zone to cryptographically sign records, ensuring data integrity against tampering.
6.  **Conditional Forwarding:** Internal resolvers are configured to forward queries for specific internal domains (like Active Directory domains) directly to the appropriate internal domain controllers, bypassing external lookups.

**Laptop Movement:** When a laptop moves from the office (on the internal network) to the VPN, its source IP changes. The internal DNS resolvers, seeing the new IP, will correctly serve the internal, private IP addresses for internal resources, maintaining seamless access.

**OP8**
**PKI Chain of Trust:**
1.  **Root CA (Offline):** The ultimate trust anchor. It is kept offline (air-gapped) and highly secured. It signs the subordinate CA certificate.
2.  **Subordinate/Issuing CA:** This CA is online and performs the day-to-day signing of end-entity certificates (e.g., for servers or users). It is trusted because it was signed by the Root CA.
3.  **End-Entity Certificate:** The certificate issued to the actual resource (e.g., `webserver.corp.com`). It is signed by the Subordinate CA.

**CRL vs OCSP:**
*   **CRL (Certificate Revocation List):** A periodically published list of all revoked certificates. Clients must download and check this list. (Can be slow/stale).
*   **OCSP (Online Certificate Status Protocol):** A real-time query service where a client asks the CA, "Is this specific certificate valid?" (Faster, more immediate).

**Certificate Templates & Auto-Enrollment:** Templates define the rules (key length, validity period, usage) for different types of certificates. Auto-enrollment allows client machines to automatically request and receive certificates from the Issuing CA without manual intervention, using Active Directory integration.

**Consequences of Compromise:**
*   **Compromised Subordinate CA:** High impact. An attacker can issue fraudulent certificates for any service within the scope of that CA. The damage is contained to that CA's scope, and the Root CA can revoke the Subordinate CA certificate.
*   **Compromised Root CA:** Catastrophic. Since the Root CA is the ultimate trust anchor, if it is compromised, *every* certificate issued under its trust chain is untrustworthy, requiring a complete, organization-wide PKI rebuild.

**OP9**
| Technology | Cost | Reliability | Latency | Management Complexity | Security Posture |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **MPLS** | Very High | Very High (Carrier managed) | Low (Guaranteed QoS) | Low (Carrier handles core) | High (Private network) |
| **IPsec VPN** | Low | Medium (Dependent on ISP) | Medium/High (Over public internet) | Medium (Requires endpoint configuration) | Medium (Encryption is strong, but path is public) |
| **SD-WAN** | Medium | High (Intelligent path selection) | Low/Medium (Optimizes paths) | Medium (Centralized controller) | High (Can use encrypted tunnels) |
| **WireGuard Mesh** | Very Low | Medium (Peer-to-peer) | Low (Modern crypto) | High (Manual peer configuration) | High (Strong, modern crypto) |

**Recommendation:** **SD-WAN**. For 50 users per site with latency-sensitive VoIP, SD-WAN provides the best balance. It leverages cheaper internet links (low cost) but uses intelligent path selection to steer VoIP traffic over the best available path (low latency/high reliability), while maintaining strong encryption (high security).

**OP10**
**iDRAC/iLO/IPMI:** These are **Baseboard Management Controllers (BMC)**. They are dedicated, low-level management processors embedded on the server hardware that allow administrators to monitor and control the server hardware (power state, temperature, fan speed, BIOS access) *independent* of the main operating system.

**Out-of-Band Management Criticality:** It is critical because if the OS crashes, the network stack fails, or the server is powered off, you still need a way to access the machine to diagnose the problem, reboot it, or attach a console.

**Internet Exposure Risk:** If the IPMI interface is exposed to the internet, it becomes a massive, unauthenticated attack vector. An attacker could remotely power cycle, reboot, or potentially gain low-level access to the server hardware, bypassing all OS-level security controls.

**OP11**
*   **LVM (Logical Volume Manager):** A software layer that abstracts physical disks into flexible logical volumes. It allows resizing and managing storage volumes dynamically *after* the OS is running. Snapshot semantics are typically **crash-consistent** (the state at the moment the snapshot command was issued).
*   **LVM-Thin:** An extension of LVM that allows for thin provisioning, meaning you can allocate more logical space than you have physical space, and only consume physical space as data is written. Snapshot semantics are also generally **crash-consistent**.
*   **ZFS:** A complete file system and volume manager. It manages storage pools, volumes, and datasets. Its snapshot semantics are **transactional/application-consistent** because ZFS tracks data changes at the block level, allowing for near-perfect point-in-time recovery.

**Usage:** Use LVM for simple volume resizing on existing systems. Use LVM-Thin for dynamic provisioning where space needs to be allocated on demand. Use ZFS when data integrity, advanced features (like checksumming), and application-consistent snapshots are paramount.

**OP12**
**Stretch Cluster/DR Strategy:** To survive a complete site failure, the cluster must span two geographically distant sites (Site A and Site B).

*   **Ceph CRUSH Rules:** Must be configured to ensure that data replicas are spread across different failure domains (racks, data centers). For a stretch cluster, you must define failure domains that span both sites.
*   **Monitor Placement:** Monitors must be placed in both sites, but the quorum mechanism must be robust enough to handle the network partition between sites.
*   **Network Latency:** This is the biggest constraint. High latency (e.g., >100ms) severely degrades the performance of consensus protocols (like Raft used by Ceph monitors), leading to instability.
*   **Split-Brain Problem:** This occurs when network partitioning causes both sides of the cluster to believe the other side has failed, leading both sides to independently take control of resources (e.g., two nodes thinking they are the primary). **Why 2-site Ceph is bad without a tiebreaker:** If the link between Site A and Site B fails, both sites might have a majority of monitors locally, leading to a split-brain scenario where both sides try to manage the cluster state, resulting in data corruption. A tiebreaker (like a witness node placed in a third, neutral location) is required to ensure only one side can achieve quorum.

**OP13**
**DHCP (Dynamic Host Configuration Protocol):** A network protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server information to devices on a network.

**DORA Process:**
1.  **Discover:** Client broadcasts a DHCP Discover message to find available servers.
2.  **Offer:** DHCP servers respond with a DHCP Offer, proposing an IP address and lease terms.
3.  **Request:** The client broadcasts a DHCP Request, formally accepting the offered IP address.
4.  **Acknowledge:** The server sends a DHCP ACK, finalizing the lease assignment.

**Server Unavailable:** If the DHCP server is unavailable and a Windows client's lease expires, the client will continue using its current IP address until the lease time expires. Once expired, it will attempt to renew the lease. If renewal fails, the client will typically enter a "limited connectivity" state, unable to communicate outside its local subnet, until it can successfully obtain a new lease or the lease time is manually extended/reconfigured.

**OP14**
**Unmanaged Switch:** A plug-and-play device that operates at Layer 2. It learns MAC addresses and forwards frames based on those addresses. It has no configuration interface and provides basic connectivity.

**Managed Switch:** A switch that offers a configuration interface (CLI/Web GUI).

**Enterprise Features:** Managed switches provide crucial features like:
*   **VLAN Tagging/Trunking:** Segmenting broadcast domains for security and organization.
*   **QoS (Quality of Service):** Prioritizing critical traffic (like VoIP) over bulk data transfers.
*   **Port Security:** Limiting the number of MAC addresses allowed on a port to prevent unauthorized device connection.
*   **SNMP Monitoring:** Allowing network management systems to monitor port status, traffic load, and errors.

**OP15**
**NTP (Network Time Protocol):** A protocol used to synchronize the clocks of computer systems over a network to a highly accurate time source.

**Criticality:** Accurate time synchronization is vital because many distributed systems rely on timestamps for ordering events, logging, and security.

**Consequences of Clock Drift:**
1.  **Log Correlation Failure:** When troubleshooting, logs from different servers cannot be accurately sequenced, making root cause analysis impossible.
2.  **Distributed Transaction Failure:** Systems relying on time-based locks or sequence numbers (like distributed databases) can fail or enter inconsistent states if clocks disagree.
3.  **Security Issues:** Kerberos authentication and certificate validation rely heavily on time synchronization; drift can cause authentication failures.

**OP16**
*   **Physical Server:** The actual, tangible hardware machine (CPU, RAM, NICs).
*   **Virtual Machine (VM):** A software emulation of a physical computer. It runs a full Guest OS on top of a hypervisor, which abstracts the physical hardware.
*   **Container:** A lightweight, isolated process environment that shares the host OS kernel. It only packages the application and its dependencies, not a full OS.

**Bare Metal Use Case:** You would run a workload directly on bare metal when:
1.  **Absolute Lowest Latency is Required:** For high-frequency trading or specialized hardware acceleration where the overhead of the hypervisor/OS kernel is unacceptable.
2.  **Hardware Specificity:** When the application requires direct, low-level access to specific hardware features (e.g., specialized GPUs or FPGAs) that virtualization layers might abstract away or limit.

**OP17**
**UPS (Uninterruptible Power Supply):** Provides immediate, short-term battery backup power when utility power fails. Its role is to bridge the gap between the power outage and the generator starting up, allowing for a graceful shutdown or continuous operation during the transition.

**Generator:** Provides long-term, sustained power during extended outages.

**Why Both:** The UPS handles the *instantaneous* failure (milliseconds), while the generator handles the *prolonged* failure (hours/days).

**ATS (Automatic Transfer Switch):** This device monitors the utility power. When utility power fails, the ATS automatically signals the generator to start and then switches the facility load from the utility feed to the generator feed. When utility power returns, the ATS switches the load back to the utility.

**OP18**
**Active-Passive Clustering:** One node (Active) handles all the workload, while the other node (Passive/Standby) remains powered on, synchronized, and ready to take over immediately if the Active node fails. It consumes resources but does no work.
**Active-Active Clustering:** Both nodes actively handle portions of the workload simultaneously. This provides higher resource utilization and better load distribution.

**PostgreSQL HA Implementation (Pacemaker/Corosync):**
1.  **Corosync:** Provides the cluster communication and membership service, ensuring all nodes agree on who is alive.
2.  **Pacemaker:** The cluster resource manager that monitors the health of the PostgreSQL service.
3.  **Virtual IPs (VIP):** A floating IP address is configured. Pacemaker ensures that only the active node owns this VIP. Clients connect to the VIP, not the specific server IP.
4.  **Fencing (STONITH):** This is critical. If the Active node fails, Pacemaker must use STONITH (Shoot The Other Node In The Head) to forcibly isolate or power off the failed node. This prevents the failed node from coming back online and trying to claim the VIP or write to the shared data, which would cause data corruption.
5.  **Failover Behavior:** If the Active node fails, Corosync detects the failure, Pacemaker initiates the failover, the VIP is moved to the Passive node, and the Passive node starts PostgreSQL, taking over the service.

**OP19**
**3-2-1 Rule:** Maintain **3** copies of your data, on **2** different types of media, with **1** copy stored offsite.

**RPO/RTO:**
*   **RPO (Recovery Point Objective):** The maximum acceptable amount of data loss measured in time (e.g., 1 hour). Dictates backup frequency.
*   **RTO (Recovery Time Objective):** The maximum acceptable downtime measured in time (e.g., 4 hours). Dictates recovery speed and infrastructure readiness.

**Backup Types:**
*   **Full:** A complete copy of all selected data. (Slowest backup, fastest restore).
*   **Incremental:** Backs up only the data that has changed since the *last* backup of any type. (Fastest backup, slowest restore, as it requires the last full + all subsequent incrementals).
*   **Differential:** Backs up all data that has changed since the *last full* backup. (Slower than incremental, faster restore than incremental).

**Deduplication:** Reduces storage footprint by identifying and storing only unique data blocks, regardless of how many times they appear across different files or backups.

**Storage Tiers:**
*   **Disk (Local/SAN):** For fast, frequent operational backups (short-term RTO).
*   **Tape:** For long-term, archival, low-cost storage (low access frequency).
*   **Cloud Offsite:** For geographic redundancy and disaster recovery (DR).

**Immutable Backups:** Backups written to storage that cannot be modified, deleted, or encrypted by anyone (including administrators) for a set period. This is the primary defense against ransomware encrypting or deleting backup sets.

**Testing Restores:** The most critical step. Regularly schedule test restores to a non-production environment to validate that the RTO/RPO targets are achievable and that the backup files are actually usable.

**Backup vs. Disaster Recovery (DR):**
*   **Backup:** The process of creating copies of data to protect against data loss (e.g., accidental deletion, corruption).
*   **Disaster Recovery (DR):** The comprehensive plan and infrastructure required to restore *business operations* after a catastrophic event (e.g., fire, regional power grid failure). DR relies on backups but includes failover procedures, network reconfiguration, and application startup sequencing.

**OP20**
**802.1X (Port-Based Network Access Control):** A standard that controls which devices are allowed to connect to a wired network port. It enforces authentication *before* granting network access.

**Roles:**
*   **Supplicant:** The client device (laptop, server) requesting access.
*   **Authenticator:** The network access device (the switch) that enforces the policy and relays authentication messages.
*   **Authentication Server:** The central authority (usually RADIUS) that verifies the supplicant's credentials.

**EAP Methods:**
*   **EAP-TLS:** The most secure method. It requires both the supplicant and the server to present and validate digital certificates (mutual authentication).
*   **PEAP (Protected EAP):** A tunnel-based method where the server authenticates using a certificate, and then the client authenticates using username/password *inside* that secure tunnel.

**RADIUS:** The protocol used by the Authenticator (switch) to communicate authentication requests, credentials, and authorization policies to the Authentication Server.

**Dynamic VLAN Assignment:** Upon successful authentication, the RADIUS server can instruct the switch (via RADIUS attributes) to place the supplicant onto a specific VLAN, allowing granular network segmentation based on user role (e.g., "Guest" VLAN vs. "Employee" VLAN).

**Failed Authentication:** If a device fails authentication, the switch, acting as the Authenticator, places the port into an unauthorized state (often a restricted VLAN or completely shuts down the port), preventing it from accessing any production network resources.

**MAB (MAC Authentication Bypass):** Used for devices that cannot run 802.1X supplicants (e.g., printers, IP phones). MAB allows the switch to use the device's burned-in MAC address as its identity credential and sends this MAC address to the RADIUS server for authorization, bypassing the need for a full EAP exchange.
