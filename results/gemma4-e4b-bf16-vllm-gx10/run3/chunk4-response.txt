## Go Answers

**G1** — An array in Go has a fixed size determined at compile time (e.g., `[5]int`). A slice is a dynamically sized, flexible view into an underlying array. When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array, copies the existing elements, and then appends the new element(s).

**G2** — `var x int` declares a variable `x` and initializes it to its zero value (which is `0` for `int`). `x := 0` is a short variable declaration, which declares and initializes `x` in one step. You cannot use `:=` when redeclaring a variable within the same scope, or when the variable has already been declared using `var` or `:=`.

**G3** — A goroutine is a lightweight, independently executing function managed by the Go runtime. It differs from an OS thread because goroutines are multiplexed onto a smaller number of OS threads by the Go scheduler. The Go scheduler (GMP model) maps Goroutines (G) onto OS threads (M) using a pool of logical processors (P). This allows Go to efficiently run thousands of concurrent tasks with minimal overhead compared to OS threads.

**G4** — Channels are typed conduits through which you can send and receive values between goroutines, providing a mechanism for safe communication (CSP model). An unbuffered channel requires both the sender and receiver to be ready simultaneously for the communication to proceed (synchronous). A buffered channel has a fixed capacity; sends block only when the buffer is full, and receives block only when the buffer is empty. When sending to a full buffered channel, the sending goroutine blocks until another goroutine receives a value, freeing up space in the buffer.

**G5** — The `context` package is used to carry deadlines, cancellation signals, and other request-scoped values across API boundaries and between goroutines. It allows you to propagate cancellation signals down a call stack, preventing goroutines from running indefinitely.
Example:
```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	req, _ := http.NewRequestWithContext(ctx, "GET", "http://example.com", nil)
	
	// The request will automatically be canceled if the context times out
	client := http.Client{}
	resp, err := client.Do(req)
	
	if err != nil {
		fmt.Println("Request failed or timed out:", err)
	} else {
		resp.Body.Close()
		fmt.Println("Request succeeded.")
	}
}
```

**G6** — Go's interface satisfaction is implicit (structural typing). A type satisfies an interface simply by implementing all the methods declared in that interface; there is no explicit `implements` keyword. This differs from Java/C# where explicit declaration is often required. The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (polymorphism without inheritance), but it is dangerous because the compiler loses all type information, forcing runtime type assertions or reflection, which can lead to runtime panics if misused.

**G7** — This code is unsafe because of data races. The goroutine writes to `data` and `ready` concurrently with the main goroutine reading `ready` and then `data`. Go's memory model guarantees that writes are visible to other goroutines *only* if synchronization primitives (like channels or mutexes) are used. The loop `for !ready {}` is a busy wait that might spin indefinitely or read stale values of `ready` and `data` due to compiler/CPU optimizations.
Correct alternatives:

2. **Mutex:** Protect access to `ready` and `data` using `sync.Mutex`.

**G8** — `sync.Mutex` provides exclusive locking: only one goroutine can hold the lock at a time (read or write). `sync.RWMutex` allows multiple readers to hold the lock simultaneously (`RLock`) but requires exclusive access for writers (`Lock`). Use `RWMutex` when reads vastly outnumber writes to improve concurrency. Use `sync.Map` when you have a map where keys are frequently added, deleted, or updated concurrently, as it is optimized for concurrent access patterns, often outperforming a standard `map` protected by a `sync.Mutex` in high-contention scenarios, though it has different semantics and overheads.

**G9** — Go modules manage dependencies. `go.mod` lists the required modules and their version constraints (e.g., `require github.com/pkg/errors v0.9.1`). `go.sum` contains cryptographic checksums for the exact content of every dependency listed in `go.mod`, ensuring that the downloaded code hasn't been tampered with. `go mod tidy` cleans up the `go.mod` and `go.sum` files by adding missing dependencies and removing unused ones. MVS (Minimum Version Selection) is an algorithm used to resolve version conflicts, selecting the highest version that satisfies all constraints specified in the module requirements.

**G10** — A `defer` statement schedules a function call to be executed just before the surrounding function returns. Multiple defers execute in Last-In, First-Out (LIFO) order. A common gotcha in a loop is capturing the loop variable by reference (or closure capture). If you defer a function that uses the loop variable, all deferred functions will execute *after* the loop finishes, and they will all reference the final value of the loop variable, not the value it held during each iteration.

**G11** — A pointer in Go is a variable that stores the memory address of another variable. The zero value of a pointer is `nil`. To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12** — The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It runs exactly once per package initialization. A package can have multiple `init()` functions, and they execute in the order they appear in the source code files.

**G13** — `make` is used to initialize built-in reference types (slices, maps, channels). It allocates and initializes the underlying data structure. `new` allocates memory for a value of a specified type and returns a pointer to the zero-initialized value of that type. `make` works with slices, maps, and channels; `new` works with any type.

**G14** — Error handling in Go is explicit, relying on returning an `error` type as the last return value. The `error` interface is a built-in interface with a single method: `Error() string`. The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`. `errors.Is(err, target)` checks if the error chain wraps a specific sentinel error value. `errors.As(err, &target)` checks if any error in the chain matches a specific type and assigns it to the provided variable. They differ from `==` because they handle error wrapping and type inspection across the error chain.

**G15** — Composite types are structures built from other types.
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to).
*   **Slice:** `[]Type`. Zero value: `nil` (length 0, capacity 0).
*   **Channel:** `chan Type`. Zero value: `nil` (cannot be used for send/receive).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

**G16** — A race condition occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism. The `-race` flag instruments the Go runtime to detect these unsynchronized concurrent memory accesses. Example: Two goroutines incrementing a shared counter without a mutex. Fix: Use `sync.Mutex` to wrap the increment operation, or use atomic operations/channels to coordinate updates.

**G17** — The `select` statement waits on multiple communication operations (channel receives/sends). It differs from `switch` because `select` is specifically designed for concurrency and channel operations. When multiple cases are ready, `select` chooses one pseudo-randomly. A timeout is implemented by using `select` with a `time.After(duration)` channel case.

**G18** — Escape analysis is a compiler optimization that determines whether a variable's data should be allocated on the stack (fast, automatic cleanup) or the heap (slower, managed by the garbage collector). The compiler decides based on how long the variable's lifetime is expected to exceed the scope of the function call. You can inspect this using the `-gcflags="-m"` flag. It matters because heap allocation involves runtime overhead (GC bookkeeping), while stack allocation is extremely fast.

**G19** — Reflection allows a program to examine and manipulate its own structure (types, fields, methods) at runtime. `reflect.Type` describes the structure of a value (its kind, fields, methods), while `reflect.Value` holds the actual runtime value and allows you to invoke methods or access fields. Reflection incurs significant performance costs because the compiler cannot optimize calls involving unknown types. It is justified when dynamic behavior is required (e.g., serialization libraries, ORMs), but code generation is preferred for performance-critical paths.

**G20** — `go:embed` is a directive that allows embedding files or directories directly into a Go binary as assets. It works by instructing the compiler to read the contents of the specified path and make them available as a variable of type `embed.FS` (or similar). For single files, it embeds the content as bytes. For directories/file systems, it embeds the entire structure. Limitations include file size limits and the fact that the embedded data is static at compile time. It interacts with `io/fs.FS` by providing an implementation of that interface over the embedded data.

## Rust Answers

**R1** — Ownership is Rust's system for managing memory safety without a garbage collector. It ensures that every piece of data has a single, clear owner at any given time. The three rules are: 1) Each value in Rust has a variable that’s called its owner. 2) There can only be one owner at a time. 3) When the owner goes out of scope, the value is dropped (memory is freed).

**R2** — `String` is a heap-allocated, growable, mutable UTF-8 string type (owned data). `&str` is a string slice, which is a borrowed, immutable view into string data (either owned or static). Use `String` when you need to own and modify the string data. Use `&str` in function signatures when you only need to read the string data, as it avoids unnecessary heap allocations.

**R3** — Borrowing allows you to refer to data without taking ownership of it. The borrow checker enforces rules to prevent data races at compile time.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many `&T` references at once.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. This guarantees exclusive access for modification.
The core rule is: you can have *either* one mutable reference *or* any number of immutable references, but not both simultaneously.

**R4** — `Result<T, E>` is an enum representing an operation that might succeed (`Ok(T)`) or fail (`Err(E)`). `Option<T>` is an enum representing a value that might be present (`Some(T)`) or absent (`None`). The `?` operator is syntactic sugar for propagating errors or unwrapping `Option`s. If the expression it operates on is `Err(E)`, `?` immediately returns that error from the current function. If it is `Ok(T)`, it unwraps the value `T` and continues execution.
Example:
```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> io::Result<String> {
    let mut file = File::open(path)?; // Propagates io::Error if file cannot be opened
    let mut contents = String::new();
    file.read_to_string(&mut contents)?; // Propagates io::Error if reading fails
    Ok(contents)
}
```

**R5** — These types manage shared ownership and reference counting:
*   **`Box<T>`:** A smart pointer that allocates data on the heap. It provides single ownership. Use it when you need to put a type on the heap to handle recursive types or when you need to hide the allocation details.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the heap. It is single-threaded. Use it when you need shared, immutable ownership within one thread.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>` but uses atomic operations for reference counting, making it safe to share ownership across multiple threads. Use it for thread-safe shared ownership.

**R6** — Traits define shared behavior (like interfaces in Go/Java). They specify a set of methods that a type must implement. Traits compare to Go interfaces in that they define *what* a type can do, not *what* it is. A **trait object (`dyn Trait`)** is a dynamically dispatched pointer to a type that implements the trait; the specific type is not known until runtime. A **generic with a trait bound (`T: Trait`)** is statically dispatched; the compiler knows the concrete type `T` at compile time, allowing for monomorphization and zero-cost abstraction.

**R8** — `Send` is a marker trait indicating that a type can be safely transferred (sent) to another thread. `Sync` is a marker trait indicating that a type can be safely shared between threads (i.e., it is safe to have multiple references to it across threads). You cannot send an `Rc<T>` across threads because its internal reference counter is not atomic, leading to race conditions during counting. `Arc<T>` is safe for concurrent use because its reference counting mechanism uses atomic operations, ensuring that the count is updated safely across threads.

**R9** — Rust's async/await is built around the concept of a `Future`. A `Future` is a trait representing a value that *might* be available at some point in the future. When you call an async function, it returns a `Future` immediately, without blocking the thread. The `await` keyword pauses the execution of the current task until the `Future` resolves, yielding control back to the executor. The **executor** (like Tokio or async-std) is the runtime responsible for polling these futures—it drives them forward, running them on a thread pool until they complete. This differs from Go's goroutines because Rust futures are *cooperative* (they must explicitly yield control via `.await`), whereas Go goroutines are *preemptive* (the scheduler can interrupt them).

**R10** — `unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. Three things you can do: 1) Dereference raw pointers (`*const T`, `*mut T`). 2) Call `unsafe` functions or methods. 3) Access or modify mutable static variables. Unsafe code is justified when interfacing with C libraries (FFI), implementing highly optimized data structures, or when the programmer can mathematically prove that the safety invariants will be maintained.

**R11** — Pattern matching uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches. `if let` is syntactic sugar for a specific, single-pattern match (e.g., `if let Some(x) = option { ... }`). The compiler enforces **exhaustiveness** in `match` statements, meaning you must provide a branch for every possible variant of the enum or pattern, preventing runtime errors due to unhandled cases.

**R12** — `Vec<T>` is a dynamically sized, heap-allocated, growable array. An array `[T; N]` has a fixed size `N` known at compile time and is typically allocated on the stack. When `Vec<T>` is pushed beyond its current capacity, it allocates a new, larger contiguous block of memory (usually doubling the capacity), copies all existing elements to the new location, and then deallocates the old memory block.

**R13** — Rust enums are powerful because they are *algebraic data types* that can hold different types of data for each variant (unlike C enums which are usually just integer constants). `Option<T>` is an enum with two variants: `Some(T)` (contains a value) and `None` (contains no value). Rust avoids null because `None` explicitly models the *absence* of a value as a type, forcing the programmer to handle the absence case explicitly, thus eliminating null pointer dereference errors.

**R14** — An `impl` block is used to define methods and associated functions for a specific type.
*   **`&self`:** Borrows the instance immutably. Used for read-only operations.
*   **`&mut self`:** Borrows the instance mutably. Used for operations that change the state of the instance.
*   **`self`:** Takes ownership of the instance. Used when the method consumes the instance (e.g., `into_inner()`).
Associated functions (like `String::new()`) are functions defined within the `impl` block but do not take `self` as the first argument; they are called directly on the type name.

**R15** — A derive macro is a procedural macro that automatically implements standard traits for a struct or enum based on its definition. Examples: `#[derive(Debug)]` allows printing the struct using `{:?}`; `#[derive(Clone)]` implements deep copying; `#[derive(PartialEq)]` implements equality checks. You cannot derive a trait if the type definition itself violates the trait's requirements (e.g., trying to derive `Clone` on a type that contains a non-`Clone` field).

**R16** — `Cow<'a, T>` (Clone On Write) is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`). It is useful when you frequently receive data that might be immutable, but sometimes you need to modify it. If you only read the data, `Cow` acts like a cheap reference. If you attempt to mutate it, `Cow` automatically clones the data into an owned version (`T`) behind the scenes, ensuring the mutation is safe without forcing an allocation on every read.

**R17** — Rust's module system organizes code hierarchically. `mod` declares a module (which can correspond to a file or a directory). `use` brings items from a module into the current scope for easier access. `pub` makes items accessible outside the current module. The file system maps to modules: a file named `foo.rs` defines the `foo` module. The major change between editions was the standardization and refinement of how modules interact with the file system and how visibility (`pub`) is enforced across crate boundaries.

**R18** — `Pin<T>` is a wrapper that guarantees that a value `T` will not be moved in memory after it has been pinned. This is crucial for types that contain self-references (where a part of the data points back to another part of the same data structure) or for async state machines. If a future's state machine moves in memory, any internal pointers referencing its old location become invalid. `Unpin` is a marker trait indicating that a type *can* be safely moved.

**R19** — Rust's macro system allows metaprogramming. **Declarative macros (`macro_rules!`)** are pattern-matching macros that operate on tokens (like a sophisticated text replacement engine). **Procedural macros** (like `#[derive(...)]` or `#[attribute(...)]`) are functions that take Rust code as input (Abstract Syntax Tree - AST) and output new Rust code. **Hygiene rules** prevent macros from accidentally capturing or interfering with identifiers defined inside the code they are expanding, ensuring that generated code is locally scoped and safe.

**R20** — Zero-cost abstractions mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level code manually.
*   **Generics (Monomorphization):** When you use a generic function like `fn map<T>(items: Vec<T>, f: fn(T) -> U) -> Vec<U>`, the compiler generates a specialized version of `map` for every concrete type `T` used (e.g., one version for `i32`, one for `String`). This avoids runtime overhead associated with dynamic dispatch.
*   **Iterators/Trait Static Dispatch:** Iterators provide ergonomic chaining, but when combined with generics, the compiler often uses static dispatch (similar to monomorphization) to resolve method calls at compile time, avoiding the runtime lookup cost of virtual tables.
