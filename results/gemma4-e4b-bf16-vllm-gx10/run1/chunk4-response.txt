## Go Answers

**G1 — Easy:**
A **slice** is a dynamically-sized, flexible view into an underlying array. It is a descriptor containing a pointer to the underlying array, a length, and a capacity. An **array** is a fixed-size collection of elements whose size is part of its type signature (e.g., `[5]int`).
When you append to a slice that has reached its capacity, Go allocates a new, larger underlying array (usually doubling the capacity), copies the existing elements from the old array to the new one, and then appends the new element. The slice header is then updated to point to this new array.

**G2 — Easy:**
`var x int` declares a variable `x` of type `int` and initializes it to its zero value (which is `0` for integers). `x := 0` is a short variable declaration, which declares and initializes `x` to `0` in the current scope.
You cannot use `:=` when you are *reassigning* a variable that has already been declared in the current scope. For example, if `x` is already declared, you must use `x = 5` instead of `x := 5`.

**G3 — Medium:**
A **goroutine** is a lightweight, independently executing function managed by the Go runtime. It is much cheaper to create and manage than an OS thread.
The Go scheduler (GMP model) maps goroutines (G) onto OS threads (M) using a pool of logical processors (P). The scheduler multiplexes many goroutines onto a smaller number of OS threads, efficiently managing context switching and preventing the overhead associated with traditional OS thread management.

**G4 — Medium:**
Channels are typed conduits through which you can send and receive values between goroutines, providing a mechanism for safe communication (CSP model).
*   **Unbuffered channel:** Requires both the sender and receiver to be ready at the moment of communication (synchronous rendezvous).
*   **Buffered channel:** Has a fixed capacity. Sending to or receiving from it blocks only when the buffer is full or empty, respectively.
When sending to a full buffered channel, the sending goroutine blocks until another goroutine receives a value from that channel, freeing up a slot.

**G5 — Medium:**
The `context` package is used to carry deadlines, cancellation signals, and other request-scoped values across API boundaries and between goroutines. It allows you to propagate request context throughout a service call chain, enabling graceful shutdown or timeout handling.
```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func main() {
	// Create a context that automatically cancels after 2 seconds
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel() // Always call cancel to release resources

	req, err := http.NewRequestWithContext(ctx, "GET", "http://slow-api.com/data", nil)
	if err != nil {
		fmt.Println("Error creating request:", err)
		return
	}

	client := &http.Client{}
	resp, err := client.Do(req)

	if err != nil {
		// Check if the error was due to context cancellation/timeout
		if ctx.Err() == context.DeadlineExceeded {
			fmt.Println("Request timed out!")
		} else {
			fmt.Println("Error during request:", err)
		}
		return
	}
	defer resp.Body.Close()
	fmt.Println("Request successful.")
}
```

**G6 — Medium:**
Go's interface satisfaction model is **implicit**. A type satisfies an interface simply by implementing all the methods declared in that interface; there is no explicit `implements` keyword required.
This differs from Java/C# where interfaces must be explicitly implemented.
The empty interface `interface{}` (or `any` in Go 1.18+) can hold a value of *any* type. It is powerful because it allows for maximum flexibility (e.g., generic functions that accept anything). It is dangerous because using it requires **type assertion** or **type switching** to determine the underlying type before you can use its specific methods or fields, which can lead to runtime panics if the assertion fails.

**G8 — Hard:**
*   **`sync.Mutex`:** A standard mutual exclusion lock. Only one goroutine can hold the lock at any given time, providing exclusive access for both reading and writing.
*   **`sync.RWMutex`:** A Read-Write Mutex. It allows multiple readers to hold the lock simultaneously (`RLock`), but requires exclusive access for writers (`Lock`).
**`sync.Map` vs. Map + Mutex:**
*   **Map + Mutex:** Standard, predictable performance. Good for general-purpose locking where reads and writes are mixed.
*   **`sync.Map`:** Optimized for scenarios where keys are written once but read many times (read-heavy workloads). It avoids locking the entire map for every read operation, potentially offering better concurrency for reads.
**Trade-offs:** `sync.Map` has higher overhead for writes compared to a standard map protected by a mutex, and its API is less intuitive than a standard map.

**G9 — Hard:**
**Go Modules** are Go's dependency management system. They define the project's dependencies and the specific versions required.
*   **`go.mod`:** Declares the module path, the required Go version, and lists all direct dependencies along with their required versions.
*   **`go.sum`:** Contains cryptographic checksums (hashes) of the exact content of every dependency file listed in `go.mod`. This ensures that the downloaded dependencies have not been tampered with.
**`go mod tidy`** cleans up the `go.mod` and `go.sum` files by adding any missing required dependencies and removing any dependencies that are no longer used in the source code.
**Minimum Version Selection (MVS):** MVS is an algorithm used by Go to select the highest possible version of a dependency that satisfies all version constraints specified across all modules in the dependency graph, while ensuring that the selected version is compatible with all requirements.

**G10 — Medium:**
A `defer` statement schedules a function call to be executed just before the surrounding function returns.
Multiple `defer` statements execute in **Last-In, First-Out (LIFO)** order.
**Gotcha in a loop:** If you defer a function call that captures a loop variable (e.g., `i`), the deferred function will execute *after* the loop has finished, meaning it will use the *final* value of the loop variable, not the value it had during each iteration.

**G11 — Easy:**
A **pointer** in Go is a variable that stores the memory address of another variable. It allows you to refer to and modify the original data indirectly.
The zero value of a pointer is `nil`, which indicates that it does not point to any valid memory address.
To create a pointer to a struct literal, you use the address-of operator (`&`): `p := &MyStruct{Field: value}`.

**G12 — Easy:**
The `init()` function is a special function that runs automatically before the `main` function (or before any other code in the package) is executed. It is used for package-level initialization logic.
A package **can** have multiple `init()` functions. They execute sequentially in the order they appear in the source files (though the exact order across different files can sometimes be implementation-dependent, the standard is sequential execution).

**G13 — Easy:**
*   **`make`:** Used to initialize built-in reference types that require allocation, specifically **slices, maps, and channels**. It takes arguments defining the initial length/capacity or size. (e.g., `make([]int, 5)`).
*   **`new`:** Used to allocate memory for a value of a specific type and return a pointer to it. It initializes the memory to the zero value of the type. It works with **any type** (e.g., `new(MyStruct)`).

**G14 — Easy:**
Error handling in Go is explicit and relies on returning an `error` type as the last return value from functions that might fail. The `error` interface is an interface with a single method: `Error() string`.
The idiomatic pattern is to check the returned error immediately: `if err != nil { return err }`.
*   `errors.Is(err, target)`: Checks if the error chain contains a specific sentinel error value (e.g., checking if a network error is specifically `io.EOF`).
*   `errors.As(err, &target)`: Checks if the error chain contains a value that matches a specific type, allowing you to extract that typed error for inspection.
*   `==`: Only checks for exact pointer equality, which is rarely useful for error checking unless you are comparing against a specific, known error variable.

**G15 — Easy:**
*   **Map:** `map[KeyType]ValueType`. Zero value: `nil` (cannot be written to until initialized with `make`).
*   **Slice:** `[]Type`. Zero value: `nil` (length 0, capacity 0).
*   **Channel:** `chan Type`. Zero value: `nil` (cannot be used until initialized with `make`).
*   **Struct:** `struct { ... }`. Zero value: A struct where all fields are set to their respective zero values.

**G16 — Medium:**
A **race condition** occurs when two or more goroutines access the same memory location concurrently, and at least one of the accesses is a write, without any synchronization mechanism to order the accesses. The final outcome depends on the unpredictable timing of the scheduler.
The `-race` flag compiles and runs the program with a data race detector enabled. If a data race is detected, the program will panic and report the location of the race.
**Example Fix (Mutex):** Wrap the shared access in `mutex.Lock()` and `defer mutex.Unlock()`.
**Example Fix (Channel):** Instead of sharing memory, pass the data between goroutines via a channel, ensuring sequential, synchronized transfer.

**G17 — Medium:**
The `select` statement allows a goroutine to wait on multiple communication operations (channel receives or sends) simultaneously. It is Go's mechanism for concurrency control, similar to `switch` but for channels.
When multiple cases are ready, `select` chooses one of them **randomly**.
To implement a timeout, you create a `time.After()` channel and include it as a case in the `select` block:
```go
select {
case msg := <-ch:
    // Received message
case <-time.After(5 * time.Second):
    fmt.Println("Timeout occurred")
}
```

**G18 — Hard:**
**Escape analysis** is a compiler optimization that determines whether a variable's data needs to reside on the stack or the heap during runtime.
The compiler decides based on the variable's lifetime and how long it needs to exist. If a variable's lifetime is strictly confined to the current function call, it can usually be allocated on the stack (fast). If the variable needs to outlive the function call (e.g., it's returned from the function, or stored in a global/heap-allocated structure), it must be allocated on the heap.
You can inspect this using the `-gcflags="-m"` compiler flag. It matters for performance because stack allocation/deallocation is significantly faster than heap allocation/garbage collection.

**G19 — Hard:**
The `reflect` package allows a program to inspect and manipulate its own structure (types, values, fields) at runtime.
*   **`reflect.Type`:** Represents the *type* information of a value (e.g., knowing that a variable is an `int` or a `struct`).
*   **`reflect.Value`:** Represents the *actual value* at runtime, allowing you to read or modify its contents.
**Performance Costs:** Reflection is extremely slow compared to statically typed code because the compiler cannot optimize calls involving reflection; it must perform dynamic lookups at runtime.
**Justification:** Reflection is justified when you need to write generic libraries that must operate on arbitrary types (e.g., serialization/deserialization frameworks) where static type knowledge is impossible or too restrictive. Code generation is preferred when performance is critical.

**G20 — Hard:**
The `go:embed` directive allows embedding files or directories directly into a Go binary as assets. It is a compile-time mechanism, not a runtime file system operation.
*   **Single files:** `//go:embed data.txt` embeds the content of `data.txt` as a string or byte slice.
*   **Directories:** `//go:embed assets` embeds the entire directory structure.
*   **File systems:** It can embed an entire virtual file system structure.
**Limitations:** It embeds the content directly into the binary; it is not a dynamic file loading mechanism.
**Interaction with `io/fs.FS`:** The embedded content can be exposed as an `fs.FS` interface, allowing standard library functions designed for file systems (like `http.FileServer`) to serve the embedded assets without needing to touch the physical disk.

## Rust Answers

**R1 — Easy:**
**Ownership** is Rust's core memory management concept. It dictates that every value in Rust has a single variable that is its *owner*. When the owner goes out of scope, the value is automatically dropped (memory is freed).
The three rules are:
1.  Each value in Rust has a variable that’s called its owner.
2.  There can only be one owner at a time.
3.  When the owner goes out of scope, the value is dropped.

**R2 — Easy:**
*   **`String`:** An owned, heap-allocated, growable, mutable string type. It owns its data.
*   **`&str`:** A string slice. It is a borrowed reference to a sequence of UTF-8 bytes, usually pointing to string literals or parts of a `String`.
**Usage:**
*   Use `String` when you need to create, modify, or own the string data (e.g., user input, building a response).
*   Use `&str` in function signatures when you only need to *read* the string data and do not need to take ownership or modify it. This allows functions to accept string literals (`&'static str`) or slices of `String`s.

**R3 — Medium:**
**Borrowing** allows you to refer to data without taking ownership of it. The **borrow checker** is the static analysis tool that enforces Rust's borrowing rules at compile time to prevent data races and use-after-free errors.
*   **Shared Reference (`&T`):** Allows multiple immutable references to the same data simultaneously. You can have many readers.
*   **Mutable Reference (`&mut T`):** Allows exactly one mutable reference to the data at any given time. This enforces the "one writer OR many readers" rule.

**R4 — Medium:**
*   **`Option<T>`:** An enum representing the presence or absence of a value. It is either `Some(T)` (it has a value) or `None` (it has no value). It replaces the concept of `null`.
*   **`Result<T, E>`:** An enum representing the outcome of an operation that might fail. It is either `Ok(T)` (success, containing the value `T`) or `Err(E)` (failure, containing the error `E`).
The **`?` operator** is syntactic sugar for propagating errors. If the expression on the left of `?` is `Ok(T)`, it unwraps the value `T`. If it is `Err(E)`, it immediately returns the error `E` from the current function (provided the function signature returns a `Result`).
**File Reading Example:**
```rust
use std::fs;
use std::io;

fn read_file(path: &str) -> Result<String, io::Error> {
    // The ? operator handles the Result returned by fs::read_to_string
    let contents = fs::read_to_string(path)?; 
    Ok(contents)
}
```

**R5 — Medium:**
These types manage shared ownership and reference counting:
*   **`Box<T>`:** A smart pointer that allocates data on the **heap**. It provides single ownership. Used when the size of a type is unknown at compile time (recursive types) or when you need to move a large object onto the heap.
*   **`Rc<T>` (Reference Counted):** Allows multiple owners of the same data on the **heap**. It uses reference counting. It is **single-threaded**.
*   **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc<T>`, but its reference counting operations are atomic, making it **thread-safe**. Use this when sharing ownership across threads.

**R6 — Medium:**
**Traits** define shared behavior (a set of methods) that types can implement. They are Rust's mechanism for polymorphism.
*   **Comparison to Go Interfaces:** Traits are more powerful than Go interfaces because they can define *default implementations* for methods, and they can be used to constrain generics. Go interfaces are purely structural (duck typing).
*   **Trait Object (`dyn Trait`):** A dynamically dispatched trait object. It holds a pointer to data that implements the trait, allowing you to treat different concrete types uniformly at runtime (similar to an interface variable in Go).
*   **Generic with Trait Bound (`T: Trait`):** A statically dispatched generic. The compiler generates specialized code for every concrete type `T` used, resulting in zero runtime overhead (monomorphization).

**R8 — Hard:**
*   **`Send`:** A marker trait indicating that a type can be safely *sent* (moved) to another thread.
*   **`Sync`:** A marker trait indicating that a type can be safely *shared* between threads (i.e., it is safe to have multiple immutable references (`&T`) across threads).
You cannot send an `Rc<T>` across threads because its internal reference counting mechanism is not atomic; multiple threads could corrupt the count simultaneously.
**`Arc<T>` is safe for concurrent use** because it wraps the data in an atomic reference counter, ensuring that the count is updated safely across threads, and it typically requires the inner type `T` to also implement `Send` and `Sync`.

**R9 — Hard:**
Rust's `async/await` is built on the concept of **Futures**. A `Future` is a trait representing a value that *might* be available at some point in the future. It is essentially a state machine that knows how to poll itself until it completes.
The **executor** (like Tokio or async-std) is the runtime environment. It takes a `Future` and repeatedly "polls" it. If the future is not ready, the executor suspends it and moves on to poll other futures, only resuming the suspended future when the necessary I/O or event occurs.
**Difference from Go:** Go uses green threads (goroutines) managed by a runtime scheduler that preemptively switches between tasks. Rust's `async/await` is **cooperative multitasking**; a task only yields control back to the executor when it explicitly awaits an operation (like I/O), giving the executor control.

**R10 — Medium:**
`unsafe` blocks allow the programmer to bypass Rust's compile-time safety guarantees. This is necessary when interacting with low-level hardware, FFI (Foreign Function Interface), or implementing highly optimized data structures.
Three things you can do in `unsafe`:
1.  Dereference a raw pointer (`*const T` or `*mut T`).
2.  Call an `unsafe` function or intrinsic.
3.  Access or modify a mutable static variable.
**Justification:** `unsafe` is justified only when you have a deep, provable understanding of memory safety and concurrency, and the performance or capability gain outweighs the risk of introducing undefined behavior.

**R11 — Easy:**
**Pattern matching** uses the `match` keyword to compare a value against a series of patterns and execute code based on which pattern matches.
`if let` is syntactic sugar used for matching a single, specific pattern and immediately executing code if it matches, otherwise continuing.
The compiler enforces **exhaustiveness** in `match` statements. If the pattern matching logic does not cover every possible variant of the enum or value type, the compiler will issue an error, forcing the programmer to handle all cases.

**R12 — Easy:**
*   **`Vec<T>`:** A dynamically sized, heap-allocated, growable array. It manages its own memory.
*   **Array `[T; N]`:** A fixed-size collection whose size `N` is part of its type. It is typically allocated on the stack.
When `Vec<T>` is pushed beyond its current capacity, it performs a reallocation: it allocates a new, larger contiguous block of memory (often doubling the capacity), copies all existing elements to the new block, and then deallocates the old block.

**R13 — Easy:**
**Enums** in Rust are powerful algebraic data types. Unlike C/Java enums (which are often just integer constants), Rust enums can hold associated data. They are essentially tagged unions.
**`Option<T>`** is an enum defined as `enum Option<T> { None, Some(T) }`. It is Rust's idiomatic way to handle the absence of a value, effectively eliminating the need for `null` pointers, which are a major source of bugs in other languages.

**R14 — Easy:**
The **`impl` block** is used to define methods and associated functions for a specific type.
*   **`&self`:** Takes an immutable reference to the instance. Used for methods that only read data (e.g., `len()`).
*   **`&mut self`:** Takes a mutable reference to the instance. Used for methods that need to modify the instance's state (e.g., `push()`).
*   **`self`:** Takes ownership of the instance. Used when the method consumes the instance (e.g., `into_inner()`).
**Associated Functions:** These are functions defined within an `impl` block but do not take `self` as the first argument (e.g., `String::new()`). They are often used as constructors.

**R15 — Easy:**
A **derive macro** is a procedural macro that automatically implements standard traits for a struct or enum based on its definition.
Commonly derived traits:
*   `Debug`: Allows printing the value using `{:?}`.
*   `Clone`: Allows creating deep copies of the value.
*   `PartialEq`/`Eq`: Allows comparison using `==` and `!=`.
*   `Serialize`/`Deserialize`: Used by serialization libraries (like Serde).
You **cannot** derive a trait if the type does not meet the requirements of that trait. For example, you cannot derive `Eq` if you have not implemented `PartialEq` correctly, or if the type contains non-comparable elements.

**R16 — Medium:**
**`Cow<'a, T>` (Clone On Write)** is a smart pointer that can hold either an owned value (`T`) or a borrowed reference (`&'a T`).
It is useful when you frequently receive data that might be immutable (a borrow) but sometimes need to modify it.
**Example:** If you receive a string slice (`&str`) but later need to append to it, using `Cow` allows you to initially hold the cheap borrow. Only when you attempt to write to it does `Cow` perform the allocation and clone the data into an owned `String` internally. This avoids unnecessary allocations if the data is only read.

**R17 — Medium:**
Rust's module system organizes code into hierarchical units.
*   **`mod`:** Declares a module, which can be a file or a block. It defines the scope.
*   **`use`:** Brings items (functions, structs, traits) from another module into the current scope, allowing you to refer to them without the full path.
*   **`pub`:** Makes an item publicly visible outside of its current module.
The file system maps to modules: a file named `foo.rs` typically corresponds to the `foo` module.
**2015 vs 2018:** The 2018 edition introduced significant improvements, notably better support for path resolution, clearer rules for module visibility, and better integration with the standard library's module structure.

**R18 — Hard:**
**`Pin<T>`** is a wrapper that guarantees that a value `T` will not be moved in memory after it has been pinned.
It is needed because certain types, particularly those involved in asynchronous operations (like `Future`s), must maintain a stable memory location throughout their execution. If a `Future` were moved in memory while it was suspended, its internal state (which often contains pointers to itself or other data) would become invalid, leading to crashes.
**`Unpin`** is a marker trait. If a type implements `Unpin`, it means it is safe to move it in memory. If it does *not* implement `Unpin`, it must be pinned using `Pin<T>`.

**R19 — Hard:**
Rust's macro system allows code to write code.
*   **Declarative Macros (`macro_rules!`):** These are pattern-matching macros. They operate by matching input tokens against defined patterns and then expanding them into token streams. They are simpler and operate on syntax.
*   **Procedural Macros:** These are more powerful. They are functions that take Rust code (as tokens) as input and output new Rust code. They are categorized as:
    *   **Derive Macros:** Automatically implement traits (e.g., `#[derive(Debug)]`).
    *   **Attribute Macros:** Modify the code surrounding an item (e.g., `#[my_logger]`).
    *   **Function-like Macros:** Act like regular functions but operate on tokens.
**Hygiene Rules:** These rules prevent macro expansion from accidentally capturing or interfering with identifiers (names) defined inside the code being macro-processed. They ensure that the generated code is locally scoped and doesn't pollute the surrounding environment.

**R20 — Hard:**
**Zero-cost abstractions** mean that high-level language features (like generics or iterators) compile down to machine code that is as fast as if the programmer had written the equivalent low-level, hand-optimized code (like C).
*   **Generics (Monomorphization):** When you use a generic function like `fn map<T>(items: Vec<T>, f: fn(T) -> U) -> Vec<U>`, the compiler generates a specific version of `map` for *every* concrete type `T` used (e.g., one version for `Vec<i32>`, another for `Vec<String>`). This avoids runtime type checking overhead.
*   **Iterators:** Rust iterators are implemented as traits that define a sequence of operations. The compiler optimizes the chain of iterator methods (like `.map().filter().collect()`) into a single, highly efficient loop structure, often avoiding intermediate allocations.
*   **Trait Static Dispatch:** When a trait is used with generics (`T: Trait`), the compiler resolves the exact method call at compile time (static dispatch), which is as fast as a direct function call, unlike dynamic dispatch (`dyn Trait`), which requires a runtime lookup.
