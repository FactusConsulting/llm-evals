## Kubernetes Answers

**K1 — Easy: What is the difference between a Deployment and a StatefulSet?**
A **Deployment** manages stateless applications, ensuring a specified number of identical, interchangeable replicas are running. Pods managed by a Deployment have no stable identity. A **StatefulSet** manages stateful applications, providing stable, unique network identifiers and persistent storage to each pod (e.g., database primary/replica).

**K2 — Easy: How does a Kubernetes Service of type ClusterIP route traffic to pods?**
A ClusterIP Service exposes a stable internal IP address within the cluster. It uses `kube-proxy` (which typically runs iptables or IPVS rules on each node) to intercept traffic destined for the Service's ClusterIP and redirect it to one of the healthy backing Pods selected via the Service's selector.

**K3 — Medium: Explain the difference between a PersistentVolume, a PersistentVolumeClaim, and a StorageClass. How do they relate?**
*   **PersistentVolume (PV):** A piece of storage in the cluster provisioned by an administrator or dynamically. It is a cluster resource representing the actual storage capacity (e.g., an AWS EBS volume).
*   **PersistentVolumeClaim (PVC):** A request for storage by a user/application. It is a namespace resource that requests a specific amount and access mode (e.g., ReadWriteOnce) of storage.
*   **StorageClass:** A class that defines "classes" of storage (e.g., fast SSD, slow HDD). It dictates the dynamic provisioning mechanism.
*   **Relation:** A PVC requests storage. If a StorageClass is defined, the cluster uses it to dynamically provision a PV that matches the PVC's requirements. The PVC then binds to the created PV, which the Pod consumes via a Volume mount.

**K4 — Medium: A pod is stuck in CrashLoopBackOff. Describe your troubleshooting steps (at least 4 distinct checks).**
1.  **Check Pod Events/Status:** Run `kubectl describe pod <name>` to see the reason for the crash (e.g., ImagePullBackOff, OOMKilled, CrashLoopBackOff reason).
2.  **Check Logs:** Run `kubectl logs <name>` (and potentially `kubectl logs <name> --previous`) to see the application-level error that caused the container to exit.
3.  **Check Configuration/Image:** Verify the container image tag is correct, the image exists in the registry, and the resource requests/limits are reasonable.
4.  **Check Readiness/Liveness Probes:** If probes are configured, check if the application is failing the health checks, causing Kubernetes to restart the container.

**K5 — Medium: What is the role of CoreDNS in a Kubernetes cluster? What happens to DNS resolution if the CoreDNS pods are down?**
CoreDNS acts as the cluster's internal DNS service. It resolves service names (e.g., `my-service.my-namespace.svc.cluster.local`) to the correct ClusterIPs and handles internal cluster DNS lookups. If CoreDNS pods are down, internal DNS resolution fails. Pods will be unable to resolve other services within the cluster by name, leading to application connection failures, although external DNS resolution might still function if the node's underlying `/etc/resolv.conf` points to external resolvers.

**K6 — Hard: Explain how the Kubernetes scheduler decides which node to place a pod on. Cover: filtering, scoring, and at least 3 specific factors it considers.**
The scheduler uses a two-phase process:
1.  **Filtering (Predicates):** The scheduler first filters the set of all available nodes to find those that *can* run the pod based on hard constraints. Examples include:
    *   **Resource Availability:** Does the node have enough CPU/Memory?
    *   **Volume Zone/Topology:** Does the node support the required volume topology?
    *   **Taints/Tolerations:** Does the node have taints that the pod does not tolerate?
2.  **Scoring (Priorities):** From the remaining eligible nodes, the scheduler scores them based on soft preferences. The node with the highest score is chosen. Examples of scoring factors include:
    *   **Least Requested Priority:** Preferring nodes with the least amount of current resource utilization.
    *   **Node Affinity/Anti-Affinity:** Preferring or avoiding nodes based on labels.
    *   **Spread Constraints:** Ensuring pods are spread across different failure domains (e.g., different racks).

**K7 — Hard: You have a pod with requests.memory: 256Mi and limits.memory: 512Mi. The node has 4GB RAM with 3.5GB already requested. Will the pod be scheduled? What happens if it actually uses 600Mi at runtime?**
**Scheduling:** The pod *will likely not* be scheduled immediately because the total requested memory (3.5GB + 256Mi = 3.756GB) is less than the node capacity (4GB), but the scheduler must account for overhead and fragmentation. More critically, if the scheduler strictly enforces requests, it might pass the initial check. However, the node is already heavily utilized.
**Runtime Behavior:** If the pod starts and attempts to use 600Mi, it will exceed its defined `limits.memory` (512Mi). Kubernetes will trigger the Out-Of-Memory (OOM) killer, and the container will be terminated by the Kubelet, resulting in the pod entering a `CrashLoopBackOff` state.

**K8 — Hard: Explain the full lifecycle of a request hitting a Kubernetes Ingress backed by an NGINX ingress controller, all the way to the application pod. Include at least: external LB, ingress controller, Service, Endpoints, kube-proxy/iptables.**
1.  **External LB:** An external Load Balancer (e.g., AWS ELB, GCP LB) receives the external HTTP request and forwards it to the NodePort exposed by the Ingress Controller Pods.
2.  **Ingress Controller:** The NGINX controller pod receives the traffic. It inspects the host/path headers against the configured Ingress rules.
3.  **Service:** Based on the Ingress rule, the controller forwards the request to the stable ClusterIP of the target Kubernetes Service.
4.  **Endpoints:** The Service object maintains an Endpoints object, which is a list of the actual IP addresses of the healthy application Pods matching the Service selector.
5.  **kube-proxy/iptables:** `kube-proxy` on the node intercepts traffic destined for the Service ClusterIP. It uses its configured iptables rules to perform DNAT (Destination Network Address Translation), rewriting the destination IP/port to the IP and port of one of the healthy Pods listed in the Endpoints object.
6.  **Application Pod:** The request finally reaches the application container running inside the target Pod.

**K9 — Medium: What is a NetworkPolicy? If no NetworkPolicy exists in a namespace, what is the default behavior? What happens when you apply one that selects certain pods?**
A **NetworkPolicy** is a Kubernetes resource that defines rules about how groups of pods are allowed to communicate with each other and with external network endpoints.
**Default Behavior:** If no NetworkPolicy exists in a namespace, the default behavior is "allow all" ingress and egress traffic.
**Applying a Policy:** When you apply a NetworkPolicy that selects certain pods, the default behavior *changes* for those selected pods. By default, Kubernetes NetworkPolicies are **deny-by-default** for ingress traffic to selected pods. Therefore, if you apply a policy, only traffic explicitly allowed by that policy will reach the selected pods; all other traffic is dropped.

**K10 — Medium: Explain the difference between RollingUpdate and Recreate deployment strategies. When would you choose Recreate?**
*   **RollingUpdate:** Gradually replaces old Pods with new Pods one by one (or in batches). It maintains service availability throughout the update by ensuring a minimum number of old and new Pods are running concurrently.
*   **Recreate:** Terminates all existing Pods of the application, waits for them to terminate, and then creates all new Pods. This results in downtime.
*   **When to choose Recreate:** You choose Recreate when the application is not designed to handle partial traffic during an update, or when the change is so fundamental (e.g., changing the underlying OS image) that a clean slate is required, and brief downtime is acceptable.

**K11 — Easy: What is a Kubernetes namespace, and what are the default namespaces created in a new cluster?**
A **Namespace** is a mechanism to partition cluster resources across multiple virtual clusters within a single physical cluster. It provides scope isolation for names, resources, and policies.
The default namespaces typically created are: `default`, `kube-system` (for cluster components), `kube-public`, and `kube-node-lease`.

**K12 — Easy: What is `kubectl describe pod <name>` used for? Name at least 3 pieces of information it shows that `kubectl get pod` does not.**
`kubectl describe pod <name>` provides a detailed status report on the pod, including events, configuration details, and resource status.
Three pieces of information it shows that `kubectl get pod` does not:
1.  **Events:** A chronological log of actions taken on the pod (e.g., scheduling events, image pull failures).
2.  **Container Status Details:** Specific details about container restarts, exit codes, and resource usage history.
3.  **Node Assignment/Conditions:** Detailed information about which node it is scheduled on and the current state conditions (e.g., `Ready`, `Progressing`).

**K13 — Easy: What is a ConfigMap, and how can a pod consume it? Name at least two different methods.**
A **ConfigMap** is an API object used to store non-confidential configuration data in key-value pairs, allowing configuration to be injected into Pods without rebuilding the image.
Two methods to consume it:
1.  **As Environment Variables:** Injecting specific keys from the ConfigMap directly as environment variables within the container spec.
2.  **As Mounted Files:** Mounting the ConfigMap as a volume inside the container, where each key becomes a file in the specified directory.

**K14 — Easy: What is the difference between a Service of type ClusterIP, NodePort, and LoadBalancer?**
*   **ClusterIP:** Exposes the Service on an internal IP address only, accessible from within the cluster.
*   **NodePort:** Exposes the Service on a specific port on *every* Node's IP address. This allows external access via `<NodeIP>:<NodePort>`.
*   **LoadBalancer:** Provisions an external cloud load balancer (if running on a cloud provider) that routes external traffic to the Service's nodes. This provides a stable, external IP address.

**K15 — Easy: What is a DaemonSet, and when would you use one instead of a Deployment?**
A **DaemonSet** ensures that a copy of a specified Pod runs on *every* (or a selected subset of) eligible nodes in the cluster.
You use a DaemonSet instead of a Deployment when the workload needs to run on every node for infrastructure-level tasks, such as logging agents (Fluentd), monitoring agents (Prometheus Node Exporter), or network plugins (CNI).

**K16 — Medium: What are taints and tolerations? How do they differ from node affinity, and give a practical use case for each?**
*   **Taints:** A property applied to a Node that repels Pods. They act as a "keep out" sign.
*   **Tolerations:** A property applied to a Pod that allows it to be scheduled onto a Node that has a matching taint.
*   **Difference from Affinity:** Taints/Tolerations are about *repelling* or *allowing* based on node state. Node Affinity is about *preferring* or *requiring* placement based on node *labels*.
*   **Use Case (Taint/Toleration):** Isolating a GPU node by tainting it (`dedicated=gpu:NoSchedule`), ensuring only GPU-requiring pods (with the matching toleration) can run there.
*   **Use Case (Affinity):** Ensuring a database pod is always scheduled on a node labeled `disktype=ssd` (required affinity).

**K17 — Medium: Explain what a Kubernetes Operator is. How does it differ from a standard controller, and what problems does the Operator pattern solve?**
An **Operator** is a method of packaging, deploying, and managing a complex application (like a database cluster) using custom controllers.
**Difference from Controller:** A standard controller watches the state of a resource (e.g., Deployment) and works to match the *desired state* defined in the manifest. An Operator extends this by embedding *domain-specific knowledge* (SME knowledge) into the controller logic.
**Problem Solved:** It automates complex, human-driven operational tasks (like backups, failover, scaling, patching, and recovery) that standard controllers cannot handle, effectively turning an application into a self-managing system.

**K18 — Hard: Explain the etcd consistency model used by Kubernetes. What happens to the cluster if the etcd quorum is lost? How do you recover from a situation where 2 out of 3 etcd nodes are permanently lost?**
Kubernetes uses **Raft** consensus algorithm, which enforces **Strong Consistency**. This means that once a write is acknowledged by a majority (quorum) of etcd members, all subsequent reads will see that write.
**Quorum Loss:** If the quorum (majority) is lost (e.g., 2 out of 3 nodes fail), etcd cannot guarantee consistency, and it stops accepting writes to prevent data divergence. The Kubernetes control plane will become unstable, and the cluster will effectively stop accepting configuration changes.
**Recovery (2/3 lost):** If 2 out of 3 nodes are permanently lost, the cluster cannot recover its quorum. The remaining single node cannot form a majority. Recovery requires manually introducing a new, healthy node and using etcd's snapshot/restore mechanism to bring the cluster back to a functional state with a new quorum.

**K19 — Hard: Describe how Kubernetes RBAC works. Explain the relationship between Role, ClusterRole, RoleBinding, and ClusterRoleBinding. A developer needs read-only access to pods and logs in a single namespace — write the RBAC manifests.**
**RBAC Flow:** RBAC defines *who* (Subject) can do *what* (Verb/Resource) on *which* resources.
*   **Role:** Defines a set of permissions (e.g., `get`, `list` pods) scoped to a specific **Namespace**.
*   **ClusterRole:** Defines a set of permissions scoped across the **entire cluster**.
*   **RoleBinding:** Binds a **Role** to a **Subject** (User/Group) within a specific **Namespace**.
*   **ClusterRoleBinding:** Binds a **ClusterRole** to a **Subject** across the **entire cluster**.
**Manifests (Read-only pods/logs in 'dev' namespace):**
```yaml
# 1. Define the Role (Permissions within the namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# 2. Bind the Role to a User/Group (Subject)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-reader-binding
  namespace: dev
subjects:
- kind: User
  name: developer-user # Replace with actual user/group name
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**K20 — Hard: You notice pod DNS resolution is slow (>5s) for external domains. Explain how ndots in /etc/resolv.conf inside a pod causes excessive DNS queries, and how you would fix it using dnsConfig in the pod spec.**
The `ndots` value in `/etc/resolv.conf` specifies how many dots a hostname must contain before the system attempts a search domain lookup. If `ndots` is set too low (e.g., 1), and the pod tries to resolve an external domain like `api.external.com`, the resolver might first try to resolve it as `api.external.com.svc.cluster.local` (using the cluster's search domain) before trying the external DNS server, leading to unnecessary internal lookups and timeouts.
**Fix:** You can use `dnsConfig` in the Pod spec to override the DNS settings. By setting `dnsConfig.options` or explicitly defining `dnsConfig.searches` and `dnsConfig.nameservers`, you can ensure the pod queries the correct external nameservers directly, bypassing the cluster's search domain logic for external lookups.

## Development Answers

**D1 — Easy: What is the difference between git rebase and git merge? When should you avoid rebasing?**
*   **Merge:** Combines the histories of two branches by creating a new "merge commit." It preserves the exact history of both branches.
*   **Rebase:** Rewrites history by taking the commits from one branch and reapplying them one-by-one onto the tip of another branch. It creates a linear, cleaner history.
*   **Avoid Rebasing:** You should **never** rebase commits that have already been pushed to a shared, public repository, as this rewrites history, causing major synchronization issues for collaborators.

**D2 — Easy: Explain the difference between TCP and UDP. Name 2 protocols that use each.**
*   **TCP (Transmission Control Protocol):** Connection-oriented, reliable, ordered, and error-checked. It establishes a handshake before sending data. (Protocols: HTTP/1.1, FTP).
*   **UDP (User Datagram Protocol):** Connectionless, unreliable (best-effort delivery), and fast. It sends packets without prior negotiation. (Protocols: DNS, VoIP/SIP).

**D3 — Medium: What is a race condition? Give a concrete example in any language.**
A **race condition** occurs when the outcome of a program depends on the unpredictable sequence or timing of multiple threads or processes accessing and modifying shared data.
**Example (Pseudocode/Java):** Two threads try to increment a shared counter variable `count` initialized to 0.
Thread A reads `count` (0).
Thread B reads `count` (0).
Thread A calculates $0 + 1 = 1$ and writes 1 back to `count`.
Thread B calculates $0 + 1 = 1$ and writes 1 back to `count`.
The expected result is 2, but the actual result is 1 because the operations overlapped.

**D4 — Medium: Explain the difference between symmetric and asymmetric encryption. How are both used together in TLS?**
*   **Symmetric Encryption:** Uses a single, shared secret key for both encryption and decryption (e.g., AES). It is very fast.
*   **Asymmetric Encryption (Public-Key):** Uses a pair of keys: a public key (shared widely for encryption) and a private key (kept secret for decryption). It is computationally intensive.
*   **TLS Usage:** TLS uses both. First, the **asymmetric** handshake (using RSA or ECDH) is used to securely exchange a temporary, random **symmetric** session key. Once the session key is established, all subsequent bulk data transfer is encrypted using the fast **symmetric** algorithm.

**D5 — Medium: What is a container image layer? How does layer caching affect Dockerfile best practices?**
A container image is built from a series of read-only, immutable layers. Each instruction in a Dockerfile (e.g., `RUN`, `COPY`) creates a new layer on top of the previous one.
**Layer Caching:** Docker caches the result of each layer. If a layer's instruction and its context (files) have not changed since the last build, Docker reuses the cached layer, significantly speeding up builds.
**Best Practices:** Place instructions that change infrequently (like installing base OS packages via `RUN apt-get update && apt-get install -y ...`) near the top. Place instructions that change frequently (like `COPY . .`) near the bottom to maximize cache hits.

**D6 — Medium: You have a REST API returning HTTP 503 intermittently. Describe at least 4 things you would check, and in what order.**
1.  **Application Logs/Metrics (Deep Dive):** Check the application logs for specific exceptions, thread pool exhaustion, or resource contention that might cause the service to temporarily stop responding.
2.  **Resource Utilization (CPU/Memory):** Check the host/container metrics. Is the service hitting CPU throttling limits or running out of memory, causing the process to become unresponsive?
3.  **Dependency Health:** Check the health of downstream services (databases, caches, external APIs). A 503 often means the service cannot reach its required dependencies.
4.  **Load Balancer/Service Mesh Health:** Check the ingress controller/load balancer metrics to ensure it is correctly routing traffic and that the health checks are not prematurely marking the service as unhealthy.

**D7 — Hard: Explain the CAP theorem. Give a real-world example of a system that chooses CP over AP, and one that chooses AP over CP.**
The **CAP Theorem** states that a distributed data store can only provide two out of three guarantees simultaneously: **Consistency** (all nodes see the same data at the same time), **Availability** (every request receives a response, without guarantee that it is the latest data), and **Partition Tolerance** (the system continues to operate despite arbitrary message loss or failure of part of the network).
*   **CP Example (Consistency over Availability):** Traditional relational databases (like PostgreSQL clusters configured for strong consistency). If a network partition occurs, the system will refuse writes/reads on the minority side to prevent data divergence.
*   **AP Example (Availability over Consistency):** Cassandra or DynamoDB. If a network partition occurs, nodes continue to accept reads and writes, prioritizing uptime, and resolving conflicts later (eventual consistency).

**D8 — Medium: What is the difference between horizontal and vertical scaling? What architectural patterns enable horizontal scaling?**
*   **Vertical Scaling (Scaling Up):** Increasing the resources (CPU, RAM) of an *existing* single server instance. (Easier, but has hard limits).
*   **Horizontal Scaling (Scaling Out):** Adding *more* instances (servers/pods) to distribute the load across multiple machines. (More resilient, virtually limitless).
*   **Patterns for Horizontal Scaling:** Statelessness (ensuring no session data is tied to a specific instance), Load Balancing, and Microservices architecture.

**D9 — Easy: What is an environment variable? How do you set one that persists across shell sessions on Linux?**
An **environment variable** is a dynamic named value that can affect the way running processes will behave on a computer. They are used to pass configuration data to applications.
To set one persistently on Linux, you must add the export command to a shell startup file, such as `~/.bashrc` or `~/.zshrc`.

**D10 — Easy: What is JSON, and how does it differ from YAML? Name one advantage of each format.**
*   **JSON (JavaScript Object Notation):** A lightweight data-interchange format using key-value pairs and arrays.
    *   *Advantage:* Extremely fast to parse in most programming languages.
*   **YAML (YAML Ain't Markup Language):** A human-readable data serialization standard that uses indentation to denote structure.
    *   *Advantage:* Highly readable and concise for configuration files (like Kubernetes manifests).

**D11 — Easy: What is a REST API? Explain the difference between GET, POST, PUT, and DELETE HTTP methods.**
A **REST API** (Representational State Transfer) is an architectural style for designing networked applications, typically using standard HTTP methods to perform CRUD operations on resources identified by URLs.
*   **GET:** Retrieves a resource or a collection of resources (Safe and Idempotent).
*   **POST:** Submits data to a specified resource, often causing a change in state or creating a new resource.
*   **PUT:** Replaces an entire resource at a known URI. It is idempotent.
*   **DELETE:** Removes a specified resource. It is idempotent.

**D12 — Easy: What is version pinning in dependency management, and why is it important for reproducible builds?**
**Version Pinning** is the practice of explicitly locking down the exact version number of every dependency used in a project (e.g., `library-x: 1.2.3` instead of `library-x: ^1.2.0`).
**Importance:** It ensures **reproducible builds**. Without pinning, a dependency update (even a minor patch) could introduce breaking changes or subtle bugs into the build environment, causing the application to fail in production even if it worked locally previously.

**D13 — Easy: What is the difference between a compiled language and an interpreted language? Give two examples of each.**
*   **Compiled Language:** Source code is translated entirely into machine code (binary executable) *before* runtime by a compiler. This results in faster execution speed. (Examples: C++, Go).
*   **Interpreted Language:** Source code is read and executed line-by-line at runtime by an interpreter. This allows for greater flexibility during development. (Examples: Python, JavaScript).

**D14 — Medium: Explain what a reverse proxy is and how it differs from a forward proxy. Name two common reverse proxy servers and a use case for each.**
*   **Forward Proxy:** Sits in front of the *client*. It acts as an intermediary for the client to access the internet, often used for anonymity or filtering outbound traffic.
*   **Reverse Proxy:** Sits in front of the *server(s)*. It intercepts requests from clients and forwards them to the appropriate backend server. It shields the backend servers from direct client exposure.
*   **Servers & Use Cases:**
    *   **NGINX:** Used for SSL termination, load balancing across multiple application servers.
    *   **HAProxy:** Used for high-performance TCP/HTTP load balancing, often used in complex multi-tier architectures.

**D15 — Medium: What is a deadlock? What four conditions (Coffman conditions) must hold simultaneously for a deadlock to occur?**
A **deadlock** is a situation where two or more competing actions are waiting for the other to finish, and thus neither ever does.
The four necessary conditions (Coffman conditions) are:
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode.
2.  **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources held by other processes.
3.  **No Preemption:** A resource cannot be forcibly taken from a process; it must be released voluntarily.
4.  **Circular Wait:** A set of processes must exist where each process is waiting for a resource held by the next process in the set.

**D16 — Hard: Explain the concept of eventual consistency. How do distributed databases like Cassandra handle read-after-write consistency, and what tunable consistency levels exist?**
**Eventual Consistency:** A consistency model where, if no new updates are made to a given data item, eventually all accesses to that item will return the last updated value. There is a window of time where different replicas might return stale data.
**Cassandra Handling:** Cassandra uses mechanisms like **vector clocks** and **read repair** to resolve conflicts when replicas receive updates out of order. When a client reads data, Cassandra checks the timestamps/clocks of the returned replicas and returns the most recent version.
**Tunable Consistency Levels:** Clients specify the required consistency level per operation (e.g., `ONE`, `QUORUM`, `ALL`).
*   `ONE`: Read/write succeeds if at least one replica responds. (High Availability, Low Consistency).
*   `QUORUM`: Read/write succeeds if a majority of replicas respond. (Balanced).
*   `ALL`: Read/write succeeds only if *all* replicas respond. (High Consistency, Low Availability).

**D17 — Hard: What is mTLS (mutual TLS)? Explain the full handshake process, including how both client and server authenticate each other. Where is mTLS commonly used in infrastructure?**
**mTLS** requires *both* the client and the server to present and validate cryptographic certificates during the TLS handshake, ensuring mutual authentication.
**Handshake Process:**
1.  Client initiates connection.
2.  Server sends its certificate to the client.
3.  Client verifies the server's certificate against its trusted CA list.
4.  Server requests the client's certificate.
5.  Client sends its certificate to the server.
6.  Server verifies the client's certificate against its trusted CA list.
7.  If both validations pass, they proceed to exchange and agree upon a symmetric session key.
**Use Case:** Service-to-service communication in a Zero Trust architecture, securing internal microservice mesh traffic (e.g., Istio/Linkerd).

**D18 — Hard: Explain how a hash table works internally, including collision resolution strategies (chaining vs. open addressing). What is the time complexity for insertion, lookup, and deletion in average and worst cases?**
A hash table maps keys to values using a hash function that converts the key into an index (bucket) in an underlying array.
**Collision Resolution:** When two different keys hash to the same index:
*   **Chaining:** Each bucket holds a pointer to a linked list (or dynamic array) containing all key-value pairs that hashed to that index.
*   **Open Addressing:** If a slot is full, the algorithm probes for the next available slot in the array itself (e.g., linear probing, quadratic probing).
**Time Complexity:**
*   **Average Case (Good Hash Function, Low Load Factor):** $O(1)$ for insertion, lookup, and deletion.
*   **Worst Case (All keys hash to the same bucket):** $O(n)$ for all operations (effectively degrading to a linked list search).

**D19 — Hard: What is a circuit breaker pattern in microservices? Explain its three states (closed, open, half-open) and how it prevents cascade failures. How does it relate to retry policies and exponential backoff?**
The **Circuit Breaker** pattern prevents an application from repeatedly trying to execute an operation that is likely to fail against a remote service that is currently unavailable or slow.
**States:**
1.  **Closed:** Normal operation. Requests pass through to the service. If failures exceed a threshold, the breaker trips to Open.
2.  **Open:** Requests are immediately rejected by the breaker without attempting to call the failing service. This gives the downstream service time to recover.
3.  **Half-Open:** After a timeout in the Open state, the breaker allows a small number of test requests through. If these succeed, the breaker closes; if they fail, it returns to Open.
**Relation to Retries/Backoff:** Circuit breakers act as a *fail-fast* mechanism, preventing the system from wasting resources on doomed retries. Exponential backoff is used *within* the retry logic (if the breaker is closed or half-open) to space out retries, preventing the client from overwhelming the recovering service.

**D20 — Hard: Explain the difference between optimistic and pessimistic concurrency control in databases. When would you choose each? Give a concrete example using database features (e.g., row versioning, SELECT FOR UPDATE).**
*   **Pessimistic Concurrency Control:** Assumes conflicts are likely. It locks the data *before* the transaction reads or modifies it, preventing other transactions from accessing it until the lock is released. (High safety, lower concurrency).
    *   *Example:* Using `SELECT ... FOR UPDATE` in SQL.
*   **Optimistic Concurrency Control:** Assumes conflicts are rare. Transactions proceed without locking. Before committing, the system checks if the data has been modified by another transaction since it was read. If it has, the transaction fails and must be retried. (High concurrency, requires retry logic).
    *   *Example:* Using a `version` column (row versioning). The `UPDATE` statement includes a `WHERE version = [original_version]`. If the version doesn't match, the update affects 0 rows, signaling a conflict.
