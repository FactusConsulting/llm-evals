## JavaScript / TypeScript (20 questions)

**JS1** — `var` is function-scoped and subject to hoisting (initialized as `undefined`). `let` and `const` are block-scoped. `const` requires initialization and cannot be reassigned. Hoisting is JavaScript's behavior of moving declarations to the top of their scope during compilation, but only the declaration, not the assignment.

**JS2** — The Event Loop is the mechanism that monitors the call stack and the various queues (microtask and macrotask) to ensure non-blocking I/O operations in JavaScript. The **Call Stack** executes synchronous code. When an async operation completes, its callback is placed in the appropriate queue. The Event Loop continuously checks if the Call Stack is empty; if it is, it pulls the next task from the **Microtask Queue** (e.g., Promises) and executes it. Only after the Microtask Queue is empty does it pull a task from the **Macrotask Queue** (e.g., `setTimeout`, I/O) to execute.

**JS3** — A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). Practically, it allows an inner function to access variables from its outer function even after the outer function has finished executing. The classic for loop closure bug occurs when using `var` in a loop; all iterations reference the *same* variable, so by the time the callbacks execute, the loop variable is in its final state. The fix is to use `let` (which creates a new binding for each iteration) or pass the index as an argument to the callback.

**JS4** — A **Promise** is an object representing the eventual completion (or failure) of an asynchronous operation. **Async/await** is syntactic sugar built on top of Promises, allowing asynchronous code to be written in a synchronous-looking style. Error handling with Promises uses `.catch()` or a `try...catch` block around `await`. With `async/await`, standard `try...catch` works perfectly. `Promise.all()` waits for *all* promises to resolve, rejecting immediately if *any* one rejects. `Promise.allSettled()` waits for *all* promises to either resolve or reject, returning an array of status objects describing the outcome of each.

**JS5** — A **Type** describes the shape of data at runtime and is a compile-time construct (e.g., `string`, `number`, or a union/intersection). An **Interface** is a compile-time contract that describes the shape of an object, primarily used for ensuring objects adhere to a specific structure. You use **Types** for primitive types, unions, and complex utility types. You use **Interfaces** when defining public APIs or contracts that objects must implement. **Discriminated Unions** are unions where one member has a unique, literal property (the "discriminant"). This allows TypeScript to narrow down the type safely using a `switch` statement on that property.

**JS6** — Prototypal inheritance means that objects inherit properties and methods directly from other objects (their prototypes), rather than from classes. `Object.create(proto)` creates a new object whose internal `[[Prototype]]` link points directly to the object passed as `proto`. ES6 classes are primarily syntactic sugar over JavaScript's existing prototypal inheritance mechanism; they provide a cleaner, more familiar syntax for developers coming from class-based languages, but under the hood, they still rely on prototype chains.

**JS7** — The `this` keyword refers to the object that is currently executing the function. Its value is determined dynamically based on *how* a function is called, not where it is defined. The 4 binding rules in priority order are: 1. **New binding** (when using `new`), 2. **Explicit binding** (`.call()`, `.apply()`, `.bind()`), 3. **Implicit binding** (when a function is called as a method of an object), and 4. **Default binding** (when called globally/in strict mode, `this` is `undefined` or the global object). `bind()` returns a *new* function with the context permanently set; yes, you can re-bind the returned function.

**JS8** — **WeakRef** provides a weak reference to an object. If the object is no longer strongly referenced anywhere else, the garbage collector can reclaim it, and the `WeakRef` will automatically become "dereferenced." **FinalizationRegistry** allows you to register a callback function that will be executed *after* the associated object has been garbage collected. You use them to perform cleanup tasks (like removing listeners) without preventing the object from being collected. WeakMap keys must be objects because primitive types (like strings or numbers) are compared by value, which would prevent the garbage collector from ever recognizing that the key is no longer needed.

**JS9** — V8 optimizes JS by compiling code into highly efficient machine code. **Hidden Classes** (or Shapes) allow V8 to represent objects with the same structure (same property order/types) using a single internal representation, avoiding the overhead of checking every property individually. **Inline Caching** stores the expected type/shape of an object at the call site, allowing subsequent calls to skip type checks if the assumption holds. **Deoptimization** occurs when V8's assumptions (e.g., "this object will always have property X") are violated at runtime. Coding patterns that cause deoptimization include dynamic property addition/deletion, using `eval()`, or frequently changing object shapes.

**JS10** — **Tree-shaking** is a dead code elimination technique used by bundlers (like Webpack) to eliminate unused exports from modules during the build process. It works effectively with **ES Modules** (`import`/`export`) because ES Modules are static; the bundler can analyze the entire dependency graph at compile time to see exactly which exports are imported and used. **CommonJS** (`require`/`module.exports`) is dynamic; since `require()` can be called conditionally or based on runtime values, the bundler cannot statically determine all dependencies, making effective tree-shaking difficult or impossible.

**JS11** — `null` represents the intentional absence of any object value (a deliberate assignment of "no value"). `undefined` means a variable has been declared but has not yet been assigned a value. `==` performs type coercion before comparison (e.g., `0 == false` is true). `===` performs strict equality, checking both value and type without coercion. **Nullish coalescing (`??`)** returns the right-hand operand only if the left-hand operand is strictly `null` or `undefined`. **Optional chaining (`?.`)** allows you to safely access deeply nested properties without explicitly checking if each intermediate property exists, returning `undefined` if any part of the chain is nullish.

**JS12** — **`map()`** creates a new array by applying a function to every element in the calling array. **`filter()`** creates a new array containing only elements for which the provided testing function returns `true`. **`reduce()`** executes a reducer function on each element, resulting in a single output value. When using an initial value, `reduce()` starts the accumulation process with that value, ensuring the callback runs at least once, even on an empty array. **`flatMap()`** is useful when you need to map over an array and then flatten the result by one level. It combines the functionality of `map()` followed by `flat(1)`.

**JS13** — **Template literals** (backticks `` ` ``) allow for embedded expressions (`${expression}`) and multi-line strings, making string construction cleaner. **Tagged templates** allow a function to intercept and process the string parts and the interpolated values *before* the final string is constructed. Example: For HTML escaping, the tag function iterates over the string parts and escapes any HTML special characters (`<`, `>`, `&`) before joining them back together.

**JS14** — **Destructuring** is a syntax that allows you to unpack values from arrays or properties from objects into distinct variables. **Object destructuring** pulls properties out of an object (e.g., `const { name, age } = user;`). **Array destructuring** pulls elements out of an array (e.g., `const [first, second] = arr;`). **Default values** allow you to assign a fallback value if the property/element is missing (e.g., `const { age = 30 } = user;`). **Renaming** allows you to assign the extracted value to a different variable name (e.g., `const { name: fullName } = user;`). The **rest operator (`...`)** collects the remaining, un-destructured properties/elements into a new array or object.

**JS15** — **`for...in`** iterates over the *enumerable properties* of an object, including inherited ones (though usually only own properties are intended). **`for...of`** iterates over the *values* of an iterable object (like Arrays, Maps, Sets). You should avoid `for...in` on arrays because it iterates over keys (indices) as strings, and it can iterate over non-index properties added to the array object, leading to unpredictable iteration order and behavior.

**JS16** — **Generics** allow you to write reusable code that can work over a variety of types rather than a single one. **Generic Constraints (`extends`)** restrict the types that can be used with a generic type parameter, ensuring it has certain properties (e.g., `function identity<T extends { length: number }>(arg: T): T`). **Conditional Types (`T extends U ? X : Y`)** allow you to define types that resolve to one of two types based on a condition. **`infer`** is used within conditional types to "capture" a type from a complex structure (e.g., inferring the type of the element inside an array).

**JS17** — The **Module System** defines how code dependencies are managed. **CommonJS** (Node.js standard) uses synchronous loading via `require()` and exports via `module.exports`. **ES Modules** (standardized JS) use static `import` and `export` syntax, enabling static analysis. Node.js supports both; files ending in `.js` default to CommonJS unless the package specifies `"type": "module"` in `package.json`, which forces ES Module interpretation for `.js` files.

**JS18** — TypeScript uses a **Structural Type System**, meaning two types are considered compatible if they have the same structure (the same members with compatible types), regardless of whether they explicitly declare that they implement each other. **Excess property checks** ensure that an object passed to a function or assigned to a type does not contain properties that are *not* defined in that type. They apply when strict checks are enabled. **`extends`** implies inheritance (the derived type must have all members of the base type plus potentially more). **`satisfies`** is used for type checking only; it asserts that an object conforms to a type without imposing structural constraints on the object itself. **Variance** describes how subtyping relationships behave with generics: `in` (contravariant) means the type can be used as an input parameter (e.g., `string` can be used where `object` is expected). `out` (covariant) means the type can be used as an output parameter (e.g., `string` can be returned where `object` is expected).

**JS19** — **Proxy** is an object that wraps another object (the target) and allows you to intercept fundamental operations like property lookups, assignments, function calls, etc., via "traps." **Reflect** is an API that provides methods to perform these operations in a standardized, reflective way, often used *inside* a Proxy handler. For example, to log every time a property is set, you use the `set` trap in the Proxy handler, which calls `Reflect.set(target, key, value)` to perform the actual assignment. This is used for validation, logging, or creating reactive state management.

**JS20** — **SharedArrayBuffer** is a low-level memory buffer that can be shared directly between different execution contexts (like Web Workers). **Atomics** provides methods to perform atomic operations (operations that complete entirely without interruption) on the data within that shared memory. Web Workers communicate by sharing this memory buffer. Ordering guarantees are provided by the atomic operations themselves, ensuring that reads and writes appear to happen in a specific, predictable sequence across threads. `Atomics.wait(typedArray, index, expectedValue)` pauses the thread until another thread calls `Atomics.notify()` on that location, signaling a change.

## Bash (20 questions)

**B1** — **`$@`** expands to all positional parameters, with each parameter quoted separately (e.g., if arguments are "a b", `$@` expands to `"a" "b"`). **`$*`** expands to all positional parameters as a single string, separated by the first character of the `$IFS` variable (usually space). **`"$@"`** (quoted) ensures that arguments containing spaces are treated as distinct arguments. **`"$*"`** (quoted) treats all arguments as one single string.

**B2** — `set -euo pipefail` enforces strict error checking:
*   **`-e` (errexit):** The script will exit immediately if any command exits with a non-zero status.
*   **`-u` (nounset):** The script will exit immediately if an unset variable is used.
*   **`-o pipefail`:** If any command in a pipeline fails (returns non-zero), the entire pipeline command fails, rather than just returning the status of the last command.

**B3** — **`$(command)`** (Command Substitution) executes the `command` and substitutes its standard output into the current command line. **`command`** executes the command directly. **`$((expression))`** performs arithmetic evaluation within Bash. **`expr`** is an external utility that evaluates expressions; it is generally slower and requires more quoting than Bash's built-in arithmetic expansion.

**B4** — **Process substitution (`<(command)`)** runs a command and makes its standard output available as a temporary file path that the current shell can read from, allowing it to be used as an argument to another command that expects a file. This is useful when a command needs to be treated like a file but its output is generated dynamically. Example: `diff <(ls -1) <(ls -1 | sort)` compares the output of two separate `ls` commands as if they were files.

**B5** — You must use quoting and globbing patterns carefully. The safest way is to use `find` combined with `while read -r` and `find -print0` with `xargs -0`. Example: `find . -name "* *" -print0 | xargs -0 -I {} echo "Processing {}"`. The `for f in $(ls)` approach is dangerous because if a filename contains a space, `ls` outputs it as two separate tokens, causing the loop to iterate over two incorrect items.

**B6** — A **here document (`<<EOF`)** allows you to feed multiple lines of input into a command until a specified delimiter (EOF) is encountered. The content is treated as literal input. A **here string (`<<<`)** feeds a single line of input into a command. **`<<-EOF`** (with a leading hyphen) allows for *here document indentation stripping*; any leading tabs/spaces on subsequent lines are removed before being passed to the command.

**B7** — **`cmd > file 2>&1`**: Redirects stdout (`> file`) first, then redirects stderr (`2`) to the same location as stdout (`&1`). This is the standard, safe way to redirect both streams to the same file. **`cmd 2>&1 > file`**: Redirects stderr (`2`) to stdout (`&1`) *first*. Then, stdout (`> file`) is redirected. Since the redirection to `file` happens *after* stderr is redirected to stdout, stderr ends up going to `file` as well. **`cmd &> file`** (Bash 4+): This is a shorthand that redirects both stdout and stderr to `file` simultaneously. The first two differ because the order of redirection matters when combining streams.

**B8** — A robust lock function uses `mkdir` because it is an atomic operation (it either succeeds completely or fails completely, preventing race conditions where two processes might try to create a file simultaneously).
```bash
LOCK_DIR="/tmp/mylock_$$"
function acquire_lock() {
    if mkdir "$LOCK_DIR" 2>/dev/null; then
        echo "Lock acquired in $LOCK_DIR"
        trap 'rmdir "$LOCK_DIR"' EXIT TERM INT
        return 0
    else
        echo "Could not acquire lock." >&2
        return 1
    fi
}
# ... use lock ...
acquire_lock
```
`mkdir` is preferred because if two processes try to create the directory simultaneously, only one will succeed atomically; the other will fail immediately, whereas file creation might leave a partially written or corrupted file.

**B9** — **Single quotes (`'...'`)**: Treat everything literally; no variable expansion or command substitution occurs. **Double quotes (`"..."`)**: Allow variable expansion (`$VAR`) and command substitution (`$(cmd)`), but still respect escaping (`\"`). **No quotes**: Allows word splitting and pathname expansion (globbing). Example: `echo 'Hello $USER'` (prints "Hello $USER"), `echo "Hello $USER"` (prints "Hello username"), `echo Hello World` (prints "Hello" and "World" as two arguments).

**B10** — File existence: `[ -f file ]` (is a regular file), `[ -d dir ]` (is a directory). Readability: `[ -r file ]`. **`[ ]` (test)** is an external command that evaluates the expression. **`[[ ]]`** is a Bash keyword/builtin that offers extended features, such as pattern matching (`=~`) and better handling of word splitting, making it generally safer and more powerful than `[ ]`.

**B11** — **`$?`**: The exit status of the most recently executed foreground command (0 for success). **`$$`**: The Process ID (PID) of the current shell script. **`$!`**: The PID of the most recently backgrounded command. **`$#`**: The number of positional arguments passed to the script. Use case: `$?` to check if `grep` succeeded; `$$` to name a lock file; `$!` to monitor a background job; `$#` to loop over arguments.

**B12** — Functions are defined using `function name { ... }` or `name() { ... }`. Both are valid, but `name() { ... }` is more common. To return values, you typically print them to stdout, which can then be captured by command substitution, or you can use `return` to exit the function with a status code (0-255).
```bash
my_func() {
    echo "Value1"
    echo "Value2"
}
result=$(my_func) # result will be "Value1\nValue2"
```

**B13** — **PATH** is an environment variable containing a colon-separated list of directories where the shell searches for executable commands. Bash resolves commands by iterating through the directories listed in `$PATH` until it finds an executable file matching the command name. A **builtin command** is part of the shell itself (e.g., `cd`, `echo`) and runs internally without spawning a new process. An **external command** is a separate executable file found in a directory listed in `$PATH` (e.g., `grep`, `ls`). You can check using `type command_name`.

**B14** — **`trap`** allows you to specify commands to run when the shell receives a specific signal. You set handlers like `trap 'cleanup_function' EXIT` (runs on normal exit), `trap 'cleanup_function' INT` (runs on Ctrl+C), `trap 'cleanup_function' TERM` (runs on termination signal), and `trap 'cleanup_function' ERR` (runs if a command fails). When multiple signals arrive, the shell processes them sequentially based on the signal handler definitions, though the order of execution can be complex depending on the signal type (e.g., `SIGKILL` cannot be trapped).

**B15** — **`xargs`** takes standard input and builds and executes command lines from it. **Command substitution** (`$(cmd)`) executes a command and substitutes its output *into* the current command line. `xargs` is better for batch processing. To handle spaces/newlines safely: `find . -name "*.log" -print0 | xargs -0 -I {} your_command {}`. `-0` tells `xargs` to expect null-terminated input. `-P N` runs up to $N$ processes in parallel.

**B16** — **Bash Arrays**: Indexed arrays, declared like `my_array=(item1 item2)`. You access elements using `$my_array[index]`. You iterate using `for item in "${my_array[@]}"`. Length is `${#my_array[@]}`. **Associative Arrays**: Key-value maps, declared using `declare -A my_assoc_array`. You access elements using `${my_assoc_array[key]}`. They are used when keys are meaningful names rather than sequential indices.

**B17** — A **subshell (`(...)`)** executes commands in a separate, isolated process. Any variables set or modified inside the subshell are lost when it exits, and its exit code is returned to the parent. A **group command (`{ ...; }`)** executes commands in the *current* shell environment. Variables modified inside the group persist in the parent shell. Piping into a `while` loop (`while read line; do ... done < file`) runs the loop in a subshell context, meaning any variable changes made inside the loop body are lost when the loop finishes, as the loop itself is running in a subshell spawned by the pipe.

**B18** — Bash handles signals by intercepting them and executing associated handlers (traps). **SIGINT** (Interrupt, Ctrl+C): Graceful interruption. **SIGTERM** (Terminate): A polite request to shut down. **SIGHUP** (Hangup): Often sent when a controlling terminal closes; used to signal configuration reload. **SIGKILL** (Kill): Cannot be caught or ignored; immediate, forceful termination by the kernel. To handle graceful shutdown, use `trap` to catch `SIGINT` and `SIGTERM`, allowing the script to finish current tasks and clean up background processes before exiting.

**B19** — This requires splitting the file, processing chunks in parallel, and merging.
1. **Split:** `split -l 10000 logfile.log chunk_` (Splits into 10k line files).
2. **Process (Parallel):** `find . -name "chunk_*" -print0 | xargs -0 -P 4 -I {} bash -c 'process_chunk "$@"' _ {}` (Runs `process_chunk` on 4 files concurrently).
3. **Merge:** `cat chunk_*_processed > final_log.log`.
The performance trade-off is I/O overhead vs. CPU utilization. Error propagation is handled by checking the exit code of the `xargs` command; if any parallel job fails, `xargs` will typically return a non-zero status, which the main script can check using `if [ $? -ne 0 ]`.

**B20** — **`exec`** replaces the current shell process image with a new program, meaning the shell itself is replaced; it does not spawn a new child process. If you run `ls`, the shell remains, and `ls` is a child. If you run `exec ls`, the shell *becomes* `ls`. For file descriptor manipulation: `exec 3>file` opens file descriptor 3 to `file`. `exec 3>&-` closes file descriptor 3. A **coprocess** allows a parent shell to communicate with a child process using named pipes (FIFOs) for bidirectional, persistent communication, which is more complex than simple piping and is useful for long-running, interactive background tasks.

## PowerShell (20 questions)

**PS1** — **`Write-Output`** sends objects down the pipeline, allowing subsequent cmdlets to process them. This is the standard, pipeline-friendly way. **`Write-Host`** writes directly to the console host, bypassing the pipeline. This is useful for immediate, formatted user feedback that should not be processed by other scripts. The distinction matters because pipeline objects are structured data that cmdlets can act upon; `Write-Host` output is just raw text.

**PS2** — The PowerShell pipeline passes objects from one cmdlet to the next. **`ForEach-Object`** (alias `%`) is a cmdlet designed to process objects coming *through* the pipeline. **`foreach` statement** is a language construct used within a script block or function to iterate over a collection (like an array or list) that is already loaded into memory. Use `ForEach-Object` when processing streamed input; use `foreach` when iterating over a pre-existing collection.

**PS3** — **`[PSCustomObject]`** creates a lightweight, dynamic object with properties defined at runtime, ideal for structured output that needs to be piped. **`[hashtable]`** is a key-value collection, similar to a dictionary, where you access values via keys (e.g., `$hash['Key']`). Use `[PSCustomObject]` for structured, predictable output; use `[hashtable]` for temporary data storage or configuration lookups. Conversion: `[PSCustomObject]@{Key = $hash.Value}` or `$hash | ConvertTo-Object`.

**PS4** — PowerShell distinguishes between **Terminating Errors** (which stop the current operation, like a cmdlet failing to find a file) and **Non-Terminating Errors** (which are warnings or informational messages). **`-ErrorAction`** controls how a *specific* command handles errors (e.g., `Stop`, `Continue`, `SilentlyContinue`). **`$ErrorActionPreference`** sets the default behavior for the entire session. **`try/catch`** allows you to explicitly trap and handle terminating errors within a block of code.

**PS5** — **Splatting (`@params`)** is a technique where you pass a hashtable containing parameter names as keys and values as values to a cmdlet. This allows you to pass a set of parameters dynamically from a variable, making scripts cleaner and reusable. Example: `$params = @{Path = "C:\Logs"; LogLevel = "Error"}`. Calling `Get-Service @params` passes the parameters dynamically. This differs from passing a hashtable as a single parameter because splatting unpacks the hashtable into individual named arguments for the cmdlet.

**PS6** — **PowerShell Remoting** allows management of remote systems. **`Invoke-Command -ComputerName`** executes a script block on a remote machine, returning the results to the local session. **`Enter-PSSession`** establishes an interactive, persistent session on the remote machine, allowing you to run commands as if you were logged in locally. It primarily uses **WinRM** (Windows Remote Management) on Windows, and can leverage SSH for Linux/Unix targets.

**PS7** — The issue arises because PowerShell's pipeline is object-oriented. When you use `return $result` where `$result` is an array, PowerShell often treats the *entire array* as a single object if it's not explicitly piped or if the function is called without capturing the output correctly. In the example, `$x` becomes a single object representing the array, not an array of strings. When the function returns 0 items, it returns `$null`, which is a single null object. The correct pattern is to ensure the function *outputs* the items: `Get-Items { "one" }` or using `Write-Output "one"`.

**PS8** — A **`[scriptblock]`** is a block of code that can be passed as an argument to a cmdlet (like `Invoke-Command`). A **function** is a named, reusable block of code that can accept parameters and return values. You pass a scriptblock to a remote session using the `-ScriptBlock` parameter of `Invoke-Command`. The **double-hop problem** occurs when variables defined locally need to be accessed inside a remote scriptblock; they are not automatically serialized. You solve this by using `-ArgumentList` to explicitly pass the required variables, or by using `$using:` scope modifier within the scriptblock.

**PS9** — **`@()`** creates an empty array object. **`[array]`** is a type accelerator used to explicitly cast a variable to an array type. To force a single result into an array, wrap it: `@[single_item]`. Indexing `$null` results in an error. Indexing an empty array (`@()`) results in `$null` without error.

**PS10** — **`-eq`** (equals), **`-ne`** (not equals), **`-like`** (wildcard matching, uses `*` and `?`), **`-match`** (regex matching), **`-contains`** (checks if a specific item exists in an array), **`-in`** (checks if a value exists within a list of values). Case-sensitive variants (`-ceq`, `-clike`, etc.) enforce case matching. The difference between `-contains` and `-in` is that `-contains` checks if a *single item* is present in an array, whereas `-in` checks if a value matches *any* item in a list of values.

**PS11** — A **PowerShell module** is a collection of cmdlets, functions, and scripts that provide functionality. A **script module (`.psm1`)** is a script file that defines functions and variables. A **manifest module (`.psd1`)** is a metadata file that describes the module (version, dependencies, required parameters). A **binary module** contains compiled code. `Import-Module` loads the module's definitions into the current session's scope, making its cmdlets available.

**PS12** — **String interpolation** allows embedding expressions directly into a string using double quotes (`"`). The difference is that double quotes allow expansion (`"Hello $name"`), while single quotes (`'...'`) treat everything literally. To include expressions, use `$()` or `${expression}`. A **here-string (`@"`...`"@`)** allows multi-line strings that support interpolation, similar to template literals in JS.

**PS13** — **`Get-Member`** returns the properties and methods available on an object. **Properties** are data fields (e.g., `.Name`). **Methods** are executable functions associated with the object (e.g., `.ToString()`). **NoteProperties** are properties that are not standard members but are attached via attributes. **`Select-Object`** is used to *select* and *shape* the output (choosing specific properties or creating calculated ones). **`Where-Object`** is used to *filter* the input objects based on a condition.

**PS14** — PowerShell classes (since v5) are object-oriented constructs that allow defining custom types. They differ from C# classes in that they are less strictly typed and more dynamic, often relying on the pipeline's object model. Limitations include less rigid inheritance enforcement compared to C#. You use a **class** when you need to model a complex, reusable entity with state and behavior (e.g., a `User` object). You use a **function** when you need to perform a specific, stateless action.

**PS15** — **`CmdletBinding()`** is an attribute that transforms a standard function into an Advanced Function, giving it cmdlet-like behavior (e.g., supporting common parameters like `-Verbose`, `-ErrorAction`). **`SupportsShouldProcess`** enables the `-WhatIf` parameter. **`DefaultParameterSetName`** specifies which parameter set is used if none is specified. **`ValueFromPipeline`** allows the function to accept input objects from the pipeline. **Begin/Process/End blocks** define lifecycle stages: `Begin` runs once before processing starts; `Process` runs for each incoming object; `End` runs once after all objects have been processed.

**PS16** — **Providers** are mechanisms that allow PowerShell cmdlets (like `Get-ChildItem`) to interact with various data sources beyond the local file system. The `FileSystem` provider handles local drives. The `Registry` provider allows you to treat registry keys like folders (e.g., `Get-ChildItem HKCU:\Software`). The `Certificate` provider accesses certificate stores. This abstraction allows cmdlets to have a unified interface regardless of the underlying data source.

**PS17** — **Runspaces** are isolated environments where PowerShell code executes. A **`[runspace]`** is a single execution context. A **`[runspacepool]`** manages a pool of runspaces to handle concurrent requests efficiently. A **`[powershell]`** object represents the PowerShell engine itself. **`ForEach-Object -Parallel` (v7+)** uses the runspace pool internally to execute script blocks concurrently, managing the threading for you. Manual runspace management is required for older versions or highly customized concurrency patterns.

**PS18** — **PSScriptAnalyzer** is a static code analysis tool that checks PowerShell scripts against predefined best practices and coding standards. It enforces rules (e.g., "Always use `[CmdletBinding()]`," "Avoid using `$global:`"). **Severity levels** (e.g., Error, Warning, Information) dictate how critical the violation is. You suppress rules using `#Requires -ErrorAction SilentlyContinue` or specific analyzer directives. It integrates into CI/CD by running as a pre-commit or build step, failing the build if critical rules are violated.

**PS19** — **`$using:` scope** is used when passing variables into background jobs or parallel loops; it serializes the variable's *value* into the job's context at the time of job creation. **`$args/-ArgumentList`** is used when explicitly passing arguments to a remote session or job. Serialization limits (CLIXML depth) restrict the complexity of objects that can be passed across boundaries. Complex objects (like deeply nested custom objects or large arrays) can hit these limits, causing serialization failures, requiring you to pass only necessary primitive data or use file-based transfer for large payloads.

**PS20** — **Desired State Configuration (DSC)** is a management framework that allows you to define the *desired state* of a system (e.g., "IIS must be installed and running," "Registry key X must have value Y"). **Configurations** define the desired state. **Resources** are the specific components that enforce that state (e.g., the `WindowsFeature` resource). The **Local Configuration Manager (LCM)** is the engine on the target node that pulls the configuration and ensures the resources achieve the desired state. In modern IaC, DSC has been largely superseded by tools like Ansible, Chef, and Terraform, which offer broader orchestration capabilities.
