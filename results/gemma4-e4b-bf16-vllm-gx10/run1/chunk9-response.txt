## SC1 — Medium — Broken Deployments After Cluster Upgrade

**SC1-A:**
The pods are failing because the Kubernetes cluster upgrade enforced the **Restricted Pod Security Standard (PSS)** at the namespace level.
1.  **SecurityContext Interaction:** The pods specify `securityContext.runAsNonRoot: true`. This mandates that the container process must run as a non-root user (UID $\neq 0$).
2.  **Image Directive Conflict:** The new base image (`cgr.dev/chainguard/static:latest`) defaults its `USER` directive in the Dockerfile to `root` (UID 0).
3.  **PSS Enforcement:** The Restricted PSS prohibits running as root. When the pod starts, the Kubelet checks the security context. It sees `runAsNonRoot: true` but the container image attempts to run as root. The security context validation fails, causing the container runtime to terminate the process immediately, resulting in a `CrashLoopBackOff`.
4.  **Change from Baseline:** The **Baseline** PSS allows running as root if the image explicitly defines a non-root user or if the security context doesn't strictly forbid it. The **Restricted** PSS is much stricter, explicitly forbidding running as root unless specific, highly restrictive conditions are met, which the current configuration violates.

**SC1-B:**
```bash
kubectl get pods --all-namespaces -o json | jq -r '.items[] | select(.status.containerStatuses[]?.state?.waiting?.reason == "CrashLoopBackOff") | "\(.metadata.namespace) \(.metadata.name) \(.spec.securityContext)"'
```

**SC1-C:**
**Remediation Strategy:**
1.  **Image-Level Fix:** Modify the Dockerfile for all affected services to explicitly set a non-root user *and* ensure the application runs under that user. Change `USER root` (or rely on the default) to `USER <non_root_uid>` (e.g., `USER 1000`).
2.  **Kubernetes Manifest Changes:** In the deployment YAMLs, explicitly set `securityContext.runAsUser: <non_root_uid>` to match the user defined in the image, ensuring compliance with the PSS.
3.  **CI Pipeline Gate:** Implement a security scanning step (e.g., using Trivy or Grype) in the CI pipeline that specifically checks the resulting image manifest for the `USER` instruction in the Dockerfile, failing the build if it defaults to root or if the image does not explicitly define a non-root user.
**Zero-Downtime Rollout:**
Use a rolling update strategy (`maxSurge: 25%`, `maxUnavailable: 25%`) on the affected Deployments. Since the fix is in the image, Kubernetes will gradually replace old, failing pods with new, compliant pods. Monitor readiness probes closely during the rollout to ensure the new pods pass health checks before traffic is shifted.

## SC2 — Hard — Cross-Region Database Failover Gone Wrong

**SC2-A:**
**Stale Data Issue:** Stale data occurs because the promotion of the read replica to primary was likely **asynchronous**. In asynchronous replication, the replica applies Write-Ahead Log (WAL) records from the primary *after* they have been committed on the primary. If the primary fails before the latest committed transactions are shipped and applied to the replica, those transactions are lost upon promotion.
**Replication Lag Implication:** High replication lag means the replica is behind the primary. Promoting it means accepting the data state at the moment of promotion, which is inherently older than the last committed transaction on the original primary.
**WAL Shipping:** PostgreSQL uses streaming replication where the primary streams WAL segments to the standby. In cross-region setups, this traffic traverses the WAN.
**Data Loss Scenarios:** Data loss occurs if the primary fails before the WAL segment containing the latest committed transaction has been successfully received and flushed to disk on the replica.
**Quantifying Data Loss:** Check the `pg_stat_replication` view on the *original* primary (if accessible) or check the `pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` on the *new* primary to determine the gap between the last received and last applied LSNs.

**SC2-B:**
The goal is to transition the promoted replica into the stateful infrastructure managed by Terraform without destroying the existing resources.

1.  **Import the Promoted Replica:** Since the replica was promoted manually, it is now a standalone instance. You must import it into the state file using its new ARN/identifier.
    ```bash
    terraform import aws_db_instance.replica_instance <ARN_of_promoted_instance>
    ```
    *(Note: You must first update your Terraform code to reference the promoted instance's ARN/identifier, or use a local/data source to find it, before running the import command.)*
2.  **Update Dependent Resources:** After the instance is in state, update the configuration files (e.g., `aws_security_group_rule`, `aws_route53_record`) to reference the new instance ID/ARN.
3.  **Detach Old Instance:** Once all applications are confirmed pointing to the new EU primary, the old US-East-1 instance can be safely detached and marked for deletion in Terraform.
    ```bash
    terraform apply -target=aws_db_instance.old_instance -destroy
    ```
    *(Use `-target` to ensure only the old instance is destroyed, leaving other resources intact.)*

**SC2-C:**
**Architecture Design:**
*   **Connection Management:** Use **RDS Proxy** in the primary region and potentially in the DR region. RDS Proxy handles connection pooling, multiplexing, and automatic failover detection at the connection level, significantly reducing the load and retry errors seen by PgBouncer/applications during failover.
*   **DNS Failover:** Implement **Route53 Health Checks** targeting the application endpoints in both regions. Use weighted or failover routing policies. When the US endpoint fails the health check, Route53 automatically shifts 100% of traffic to the EU endpoint.
*   **Application Logic:** Implement **exponential backoff and jitter** in the application's database connection logic. This prevents thundering herd problems when connections are re-established after a failover.
*   **RPO < 1 Second:** To achieve this, you must use **Synchronous Replication** (or near-synchronous) across regions, which requires careful tuning of the `synchronous_commit` setting and accepting the increased write latency.
*   **Aurora Global Database:** **Yes, I would recommend Aurora Global Database.** It is specifically designed for low RPO/RTO cross-region disaster recovery. It manages the replication, failover orchestration, and data consistency much more robustly than standard RDS streaming replication, often achieving RPO measured in seconds.

## SC3 — Medium — Container Image Supply Chain Compromise

**SC3-A:**
**Immediate Incident Response Steps:**
1.  **Containment:** Isolate the affected pods immediately to prevent further malicious activity or data exfiltration.
    *   *Kubernetes Command:* `kubectl cordon <node-name>` (to prevent new pods from scheduling) and `kubectl drain <node-name> --ignore-daemonsets` (to safely evict existing pods).
    *   *Alternative Containment:* Apply a NetworkPolicy to the affected namespaces that denies all egress traffic, except to necessary monitoring endpoints.
2.  **Forensic Evidence Capture (Before Killing):**
    *   **Process Tree:** `kubectl exec -it <pod-name> -- ps auxwwf`
    *   **Network Connections:** `kubectl exec -it <pod-name> -- netstat -tulpan` or `ss -tulpan`
    *   **Filesystem Diff:** Use `kubectl cp` to copy the container's filesystem to a host volume, or use a specialized tool like `dive` or `docker export` if you can get a shell into the container runtime environment.
3.  **Post-Capture Action:** Once evidence is secured, terminate the pods (`kubectl delete pod <pod-name>`) and initiate a full forensic analysis of the captured artifacts.

**SC3-B:**
This requires interacting with the Docker Registry API (ECR). Since direct API interaction is complex, a conceptual Bash script using `aws ecr get-image` and `docker manifest inspect` is provided.

**SC3-C:**
**Hardened CI/CD Pipeline Architecture:**
1.  **Base Image Pinning:** Never use mutable tags (`:latest`, `:20-slim`). Always pin base images by their immutable **digest** (e.g., `node@sha256:abcdef123...`).
2.  **Image Signing (Cosign/Sigstore):** After a successful build, the image must be cryptographically signed using Cosign. The signature is stored alongside the image in the registry.
3.  **SBOM Generation:** Generate a Software Bill of Materials (SBOM) using tools like Syft during the build phase. This provides a complete inventory of all components.
4.  **Admission Control:** Deploy an admission controller (e.g., **Kyverno** or **OPA Gatekeeper**) in the cluster. This controller intercepts all `Pod` creation requests and verifies:
    *   The image digest matches a known-good, signed digest.
    *   The image has a valid signature from the trusted key.
5.  **Notary v2:** Notary v2 (or Sigstore) provides the framework for signing and verifying artifacts. It ensures that the image deployed is the exact artifact that passed security checks in CI, preventing tampering between the registry and the cluster.

## SC4 — Hard — Migrating a Stateful Monolith to Kubernetes

**SC4-A:**
| Blocker | Problem in K8s | Proposed Solution |
| :--- | :--- | :--- |
| **1. Local Session State** | Kubernetes is ephemeral. Pod restarts/rescheduling will lose in-memory sessions, breaking sticky sessions. | Externalize state to a distributed, highly available store (e.g., Redis Cluster, Hazelcast) accessible by all pods. |
| **2. Local NFS Mount** | Kubernetes prefers declarative, dynamic storage. Relying on a specific host path (`/data/uploads`) is non-portable. | Implement a **CSI Driver** for NFS (or migrate to cloud object storage like S3/MinIO) and use `PersistentVolumeClaim`s. |
| **3. On-Prem Oracle DB** | Kubernetes is designed for cloud-native services. Direct, high-latency connections to legacy on-prem DBs complicate HA and scaling. | Use a dedicated, highly available database proxy/gateway layer (e.g., PgBouncer equivalent for Oracle, or a dedicated cloud DB service if possible) to abstract the connection. |
| **4. IBM MQ Integration** | MQ clients are often tightly coupled to specific host IPs and network configurations, making them difficult to containerize and manage in a dynamic cluster. | Introduce an **MQ Connector Microservice**. This service runs in K8s, maintains the connection to the MQ cluster, and exposes a modern API (e.g., REST/gRPC) that the monolith calls instead of the raw MQ client library. |
| **5. F5 Sticky Sessions** | Kubernetes load balancing (Ingress/Service) is generally stateless. Sticky sessions are an anti-pattern in microservices. | Eliminate the need for sticky sessions by ensuring all state (sessions, uploads) is externalized (see Blocker 1 & 2). |

**SC4-B:**

**ReadWriteMany Necessity:** `ReadWriteMany` (RWX) is necessary because the monolith needs to write files to the shared NFS mount (`/data/uploads`), and multiple instances (pods) of the monolith might need to read or write to the *same* file concurrently or sequentially during scaling events. Standard `ReadWriteOnce` (RWO) only allows a single node/pod to mount and write to the volume at a time.

**SC4-C:**
**Phased Migration Plan (Strangler Fig Pattern):**
*   **Phase 1: State Externalization & Read Shadowing (Low Risk)**
    *   **Move:** Externalize session state to Redis Cluster (running in K8s). Migrate file uploads to a cloud object store (S3/MinIO) accessible via a new service endpoint.
    *   **Traffic:** 100% traffic remains on F5/Monolith. New K8s services are deployed in "shadow mode," receiving a copy of production traffic (if possible, via mirroring) but not serving responses.
    *   **Go/No-Go:** Successful externalization of session state; zero errors in shadow mode logs.
*   **Phase 2: Service Strangling (Medium Risk)**
    *   **Move:** Implement the MQ Connector Microservice. Route a small percentage (e.g., 5%) of non-critical write traffic through the new K8s ingress/service layer, which uses the connector.
    *   **Traffic:** F5 routes 95% to Monolith, 5% to K8s Ingress.
    *   **Go/No-Go:** 5% traffic handled successfully for 48 hours; latency metrics match legacy system.
*   **Phase 3: Full Cutover & Decommissioning (High Risk)**
    *   **Move:** Gradually shift 100% of traffic to the K8s Ingress. The monolith is kept running in a read-only state for a grace period.
    *   **Traffic:** F5 is decommissioned or placed in passive mode.
    *   **Go/No-Go:** 100% traffic handled successfully for 1 week; performance metrics (p99 latency) meet or exceed legacy baseline.
**Rollback Procedure:** If any phase fails, traffic is immediately reverted to the previous stable state (e.g., if Phase 2 fails, the K8s ingress is scaled to 0, and F5 traffic is restored to 100%).
**IBM MQ Handling:** The MQ Connector Microservice acts as the strangler. Initially, it reads from the legacy MQ queue and writes to the new K8s service API. Later, the K8s service writes back to the MQ Connector, which handles the legacy MQ interaction.

## SC5 — Medium — Mysterious Latency Spike in Microservices

**SC5-A:**
**Systematic Debugging Approach:**
1.  **Istio/Envoy Metrics:** Examine `istio_request_duration_milliseconds` filtered by the `destination_service` (inventory-service) and `source_service` (checkout-service). Look specifically at metrics related to **outlier detection** and **request queueing time** within the sidecar proxy.
2.  **Kubernetes/Node Metrics:** Verify node resource saturation (CPU throttling, I/O wait) on the inventory-service nodes during the spike, even if overall utilization looks fine.
3.  **Application Logs:** Check inventory-service logs for database connection errors, lock waits, or high garbage collection pauses during 14:00-14:30 UTC.
4.  **Distributed Tracing (Jaeger/Zipkin):** Trace requests spanning checkout $\rightarrow$ inventory. The trace visualization will show the exact span duration for the call to inventory-service. If the span duration is high, the latency is *in* the service. If the span duration is low but the total request time is high, the latency is likely in the network or the sidecar proxy.
5.  **Envoy Specifics:**
    *   **Proxy Queueing:** High values in metrics like `istio_request_queue_time_seconds` indicate the sidecar proxy is overwhelmed waiting to send the request upstream.
    *   **Upstream Latency:** High values in `istio_request_duration_milliseconds` (when measured *after* the proxy sends the request) indicate the upstream service (inventory-service) is slow.

**SC5-B:**
**SQL Diagnostic Query (PostgreSQL):**
```sql
SELECT
    a.pid AS blocking_pid,
    a.usename AS blocking_user,
    a.query AS blocking_query,
    pg_blocking_pids(a.pid) AS blocked_pids,
    b.pid AS waiting_pid,
    b.query AS waiting_query
FROM
    pg_stat_activity a
JOIN
    pg_stat_activity b ON b.wait_event_type = 'Lock' AND b.wait_event = 'transactionid'
WHERE
    a.state = 'active' AND a.query ILIKE '%stock_levels%'
    AND b.wait_event_type = 'Lock' AND b.wait_event = 'transactionid';
```
**Go Circuit Breaker Snippet (using sony/gobreaker):**

// Assume InventoryService is the client interface
type InventoryService interface {

}

func main() {
	// Configure the circuit breaker
	settings := gobreaker.Settings{
		Name: "inventory_service_cb",
		Timeout: 5 * time.Second, // How long to wait before failing fast
		MaxRequests: 5,          // Number of requests in half-open state
		Interval: 1 * time.Minute, // Time window for failure counting
		FailureThreshold: 3,     // Number of failures to trip the circuit
		ShouldTrip: func(counts gobreaker.Counts) bool {
			// Trip if failure rate exceeds 50% over the interval
			return counts.ConsecutiveFailures > 3
		},
	}
	cb := gobreaker.NewCircuitBreaker(settings)

	// Wrap the actual service call
	checkStockWithCircuitBreaker := func(itemID string) (int, error) {
		result, err := cb.Execute(func() (interface{}, error) {
			// --- Actual call to inventory-service goes here ---
			// Simulate a database lock timeout error
			if time.Now().Second()%10 < 3 {
				return nil, fmt.Errorf("database lock timeout")
			}
			return 100, nil // Success
		})

		if err != nil {
			// Handle circuit open/half-open errors
			return 0, fmt.Errorf("inventory service unavailable: %w", err)
		}
		return result.(int), nil
	}

	// Usage:
	stock, err := checkStockWithCircuitBreaker("SKU123")
	if err != nil {
		fmt.Println("Checkout failed:", err) // Circuit breaker tripped or service failed
	} else {
		fmt.Println("Stock available:", stock)
	}

**SC5-C:**
**Architectural Solution:**
1.  **CQRS (Command Query Responsibility Segregation):** Separate the high-volume, low-latency read path (used by checkout) from the complex, write-heavy reconciliation path. The checkout service reads from a highly optimized, denormalized read model.
2.  **Read Replica for Reconciliation:** The nightly reconciliation job should run exclusively against a dedicated, asynchronous **read replica** of the inventory database. This isolates the heavy locking/query load from the primary database serving live transactions.
3.  **Bulkhead Isolation:** Implement connection pool isolation. The checkout service should use one connection pool dedicated to serving requests, while the reconciliation job (if it must run on the primary) uses a completely separate, smaller pool. This prevents the reconciliation job from exhausting the pool needed by the serving pods.
4.  **CronJob Scheduling:** Reschedule the reconciliation job to run during off-peak hours (e.g., 03:00 UTC) or, ideally, run it against the read replica.
**Preventing Starvation:**
*   **PodDisruptionBudgets (PDB):** Define a PDB for the serving pods (`checkout-service`) requiring a minimum number of available replicas (e.g., `minAvailable: 80%`). This prevents voluntary disruptions (like node maintenance) from taking down too many serving instances.
*   **Resource Quotas:** Apply strict `ResourceQuota`s to the namespace hosting the CronJob. This limits the total CPU/Memory the CronJob can consume, ensuring it cannot starve the serving pods of necessary resources.

## SC6 — Hard — Zero-Trust Network Overhaul for a Hybrid Environment

**SC6-A:**
**Identity and Access Layer Design:**
The core principle is to move from network-based trust (IPs) to **cryptographically verifiable workload identity**.

1.  **Workload Identity (SPIFFE/SPIRE):**
    *   **SPIFFE (Secure Production Identity Framework for Everyone):** Defines a standard for workload identity (SVIDs - SPIFFE Verifiable Identity Documents).
    *   **SPIRE:** The implementation that issues and manages these SVIDs.
2.  **Identity Federation:**
    *   **AWS:** SPIRE agents run on EC2/EKS nodes. They attest the workload identity using **AWS IAM Roles for Service Accounts (IRSA)**. SPIRE then issues a SVID tied to that IAM role.
    *   **Azure:** SPIRE agents attest workloads using **Azure Managed Identities**.
    *   **On-Prem (VMware):** SPIRE agents attest workloads using certificates issued by the existing **On-Prem PKI** (e.g., integrating with Vault or an internal CA).
3.  **Cross-Environment Authentication:** The SVIDs (which contain verifiable identity claims) are used by a service mesh (like Istio/Linkerd) or a dedicated authorization layer. When a workload in AWS needs to talk to an on-prem service, the service mesh intercepts the request, validates the incoming SVID against the central SPIRE server, and grants access based on the identity claims (e.g., "Service A from AWS is allowed to call Service B on-prem"). **No shared secrets are used; trust is established via verifiable identity.**

**SC6-C:**
| Option | Cost | Bandwidth | Encryption | Failover | Zero-Trust Fit | Routing Change |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Direct Connect** | High (Port/Data Transfer) | Very High (Dedicated) | Managed by AWS/Customer | Manual/BGP | Excellent (Dedicated path) | Static BGP routes into TGW. |
| **ECMP VPN** | Low (Standard VPN) | Limited by Tunnel Capacity | IPsec (Encrypted) | Automatic (via BGP) | Good (Encrypted tunnels) | BGP routes advertised across multiple tunnels. |

## SC7 — Medium — CI/CD Pipeline Causing Production Drift

**SC7-A:**
**Drift Source Analysis:**
1.  **Manual `tofu apply` from Laptops:** This bypasses the centralized, audited pipeline. The local state file is likely outdated or corrupted, leading to the engineer applying changes based on a local view, potentially overwriting infrastructure managed by the pipeline or causing state corruption.
2.  **Diverged Helm Values:** Manual edits to environment-specific values files (e.g., `values-prod.yaml`) mean the Git repository no longer reflects the actual deployed state. The pipeline, when run, will attempt to reconcile the *code* state with the *actual* state, leading to unexpected changes or failures.
3.  **Direct `kubectl edit`:** This is the most dangerous. It modifies the live Kubernetes resource directly, bypassing all GitOps controls. The next `tofu apply` or Helm upgrade will see this manual change as "drift" and attempt to revert it to the state defined in Git, causing an unintended outage or configuration rollback.
**State Locking Danger:**
*   **Data Loss/Outage:** If two engineers run `tofu apply` simultaneously without locking, both might read the same state file, calculate their changes independently, and then write their changes back. The second write will overwrite the first, causing the first engineer's intended changes to be silently lost (data loss).
*   **Simultaneous Apply:** This leads to a **race condition**. The state file becomes inconsistent, potentially leading to resource creation/deletion conflicts, resulting in infrastructure failure or an unrecoverable state.

**SC7-C:**
**Drift Detection and Reconciliation:**
1.  **Scheduled Drift Detection:** Schedule a pipeline job (e.g., nightly) that runs `terraform plan -detailed-exitcode` against the production state. If the exit code is non-zero (meaning changes are detected), it triggers an alert (e.g., PagerDuty) detailing the drift, but **it does not apply the changes**.
2.  **Admission Webhook/OPA Gatekeeper:** Deploy a policy that intercepts `CREATE` or `UPDATE` requests for critical resources (e.g., ConfigMaps, Deployments) in the production namespace. The policy must check the resource metadata (e.g., `metadata.annotations`) to ensure it was created/modified by the CI service account, blocking any request lacking this annotation.
3.  **Helm Value Structure:** Use **Helmfile** to manage environments. Define a base chart structure in Git. Helmfile then uses environment-specific overlays (e.g., `values-dev.yaml`, `values-prod.yaml`) that inherit from the base, ensuring that the structure is consistent, and only environment-specific parameters (like replica count or external service URLs) are overridden.
**RBAC Enforcement:**
*   **Kubernetes RBAC:** Create a dedicated `ServiceAccount` for the CI pipeline. Bind this SA to a `Role` that grants `get`, `list`, `watch`, and `patch` permissions *only* on the resources managed by the pipeline. Crucially, deny `create` or `delete` permissions for resources that should only be managed by the pipeline.
*   **AWS RBAC:** The CI/CD runner's IAM Role must be scoped using **least privilege**. It should only have permissions (`s3:GetObject`, `s3:PutObject`, `dynamodb:PutItem`, etc.) required to interact with the specific state bucket and DynamoDB lock table, and nothing else.

## SC8 — Hard — Observability Stack Scaling Failure

**SC8-A:**
**Diagnosis:**
1.  **Prometheus OOM:** **Root Cause:** High Cardinality. Prometheus stores metrics as time series, where each unique combination of metric name + label set is a unique time series. 8.2 million active series is massive. OOM occurs because the memory required to hold the label sets and associated metadata for these millions of series exceeds the allocated 64GB RAM.
    *   **Confirmation:** Check `prometheus_tsdb_head_series` or query the API for the total series count.
    *   **Top Offender:** Use `promtool` or query the API to find metrics with the highest number of unique label combinations (e.g., `http_requests_total{endpoint="/api/v1", user_id="12345"}`).
2.  **Loki Drops:** **Root Cause:** Ingester Overload. The ingestion rate (logs/sec) exceeds the processing capacity of the ingester pods. This is often due to high volume or inefficient log parsing/labeling.
    *   **Confirmation:** Check Loki metrics like `loki_ingester_dropped_logs_total`.
3.  **Tempo Timeouts:** **Root Cause:** Backend I/O Bottleneck/Compaction Lag. Tempo relies on its backend (S3 in this case). If the Thanos compactor is lagging, older traces are not being properly indexed or moved to the long-term, queryable storage layer, leading to timeouts when querying old data.
    *   **Confirmation:** Check Thanos compaction metrics (`compactor_compaction_duration_seconds`).
4.  **Thanos Compactor Lag:** **Root Cause:** I/O Saturation or Resource Starvation. Compaction is CPU and I/O intensive. If the underlying storage or the compactor pods are resource-constrained, they cannot keep up with the incoming data rate (500GB/week).
    *   **Confirmation:** Monitor CPU/Disk I/O utilization on the Thanos compactor nodes.

**SC8-C:**
**Redesigned Observability Architecture:**
1.  **Metrics (Prometheus $\rightarrow$ Mimir/VictoriaMetrics):** Replace Prometheus with **Mimir** (or VictoriaMetrics). Mimir provides horizontal scalability, native long-term storage integration (S3), and handles high cardinality much better through its distributed architecture and remote write capabilities.
2.  **Logs (Loki $\rightarrow$ Microservices Mode):** Deploy Loki in **microservices mode**. Instead of one massive ingester, deploy smaller, dedicated ingester/querier pods per team or service domain. This isolates load spikes, preventing one noisy service from dropping logs for others.
3.  **Traces (Tempo $\rightarrow$ S3-Backed):** Ensure Tempo is configured to write traces directly to S3/object storage immediately upon ingestion, bypassing local storage bottlenecks. Use Thanos/Mimir's query layer to index metadata pointing to these S3 objects.
4.  **Governance Model (Cardinality Limits):**
    *   **Recording Rules:** Define strict recording rules in Mimir/Prometheus to pre-aggregate high-cardinality metrics into lower-cardinality summaries (e.g., instead of tracking every `user_id`, track `user_id_bucket`).
    *   **Relabeling Configs:** Implement aggressive relabeling rules at the scrape configuration level to drop unnecessary, high-cardinality labels before they even hit the TSDB.
**Chargeback Implementation:**
Implement a **Telemetry Cost Allocation Layer**. This involves:
1.  Tagging all telemetry data (metrics, logs, traces) with a mandatory `team_id` label during collection.
2.  Using Mimir/Loki's query/storage APIs to query the total storage/compute consumed *per `team_id`*.
3.  Automating a monthly report that correlates the consumed resources (e.g., GB stored, CPU-seconds used) against the team's allocated budget, enabling direct chargeback.

class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Custom permission to only allow owners of an object to edit it.

        # Read permissions are allowed to any request (GET, HEAD, OPTIONS)
        if request.method in permissions.SAFE_METHODS:
            return True
        # Write permissions are only allowed to the owner of the snippet
        return obj.owner == request.user

class UserProfileViewSet(viewsets.ModelViewSet):

    serializer_class = UserProfileSerializer

**SC9-C:**
**Defense-in-Depth Architecture:**
1.  **Authentication Migration:**
    *   **API Keys $\rightarrow$ OAuth2/JWT:** Migrate from static API keys to OAuth2. Consumers authenticate via an Identity Provider (IdP) and receive short-lived JSON Web Tokens (JWTs).
    *   **Key Rotation:** Immediately rotate all existing API keys. Use a deprecation strategy where the old keys are accepted for a grace period while new consumers adopt OAuth2.
2.  **API Gateway Layer:** Place an **API Gateway (e.g., Kong or AWS API Gateway)** in front of the ALB. This gateway handles:
    *   Centralized Authentication (validating JWT signatures/scopes).
    *   Centralized Rate Limiting (enforcing limits before traffic hits the compute layer).
    *   Request Transformation (e.g., stripping old API key headers).
3.  **Auditing:** Enable **CloudTrail Data Events** for the API Gateway/ALB to log every request, providing a comprehensive audit trail of who accessed what, when.
4.  **Data Security:** Implement **Field-Level Encryption (FLE)** for PII fields (e.g., `internal_notes`, `created_by_employee_id`) in the database. The application must use specific keys to decrypt these fields only when necessary, ensuring that even if the database is breached, the most sensitive data remains encrypted.
**Migration Strategy (API Keys to OAuth2):**
1.  **Dual Support:** Deploy the API Gateway configured to accept *both* the old API Key header *and* the new JWT header.
2.  **Phased Rollout:** Announce the deprecation timeline. New features/clients use OAuth2. Existing clients continue using API keys until the deadline.
3.  **Monitoring:** Monitor the ratio of API Key usage vs. JWT usage. Once API Key usage drops below a threshold (e.g., 5%), disable the API Key validation path in the gateway.

## SC10 — Hard — Designing a Multi-Cluster Disaster Recovery Platform

**SC10-A:**
**Multi-Cluster Architecture Comparison:**

| Feature | Active-Passive (Velero) | Active-Active (Service Mesh) |
| :--- | :--- | :--- |
| **RPO/RTO Feasibility** | **RPO:** Dependent on backup frequency (e.g., 15 min). **RTO:** Dependent on restore time (can be slow). | **RPO:** Near Zero (Continuous replication). **RTO:** Near Zero (Automatic traffic shift). |
| **Latency Impact (12ms)** | Minimal impact on backup/restore process itself. | Minimal impact on synchronous replication latency, but requires careful tuning. |
| **200TB MinIO** | Requires periodic, large-scale cross-site backup/restore. Slow. | Requires continuous, asynchronous cross-site replication (e.g., MinIO replication features). |
| **Stateful Component Replication** | **PostgreSQL:** Patroni/Streaming Replication (Asynchronous/Synchronous). **Redis:** Sentinel/Cluster Replication. **RabbitMQ:** Mirroring/Federation. **MinIO:** Cross-Region Replication. | **PostgreSQL:** Synchronous/Asynchronous Streaming. **Redis:** Cluster Replication. **RabbitMQ:** Federation. **MinIO:** Cross-Region Replication. |

**Conclusion:** To meet the strict **RPO of 15 minutes and RTO of 1 hour**, **Active-Active with a Service Mesh** is superior, as it provides near-zero RPO and automated failover, easily meeting the RTO. Active-Passive relies too heavily on the speed of the restore process to guarantee the RTO.

**Replication Strategy Summary:**
*   **PostgreSQL:** Patroni configured for **Synchronous Commit** across sites (if latency allows) or highly tuned asynchronous replication with aggressive WAL shipping.
*   **Redis:** Sentinel monitoring with automatic failover to the secondary cluster.
*   **RabbitMQ:** Use **Federation** or **Mirrored Queues** across the two clusters to ensure message durability across sites.
*   **MinIO:** Utilize MinIO's built-in **Cross-Region Replication** feature to asynchronously copy objects from Chicago to Dallas.

**SC10-C:**
**Automated Failover Orchestration Sequence:**
1.  **Failure Detection:**
    *   **Monitoring:** A dedicated external monitoring system (e.g., Prometheus Alertmanager, or a dedicated health check service) monitors the primary endpoint (Chicago) via TCP/HTTP checks.
    *   **Site Down Definition:** A site is considered "down" only if the monitoring system fails to receive a heartbeat from the primary *and* the Patroni cluster reports the primary is unreachable for a defined timeout period (e.g., 3 minutes), preventing false positives from transient network blips.
2.  **Patroni Promotion:** The monitoring system triggers the failover mechanism (e.g., calling a dedicated API endpoint or updating a configuration in the DCS). Patroni detects the primary failure and automatically promotes the Dallas standby to primary.
3.  **DNS Failover (GSLB):** The GSLB (Global Server Load Balancer) health checks fail for the Chicago endpoint. The GSLB automatically updates DNS records to point all traffic to the Dallas endpoint.
4.  **Stateful Component Failover:**
    *   **Redis:** Sentinel detects the primary failure and promotes the Dallas replica.
    *   **RabbitMQ:** Federation/Mirroring ensures queues are available on the Dallas cluster.
    *   **MinIO:** The application layer must be configured to point to the Dallas MinIO endpoint, which has already caught up via cross-region replication.
5.  **Infrastructure State Update:** A final, automated step runs a targeted `terraform apply` or configuration update to reflect the new primary region (Dallas) in the infrastructure state, ensuring future deployments target the correct active site.
**Split-Brain Handling:**
*   **Prevention:** Patroni's use of a Distributed Configuration Store (DCS like etcd) is the primary defense. Only one node can successfully acquire the lock to become the primary.
*   **Mitigation:** If a split-brain *does* occur (e.g., network partition prevents communication but both nodes think they are primary), the DCS quorum mechanism will force one node to step down, or the application logic must be designed to reject writes if it cannot confirm quorum health.
**Failback Procedure:**
1.  **Chicago Recovery:** Once Chicago is stable, it is brought back online as a *new standby* in the Dallas cluster.
2.  **Re-synchronization:** Patroni ensures the Chicago standby catches up fully from the current Dallas primary.
3.  **Planned Cutover:** A maintenance window is scheduled. The GSLB is manually shifted back to Chicago. Patroni is instructed to promote Chicago back to primary, and Dallas reverts to standby. This is a controlled, planned failback, not an automatic one.
