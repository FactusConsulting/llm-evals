## Cloud Infrastructure Architecture

**CL1** — **IaaS (Infrastructure as a Service):** Provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS (Platform as a Service):** Provides a managed runtime/framework (e.g., Google App Engine). **SaaS (Software as a Service):** Provides a complete application (e.g., Microsoft 365).

**CL2** — **Shared Responsibility:** In **IaaS**, the provider manages hardware/hypervisor; you manage OS, middleware, and data. In **Managed Kubernetes**, the provider manages the control plane; you manage worker nodes, pods, and data. In **SaaS**, the provider manages almost everything; you manage only your data and user access.

**CL3** — A **VPC** is your private network; a **Subnet** is a range of IPs within that VPC. A **Security Group** acts as a stateful firewall for instances; a **NACL** is a stateless firewall for subnets. They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Security Group. **Stateful** (SG) remembers connection state; **Stateless** (NACL) requires explicit rules for both inbound and outbound.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment. **Organizational Units (OUs)** group accounts for policy application. **Guardrails** (like AWS SCPs) enforce limits. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes connectivity. **Centralized Logging** ensures auditability. A **single-account approach** is problematic due to massive blast radius, lack of isolation, and hitting service limits.

**CL5** — **IaC** manages infrastructure via code. **Terraform/OpenTofu** is provider-agnostic and industry standard. **Pulumi** uses general-purpose languages (Python, TS). **CloudFormation/Bicep** are cloud-native (AWS/Azure). **Crossplane** manages cloud resources via Kubernetes CRDs. Choose Terraform for multi-cloud, Pulumi for developer experience, and CloudFormation/Bicep for deep native integration.

**CL6** — **HPA** scales pods based on metrics (CPU/Mem). **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes. **KEDA** is event-driven (e.g., scale based on Kafka lag). Use **KEDA** when scaling depends on external event sources rather than just resource utilization.

**CL7** — **RPO** (data loss limit) and **RTO** (downtime limit) drive the design. **Active-Active** provides zero RTO/RPO but is expensive. **Active-Passive** involves failover. **Sync replication** ensures zero data loss (high latency); **Async** allows higher performance (risk of data loss). **Pilot Light** (minimal resources running), **Warm Standby** (scaled-down version), and **Multi-site Active-Active** (full capacity in both regions).

**CL8** — **GitOps** uses Git as the single source of truth. **ArgoCD** is K8s-native with a UI; **FluxCD** is more lightweight/modular. **Secrets** are handled via **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (fetches from Vault), or **Vault** (centralized). **Drift** is automatically corrected when the controller reconciles the cluster back to the Git state.

**CL9** — Use a **StatefulSet** for stable identities/storage. Use **PV/PVC** with a **Local Storage Class** for low latency. A **Headless Service** provides direct pod IP access. **Init containers** prepare the filesystem. **ConfigMaps** are mounted as volumes to specific paths. **Pod Disruption Budgets (PDB)** ensure availability during maintenance.

**CL10** — **Service Account** is K8s-local; **Workload Identity** is the cloud-native concept; **IRSA** is the AWS implementation. Mounting long-lived credentials in a pod is dangerous (theft risk). **Workload Identity Federation** uses OIDC to exchange a K8s token for a short-lived cloud IAM token, eliminating static secrets.

**CL11** — **Object (S3/Blob):** Unstructured, massive scale, cheap (e.g., media). **Block (EBS/Disk):** Low-latency, attached to VMs (e.g., OS/DB). **File (EFS/Azure Files):** Shared access via NFS/SMB (e.g., shared config). Object has highest durability; Block/File vary by tier.

**CL12** — **Zero Trust** assumes no implicit trust. Use **Network Policies** (L4 isolation), **Service Mesh** (mTLS/L7), **Pod Identity** (least privilege), **Admission Controllers** (policy enforcement), **Image Signing** (provenance), and **Falco** (runtime detection). This differs from a **Perimeter model** which trusts everything inside the "walls."

**CL13** — A **CDN** caches content at edge locations near users. Services: **CloudFront/Azure Front Door**. Use a CDN to reduce latency and origin load; serve directly only for low-traffic, non-static, or highly dynamic content.

**CL14** — **Regions** are geographic areas; **Availability Zones (AZs)** are isolated data centers within a region. Deploy across multiple AZs for high availability. **Zonal** resources live in one AZ; **Regional** resources (like S3) are replicated across multiple AZs.

**CL15** — **Managed DBs** (RDS/Cloud SQL) handle patching, backups, HA, and scaling. You handle schema design, query optimization, and application-level logic.

**CL16** — **IAM Users** (individuals), **Groups** (collections), **Roles** (temporary identities), **Policies** (permissions). **Least Privilege** means granting only the minimum permissions required for a task.

**CL17** — **Serverless** is event-driven compute. **Lambda/Functions** scale to zero. **Cold starts** are the latency penalty when a function is invoked after being idle. Serverless is a poor fit for long-running processes or workloads requiring constant high-performance/low-latency.

**CL18** — **Ingress** is the standard L7 resource; **Gateway API** is the modern, role-oriented evolution; **Cloud LB** handles L4/L7; **Service Mesh** handles internal L7. **TLS termination** can happen at the LB, Ingress, or Mesh level. **Gateway API** is preferred for complex, multi-tenant routing.

**CL19** — Use **Reserved Instances/Savings Plans** for predictable loads; **Spot** for fault-tolerant workloads. Implement **Right-sizing**, **Storage Tiering**, and **Idle Detection**. Use **FinOps** to implement **Showback/Chargeback** (assigning costs to specific teams) via tagging and specialized tools like CloudHealth or AWS Cost Explorer.

**CL20** — **Multi-cloud** uses **Kubernetes** as the abstraction, **Terraform** for IaC, and **VPN/Interconnect** for networking. **Identity Federation** links cloud IAMs. **Trade-off:** It prevents lock-in but introduces massive operational complexity. It is justified for high-availability/compliance but often unnecessary for most startups.

## OT Infrastructure Architecture

**OT1** — **Purdue Model:** **L0:** Physical process; **L1:** Basic control (PLCs); **L2:** Supervisory (HMIs); **L3:** Site operations (Historians); **L4/5:** Enterprise/Cloud.

**OT2** — **IT** focuses on Confidentiality; **OT** focuses on Availability/Safety. You cannot patch OT like IT because updates can cause real-time timing failures or system crashes, risking physical safety.

**OT3** — An **IDMZ** acts as a buffer between L4 and L3. Only specific, inspected traffic (e.g., MQTT, OPC UA) should pass. Direct L4 $\rightarrow$ L1 connectivity is dangerous as it bypasses all control/monitoring layers.

**OT4** — **Modbus TCP:** L1/L2. **OPC UA:** L2/L3. **EtherNet/IP:** L1/L2. **PROFINET:** L1/L2. **MQTT:** L3/L4/Cloud.

**OT5** — A **Data Diode** is hardware-enforced one-way communication (physically impossible to go back). A **Firewall** is software-based and bidirectional. Use a diode for high-security telemetry where no return path is needed.

**OT6** — **Flow:** Sensor $\rightarrow$ PLC $\rightarrow$ Historian $\rightarrow$ Edge Gateway $\rightarrow$ MQTT Broker $\rightarrow$ Cloud. Security boundaries should be at the **IDMZ** and the **Edge Gateway**.

**OT7** — **IEC 62443:** A **Zone** is a grouping of assets with similar security requirements. A **Conduit** is the communication path between zones. **Model:** Corporate (Zone) $\rightarrow$ Conduit $\rightarrow$ IDMZ $\rightarrow$ Conduit $\rightarrow$ SCADA (Zone) $\rightarrow$ Conduit $\rightarrow$ PLC (Zone).

**OT8** — Implement **VLANs** for segmentation. Place **Firewalls** between production lines. Use a **Jump Host** for vendor access. Transition by building the new segmented network in parallel and migrating one line at a time during scheduled downtime.

**OT9** — **SIS** (Safety) is independent of **BPCS** (Process Control). **IEC 61511** governs SIS. SIS must be isolated to prevent "common-mode failure." If ransomware hits the SIS, it could disable safety shutdowns, leading to physical catastrophe.

**OT10** — **PLC:** Discrete control (fast). **DCS:** Process control (integrated/large scale). **SCADA:** Supervisory (distributed). They can coexist in a large plant.

**OT11** — Use **Jump Hosts** with **MFA**, **Session Recording**, and **Time-limited access**. Direct RDP to an HMI is unacceptable as it provides a direct path for lateral movement.

**OT12** — **Plan:** 1. Detect via **IDS/Anomaly detection**. 2. **Asset Inventory** to identify scope. 3. **Isolate** the compromised segment. 4. **Coordinate** with the control room. **Operator Role:** Prioritize physical safety and manual override if necessary.

**OT13** — **HMI** is the operator's interface for monitoring/control. An **Engineering Workstation** is used for programming and configuring PLCs/logic.

**OT14** — A **Historian** records time-series process data. **Plant Historian (L3)** is for real-time operational use; **Enterprise Historian (L4)** is for long-term business analytics.

**OT15** — **Ladder Logic** is a graphical programming language mimicking electrical relay diagrams. It is dominant because it is intuitive for electricians/engineers and highly reliable for PLC execution.

**OT16** — **RTU** is used for remote, low-power, or wide-area telemetry (e.g., pipelines). **PLC** is used for high-speed, local, discrete control.

**OT17** — **Analog** is continuous (4-20mA); **Digital** is discrete (On/Off). **4-20mA** is preferred because a 0mA reading indicates a broken wire (fault detection), whereas 0-20mA cannot distinguish between a zero reading and a broken wire.

**OT18** — **Asset Inventory** is the foundation of security. Use **Passive Monitoring** (safe) to listen to traffic. **Active Scanning** is dangerous because it can overwhelm/crash sensitive legacy OT devices.

**OT19** — **MITRE ATT&CK for ICS:** Tactics include **Inhibit Response Function**, **Impair Process Control**, and **Impair Safety Function**. It differs from Enterprise by focusing on physical process impact. Use it to map where your network segmentation fails to prevent process manipulation.

**OT20** — **SOC Design:** Collect logs via **Passive Taps**, integrate into **SIEM**, use **OT-specific rules** (e.g., unauthorized S7 comms). **Triage:** Requires OT engineers to validate if an alert is a process anomaly or a cyber attack. **Firmware change alert:** Treat as a critical incident; trigger immediate isolation and verification.
