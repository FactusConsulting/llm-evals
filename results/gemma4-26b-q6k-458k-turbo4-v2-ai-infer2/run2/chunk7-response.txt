## Application Architecture

**AA1** — A **monolith** is a single, unified unit where all business logic, data access, and UI are bundled together. **Microservices** are a collection of small, independent services communicating over a network. 
Three problems microservices introduce: 
1. **Network Latency:** Inter-service calls add overhead.
2. **Data Consistency:** Managing transactions across distributed databases is difficult (requires Sagas).
3. **Operational Complexity:** Requires advanced observability, service discovery, and automated deployment pipelines.

**AA2** — **Synchronous** communication means the caller waits for a response before proceeding (e.g., a REST API call). **Asynchronous** means the caller sends a message and continues its work without waiting for an immediate result (e.g., a message sent to RabbitMQ).

**AA3** — An **API Gateway** is application-aware; it handles routing, authentication, rate limiting, and protocol translation. A **reverse proxy** (like Nginx) primarily handles traffic forwarding and load balancing. An API Gateway cannot *entirely* replace a reverse proxy if you need low-level L4 traffic management or specialized proxying without application-level logic, but in modern stacks, the Gateway often performs both roles.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. 
* **Choreography:** Each service produces/listens to events; there is no central coordinator. Best for simple, decoupled workflows.
* **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex workflows with many steps.

**AA5** — **CQRS** separates the models for reading data (Query) from writing data (Command). It is often paired with **Event Sourcing** (storing state as a sequence of events). This combination solves the problem of high-contention workloads where read and write patterns differ significantly, allowing you to scale them independently and provide a perfect audit log.

**AA6** — The **Circuit Breaker** prevents a service from repeatedly trying an operation that is likely to fail. 
* **States:** **Closed** (requests flow), **Open** (requests fail immediately), **Half-Open** (testing if the service has recovered). 
* **Difference:** A retry handles transient errors; a circuit breaker handles systemic failures. You use them together by retrying small errors, but tripping the circuit if the retry threshold is exceeded.

**AA7** — 
1. **Shared DB, Shared Schema:** Lowest cost, lowest security (data leakage risk), highest noisy-neighbor risk.
2. **Shared DB, Separate Schema:** Medium cost, medium security, medium noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security (strong isolation), lowest noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all nodes see the same data simultaneously; **eventual consistency** allows temporary divergence. For an inventory system, you need **strong consistency**. 
**Architecture:** Use an RDBMS (like PostgreSQL) with ACID properties. At scale, use a distributed consensus algorithm (like Raft or Paxos) or a partitioned database that guarantees linearizability for specific keys (like Spanner).

**AA9** — A **sidecar proxy** is a helper container running alongside the application container. In **Istio**, **Envoy** acts as the data plane (handling actual traffic), while the **control plane** (Istiod) manages configuration and policy. **mTLS** between sidecars ensures that even if the network is intercepted, the identity of the services is verified and the data is encrypted, which application-level TLS cannot guarantee without manual implementation in every service.

**AA10** — The **Strangler Fig** pattern involves placing a proxy in front of the monolith. You identify a single bounded context (e.g., "Billing"), build it as a new .NET 8 microservice, and redirect traffic for *only* that context to the new service. Repeat until the monolith is "strangled" and can be decommissioned.

**AA11** — The **12-Factor App** provides principles for cloud-native apps. 
1. **Codebase:** One repo per app. 
2. **Dependencies:** Explicitly declare/isolate. 
3. **Config:** Store in environment. 
4. **Backing Services:** Treat as attached resources. 
5. **Processes:** Stateless/share-nothing. 
6. **Disposability:** Fast startup/graceful shutdown. 
These ensure apps are portable, scalable, and resilient in dynamic environments.

**AA12** — 
* **Event-driven (Kafka):** High scalability, loose coupling, complex debugging, strict ordering (within partitions), handles failures via replayability.
* **Request-driven (REST/gRPC):** Lower scalability, tight coupling, easy debugging, immediate feedback, harder failure handling (requires retries).
**Choose Event-driven** for high-throughput, asynchronous processing; **Request-driven** for real-time user interactions.

**AA13** — A **load balancer** distributes incoming network traffic across multiple servers. **Layer 4** works at the transport level (IP/TCP/UDP). **Layer 7** works at the application level (HTTP/HTTPS). **L7 is required** for path-based routing (e.g., `/api` goes to Service A, `/images` to Service B).

**AA14** — A **message queue** (RabbitMQ) is designed for transient tasks; once a message is consumed, it's gone. A **log-based broker** (Kafka) is a persistent append-only log; messages stay for a set duration, allowing multiple consumers to replay the same data. Pick **RabbitMQ** for complex routing/task queues; pick **Kafka** for high-throughput stream processing and data replay.

**AA15** — A **container** virtualizes the Operating System (sharing the host kernel), whereas a **VM** virtualizes the hardware (including a full guest OS). Containers are popular because they are lightweight, start in seconds, and have minimal overhead.

**AA16** — **Stateless** services do not store client data locally; **stateful** services do (e.g., a database). Stateless services are easier to scale because any instance can handle any request, allowing for simple horizontal scaling via a load balancer.

**AA17** — An **ORM** maps database tables to programming objects. Examples: **Hibernate** (Java), **SQLAlchemy** (Python). **Trade-offs:** ORMs increase development speed and abstraction but can introduce performance overhead and "N+1" query problems compared to optimized raw SQL.

**AA18** — The **Bulkhead pattern** isolates elements of a system into pools so that if one fails, others continue. In microservices, this is implemented by assigning specific **thread pools** to specific downstream services or using **separate deployment groups** (clusters) for different tenants to prevent one tenant from consuming all system resources.

**AA19** — **OT (Operational Transformation)** requires a central server to resolve conflicts; **CRDTs (Conflict-free Replicated Data Types)** use mathematical structures to resolve conflicts locally without a central authority. For **offline editing**, I would choose **CRDTs** because they allow users to work independently and merge seamlessly when they reconnect without needing a central coordinator to arbitrate every change.

**AA20** — Challenges include maintaining a single trace across different protocols and languages. 
* **Context Propagation:** Passing TraceIDs via headers (W3C Trace Context). 
* **Sampling:** **Head-based** (decide at start) vs **Tail-based** (decide after the trace completes, useful for catching errors). 
* **Kafka:** Ensure the TraceID is injected into the Kafka message headers so the consumer can continue the trace.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1** runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2** runs on top of an OS (e.g., Oracle VirtualBox, VMware Workstation).

**OP2** — **SAN (Storage Area Network)** provides block-level storage (iSCSI, Fibre Channel) for high-performance needs like databases. **NAS (Network Attached Storage)** provides file-level storage (NFS, SMB) for shared files. Use SAN for servers/VMs; use NAS for user file shares.

**OP3** — **3-tier** (Core, Distribution, Access) can suffer from bottlenecks and high latency. **Leaf-Spine** is a two-tier architecture that provides predictable, low-latency "East-West" traffic (server-to-server) and scales linearly by adding spine switches.

**OP4** — A highly available Proxmox cluster needs at least 3 nodes for **quorum**. Use **Ceph** for shared storage. Implement **fencing (STONITH)** to prevent a failed node from corrupting data. If a node fails, the cluster detects the loss of quorum/heartbeat and restarts the VMs on the remaining healthy nodes.

**OP5** — **VLAN trunking** allows multiple VLANs to pass over a single physical link using **802.1Q** tags. On Linux, you create sub-interfaces (e.g., `eth0.10`, `eth0.20`) where the number after the dot is the VLAN ID.

**OP6** — **RAID 1** (Mirror), **5** (Parity), **6** (Double Parity), **10** (Mirror+Striping), **Z2** (ZFS double parity). For a 6-drive database server, I would choose **RAID 6 or Z2** to balance high capacity and the ability to survive two simultaneous drive failures.

**OP7** — Use **Split-horizon DNS** to provide different IP addresses for internal vs. external users. **Recursive resolvers** handle client queries; **Authoritative servers** hold the actual records. **Conditional forwarding** sends specific domains to specific servers. When a laptop moves to VPN, it uses the internal DNS via the VPN tunnel.

**OP8** — The **Root CA** signs the **Subordinate/Issuing CA**, which signs end-entity certificates. **CRL** is a list of revoked certs; **OCSP** is a real-time check. A compromised **Subordinate CA** affects its branch; a compromised **Root CA** invalidates the entire trust chain.

**OP9** — **MPLS** (Reliable/Expensive), **IPsec VPN** (Cheap/Internet), **SD-WAN** (Flexible/Managed), **WireGuard** (Fast/Modern). For 50 users/site with VoIP, I recommend **SD-WAN** for its ability to prioritize traffic and manage multiple paths (Internet + MPLS) intelligently.

**OP10** — **iDRAC/iLO/IPMI** provide out-of-band management, allowing access to the server even if the OS is crashed. If exposed to the internet, an attacker could gain full control of the hardware.

**OP11** — **LVM** is standard volume management; **LVM-Thin** allows over-provisioning with space-efficient snapshots; **ZFS** provides integrated volume management with Copy-on-Write snapshots.

**OP12** — A **stretch cluster** requires low latency (<10ms) and a **tiebreaker** (witness) to prevent **split-brain** (where two halves of the cluster think they are the leader). 2-site Ceph is risky without a 3rd site/witness because a network partition causes both sites to stop functioning to protect data integrity.

**OP13** — **DORA**: **D**iscover, **O**ffer, **R**equest, **A**cknowledge. If the server is unavailable and the lease expires, the client loses its IP and network connectivity.

**OP14** — A **managed switch** allows configuration (VLANs, Spanning Tree, SNMP); an **unmanaged switch** is plug-and-play with no control. Managed switches are essential for security and segmentation in enterprises.

**OP15** — **NTP** ensures all servers have the same time. Clock drift causes authentication failures (Kerberos), broken logs, and database replication errors.

**OP16** — **Physical** (Full hardware), **VM** (Virtual hardware), **Container** (Virtual OS). Run workloads on **bare metal** for maximum performance/low latency (e.g., high-frequency trading or massive databases).

**OP17** — **UPS** provides short-term battery power; a **generator** provides long-term power. An **ATS** automatically switches the load from mains to the generator when power fails.

**OP18** — **Active-Passive** has one standby; **Active-Active** uses both. For PostgreSQL HA, use **Pacemaker/Corosync** to manage a **Virtual IP**. If the primary fails, **STONITH** (fencing) ensures the old primary is truly dead before the standby takes over the VIP.

**OP19** — **3-2-1 Rule:** 3 copies, 2 media types, 1 offsite. **RPO** is max data loss; **RTO** is max downtime. **Immutable backups** protect against ransomware. **Backup** is the data copy; **Disaster Recovery** is the entire plan/process to restore service.

**OP20** — **Supplicant** (client), **Authenticator** (switch), **Auth Server** (RADIUS). **EAP-TLS** is certificate-based (secure); **PEAP** is password-based. **Dynamic VLAN assignment** places users in specific networks based on identity. **MAB** allows non-802.1X devices (like printers) to connect via MAC address filtering.
