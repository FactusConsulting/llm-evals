## OpenTofu / Terraform

**T1** — `tofu plan` creates an execution plan, showing what changes will be made to reach the desired state without actually performing them. `tofu apply` executes those changes.

**T2** — State is a JSON file mapping your configuration to real-world resources. Remote state is critical for collaboration, as it provides a single source of truth, enables state locking to prevent concurrent modifications, and ensures team members are working against the same infrastructure.

**T3** — `count` uses an integer index (e.g., `[0]`, `[1]`), making it fragile if items are removed from the middle. `for_each` uses unique keys (strings), making it stable. `for_each` is preferred when managing collections where items might be added or removed, as it prevents unnecessary resource recreation.

**T4** — This is "drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the cloud API, detects the discrepancy between the real resource and the state file, and proposes a plan to revert the manual change to match the configuration.

**T5**
```hcl
resource "aws_instance" "vm" {
  for_each = toset(["web1", "web2", "web3"])
  ami           = "ami-xxxxxx"
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
```

**T6** — `terraform_remote_state` allows one configuration to read the entire state file of another, creating tight coupling and security risks (access to all data). The recommended alternative is using **Module Outputs** combined with a shared data source or a dedicated Key/Value store, which promotes loose coupling and follows the principle of least privilege.

**T7** — This is a race condition. The `null_resource` completes its execution, but the output value (often a file path or string) is not yet "ready" or visible to the provider in the same cycle. To fix it, ensure the dependent resource has an explicit `depends_on = [null_resource.name]` or, preferably, use a resource that natively manages the configuration file rather than a `null_resource`.

**T8** — `tofu import` brings existing infrastructure under management. Its limitation is that it only updates the state, not the code. The `import` **block** (1.5+) is declarative; you define the resource in code and the block, then run `plan`. This allows you to preview the import process and integrates it into the standard workflow.

**T9** — A **variable** (input) is a parameter passed into a module to customize its behavior. An **output** is a value exported by a module so other modules or the CLI can consume its data.

**T10** — A provider is a plugin that translates OpenTofu commands into API calls for specific platforms (AWS, Azure, etc.). If you run `tofu plan` without `tofu init`, the command will fail because the required provider binaries have not been downloaded to the `.terraform` directory.

**T11** — The `.terraform.lock.hcl` file contains the specific versions and checksums of providers used. It should be committed to version control to ensure every environment (Dev, Prod) and every team member uses the exact same provider versions, ensuring reproducibility.

**T12** — `tofu destroy` removes all resources managed by the current configuration. To target a single resource, use `tofu destroy -target=resource_type.resource_name`.

**T13** — A data source allows you to fetch information from existing infrastructure not managed by your current OpenTofu code. Example: Using `data "aws_ami" "latest"` to find the most recent Amazon Linux AMI ID.

**T14** — **Variables** are external inputs provided by the user. **Locals** are internal constants or derived values used to simplify code and reduce repetition. Use `locals` for complex logic or to avoid hardcoding the same value in multiple places within a module.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime).
- `prevent_destroy`: Stops OpenTofu from destroying a resource (safety mechanism for databases).
- `ignore_changes`: Tells OpenTofu to ignore updates to specific attributes (useful for tags added by external processes).

**T16** — A `moved` block allows you to rename a resource or move it into a module within your code without OpenTofu thinking the old resource was deleted and a new one needs to be created. It maps the old address to the new address in the state.

**T17** — The dependency graph is a directed acyclic graph (DAG). **Implicit dependencies** are created when one resource references another's attribute. **Explicit dependencies** are created via `depends_on`. `depends_on` should be used sparingly because it forces a specific order and can reduce parallelism, slowing down execution.

**T18** — 
1. **State Splitting**: Break large state files into smaller, decoupled ones (Tradeoff: increased complexity in managing multiple states).
2. **`-refresh=false`**: Skips the API refresh (Tradeoff: risks acting on stale data).
3. **Targeting**: Use `-target` for specific fixes (Tradeoff: can lead to inconsistent state).
4. **Reducing Resource Count**: Use modules and logic to minimize unnecessary resources (Tradeoff: requires significant refactoring).

**T19** — State locking prevents two users from running `apply` simultaneously, which would corrupt the state. If a pipeline crashes, the lock remains. You can break it with `tofu force-unlock <lock_id>`. **Risk**: If you unlock while another process is actually running, you will likely corrupt your state file.

**T20** — 
1. Update the configuration with the new `backend "s3" {}` block.
2. Run `tofu init -migrate-state`.
3. OpenTofu will detect the local state and ask to copy it to the new S3 backend.
4. Verify by running `tofu plan`; it should show "No changes" (meaning the state matches the code).

## Ansible

**A1** — A **playbook** is the orchestration file (the "what"); a **role** is a reusable collection of tasks, variables, and files (the "package"); a **task** is a single action performed on a host (the "step").

**A2** — `ansible_facts` is a dictionary of system information gathered by Ansible. You access the OS family via `ansible_facts['os_family']`.

**A3** — `command` executes a command without a shell (no pipes/redirects); `shell` runs through `/bin/sh` (supports pipes/redirects); `raw` bypasses Python entirely and sends commands via SSH (used for bootstrapping).

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent**: `apt: name=nginx state=present`.
- **Non-idempotent**: `shell: echo "hello" >> /tmp/file`.

**A5**
```yaml
- name: Install htop
  package:
    name: "{{ 'htop' if ansible_os_family == 'Debian' else 'htop' }}"
  # Note: For RedHat/EPEL requirement, use a conditional task or block
- name: Install EPEL on RedHat
  yum: name=epel-release state=present
  when: ansible_os_family == "RedHat"
```

**A6** — Order (lowest to highest): `role defaults` < `group_vars` < `host_vars` < `set_fact` < `extra_vars`.

**A7** — Use `serial: 3` in the playbook to process nodes in batches of 3. Use `wait_for` in a task to ensure the RKE2 service is actually listening on its port before the next batch starts.

**A8** — Use `ansible-vault encrypt_string 'my_secret_value' --name 'my_var_name'` to encrypt just that string within a plain text file.

**A9** — A **static inventory** is a hardcoded file (INI/YAML). A **dynamic inventory** is a script or plugin that queries a cloud provider (AWS/GCP) to get a real-time list of hosts.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a special task that only runs if a previous task "notifies" it (usually when a change occurs). It is triggered via the `notify` keyword.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, `forks`, and `pipelining`.

**A13** — `register` saves the output of a task into a variable. You access it via `variable_name.stdout` or `variable_name.changed`.

**A14** — `import_tasks` is static (processed when the playbook is parsed); `include_tasks` is dynamic (processed during runtime). `include_tasks` allows for conditional evaluation of the included file, whereas `import_tasks` does not.

**A15** — Galaxy is a hub for sharing roles. Use a `requirements.yml` file listing roles/collections, then run `ansible-galaxy install -r requirements.yml`.

**A16** — `ssh` is the default for Linux; `local` runs on the control node; `network_cli` is specialized for network devices (Cisco/Juniper).

**A17** — `delegate_to` runs a task on a different host; `run_once` runs a task only once per play. 
*Example*: `task: register_db_entry, delegate_to: localhost, run_once: true`.

**A18** — 
1. **Forks**: Increase `forks` in `ansible.cfg` to run more parallel processes.
2. **Pipelining**: Reduces SSH connections by sending modules via stdin.
3. **Fact Caching**: Stores facts in Redis/JSON to avoid re-gathering.
4. **Mitogen**: A plugin that replaces the execution engine for massive speedups.

**A19** — `{{ }}` is for expressions; `{% %}` is for logic/control; `{# #}` is for comments.
```jinja2
upstream nginx_backend {
{% for server in backend_servers %}
  server {{ server }}; # Health check enabled
{% endfor %}
}
```

**A20** — 
1. Set `serial: 1` (or small batch).
2. **Pre-task**: Remove server from Load Balancer.
3. **Task**: Update application code.
4. **Health Check**: Use `uri` module to verify the app is up.
5. **Post-task**: Re-add to Load Balancer.
6. **Rollback**: Wrap in a `block`, and in the `rescue` section, revert the code and re-add to LB.
