## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service) provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS** (Platform as a Service) provides a framework for developers to build/deploy apps without managing underlying OS (e.g., AWS Elastic Beanstalk). **SaaS** (Software as a Service) provides a complete software product managed by the provider (e.g., Microsoft 365).

**CL2** — In **IaaS**, the provider manages the physical hardware/virtualization; you manage the OS, middleware, and apps. In **managed Kubernetes**, the provider manages the Control Plane; you manage worker nodes and workloads. In **SaaS**, the provider manages the entire stack; you only manage data and user access.

**CL3** — A **VPC** is your private network; a **subnet** is a range of IP addresses within that VPC. A **Security Group** acts as a stateful firewall at the instance level; a **NACL** is a stateless firewall at the subnet level. They layer as: VPC $\rightarrow$ Subnet $\rightarrow$ NACL $\rightarrow$ Instance $\rightarrow$ Security Group. **Stateful** (SG) remembers connection state (return traffic is auto-allowed); **Stateless** (NACL) requires explicit rules for both inbound and outbound traffic.

**CL4** — A **Landing Zone** is a pre-configured, multi-account environment. **Organizational Units (OUs)** group accounts for policy application. **Guardrails** (like AWS SCPs) enforce compliance. **Shared Networking** (Transit Gateway/Hub-and-Spoke) centralizes connectivity. A **single-account approach** is problematic due to a massive blast radius, difficulty in billing attribution, and hitting service limits.

**CL5** — **IaC** manages infrastructure via code. **Terraform/OpenTofu** is provider-agnostic (HCL). **Pulumi** uses general-purpose languages (Python, TS). **CloudFormation/Bicep** are cloud-native (AWS/Azure specific). **Crossplane** treats cloud resources as Kubernetes objects. Choose Terraform for multi-cloud, Pulumi for developer experience, CloudFormation for deep AWS integration, and Crossplane for K8s-native orchestration.

**CL6** — **HPA** scales pods based on CPU/RAM. **VPA** adjusts pod resource requests/limits. **Cluster Autoscaler** adds/removes nodes. **KEDA** scales based on external events (e.g., Kafka lag). Use **KEDA** when scaling depends on non-resource metrics like queue depth or message rates.

**CL7** — **RPO** (Recovery Point Objective) is max data loss; **RTO** (Recovery Time Objective) is max downtime. **Active-Active** (both regions live, zero downtime) vs. **Active-Passive** (failover required). **Sync replication** (no data loss, high latency) vs. **Async** (low latency, potential data loss). **Pilot Light** (only DB is live), **Warm Standby** (scaled-down version live), and **Multi-site Active-Active** (full capacity in both).

**CL8** — **GitOps** uses Git as the single source of truth for desired state. **ArgoCD** is K8s-native and pulls from Git; **FluxCD** is lightweight and more Git-centric. **Secrets** are handled via **Sealed Secrets** (encrypted in Git), **External Secrets Operator** (syncs from Vault), or **Vault** (direct integration). **Drift** is corrected by the GitOps controller automatically reconciling the cluster to match Git.

**CL9** — Use a **StatefulSet** for stable network IDs and ordered deployment. Use **PV/PVCs** with a **Local Persistent Volume** storage class for low latency. A **Headless Service** provides direct pod IP discovery. **Init containers** handle filesystem setup. **ConfigMaps** are mounted as volumes to specific paths. **Pod Disruption Budgets (PDB)** ensure minimum availability during maintenance.

**CL10** — A **Service Account** is a K8s identity. **Workload Identity/IRSA** maps a K8s Service Account to a Cloud IAM Role. **Mounting long-lived credentials** (JSON keys) in pods is bad because they can be stolen. **Workload Identity Federation** uses OIDC to exchange a K8s token for a short-lived cloud token, eliminating the need for static keys.

**CL11** — **Object Storage** (S3/Blob) is for unstructured data (cheap, high durability). **Block Storage** (EBS/Managed Disk) is for OS/Databases (high performance, low latency). **File Storage** (EFS/Azure Files) is for shared access (NFS/SMB). Object has highest durability; Block has highest performance.

**CL12** — **Zero-Trust** assumes no implicit trust. Use **Network Policies** (L3/4 isolation), **Service Mesh** (mTLS for L7 identity), **Pod Identity** (least privilege), **Admission Controllers** (policy enforcement), **Image Signing** (provenance), and **Falco** (runtime detection). This differs from **Perimeter security**, which trusts everything inside the network.

**CL13** — A **CDN** caches content at edge locations closer to users. Services: **AWS CloudFront**, **Azure Front Door**. Use a CDN to reduce latency, offload origin server load, and protect against DDoS. Use it when serving static assets (images, JS) or globally distributed users.

**CL14** — A **Region** is a geographic area; an **Availability Zone (AZ)** is one or more discrete data centers within a region. Deploy across multiple AZs for high availability. **Zonal resources** live in one AZ; **Regional resources** (like S3) are distributed across the whole region.

**CL15** — **Managed Databases** (RDS/Cloud SQL) handle patching, backups, high availability, and scaling. On a **VM**, you are responsible for OS updates, DB installation, backups, and manual failover.

**CL16** — **IAM Users** (individuals), **Groups** (collections of users), **Roles** (temporary identities), and **Policies** (permission definitions). **Least Privilege** means granting only the minimum permissions required for a task, applied via granular IAM policies.

**CL17** — **Serverless** is event-driven compute (Lambda/Functions). **Cold starts** are the latency incurred when a function is invoked after being idle. Serverless is a poor fit for long-running processes, high-performance computing, or highly stateful apps.

**CL18** — **Ingress** is the standard K8s API; **Gateway API** is the modern, role-oriented successor. **Cloud LB Annotations** trigger cloud-specific LBs. **Service Mesh Gateways** handle mTLS/L7. **TLS termination** can happen at the LB, Ingress Controller, or Mesh sidecar. Use **Gateway API** for better separation of concerns (Infrastructure vs. App teams).

**CL19** — Use **Reserved Instances/Savings Plans** for predictable workloads and **Spot Instances** for fault-tolerant/batch jobs. **Right-size** instances to match actual usage. Use **S3 Intelligent-Tiering** for automated storage cost savings. Implement **FinOps** to track costs via **Showback** (reporting costs to teams) or **Chargeback** (billing teams directly).

**CL20** — Use **Kubernetes** and **Terraform** as abstraction layers to minimize lock-in. Use **Identity Federation** to bridge AWS/Azure IAM. **Multi-cloud** is justified for high availability/compliance but adds massive complexity in networking (VPN/Interconnect) and operational overhead.

## OT Infrastructure Architecture

**OT1** — The **Purdue Model** segments industrial networks. **Level 0**: Physical process (sensors/actuators). **Level 1**: Basic Control (PLCs). **Level 2**: Supervisory Control (HMIs/SCADA). **Level 3**: Site Operations (Historians). **Level 4/5**: Business/Enterprise (IT).

**OT2** — **IT** focuses on Data Confidentiality; **OT** focuses on Process Availability/Safety. You cannot patch OT systems like IT because patches can cause unexpected reboots or timing issues, potentially leading to physical damage or safety risks.

**OT3** — An **IDMZ** acts as a buffer between IT (L4) and OT (L3). Only specific, inspected traffic (e.g., data from Historian to Enterprise) should cross. Direct L4 $\rightarrow$ L1 connectivity is dangerous as it bypasses all control layers, allowing an attacker to manipulate physical processes directly.

**OT4** — 1. **Modbus TCP** (L1/L2), 2. **OPC UA** (L2/L3), 3. **EtherNet/IP** (L1/L2), 4. **PROFINET** (L1/L2), 5. **MQTT** (L3/Cloud).

**OT5** — A **Data Diode** is a hardware device allowing only one-way physical data flow (unidirectional). A **Firewall** is software-based and bidirectional. A diode is more secure because it is physically impossible to send data back, but it lacks the flexibility of a firewall.

**OT6** — Flow: **Sensor $\rightarrow$ PLC $\rightarrow$ OPC UA Server $\rightarrow$ MQTT Broker $\rightarrow$ Edge Gateway $\rightarrow$ Cloud**. Security boundaries should be placed at the **IDMZ** and the **Edge Gateway** to ensure no direct IT-to-OT connection.

**OT7** — **IEC 62443** defines **Zones** (logical groupings of assets with similar security needs) and **Conduits** (the communication paths between zones). A model would include: Corporate (Zone 1), Engineering (Zone 2), SCADA (Zone 3), PLCs (Zone 4), and SIS (Zone 5 - most isolated).

**OT8** — Implement **VLANs** for segmentation, place **Firewalls** between levels, and use **Jump Hosts** for remote access. Transition without downtime by using **Parallel Monitoring** (tapping traffic) to validate the new design before enforcing it via active blocking.

**OT9** — **SIS** is an independent layer designed to prevent catastrophic failure; **BPCS** controls the process. **IEC 61511** is the safety standard. SIS must be isolated because if ransomware hits the SIS, it could disable safety shutdowns during a physical emergency.

**OT10** — **PLC** (local logic), **DCS** (plant-wide integrated control), **SCADA** (wide-area monitoring). They can coexist: PLCs act as field devices for a DCS or SCADA system.

**OT11** — Use **Jump Hosts** with **MFA**, **Session Recording**, and **Time-limited access**. Direct RDP from corporate to an HMI is unacceptable as it provides a direct path for lateral movement from IT to OT.

**OT12** — **Detection**: Use OT-specific IDS. **Response**: Isolate the compromised segment, coordinate with the control room to ensure safe manual operation, and perform forensic analysis. The **Plant Operator**'s role is to maintain process safety and stability during the incident.

**OT13** — An **HMI** provides a visual interface for operators to monitor/control the process. An **Engineering Workstation** is used for programming PLCs and configuring the system.

**OT14** — A **Historian** records time-series process data. A **Plant Historian (L3)** is for real-time operational visibility; an **Enterprise Historian (L4)** is for long-term business analytics.

**OT15** — **Ladder Logic** is a graphical programming language for PLCs. It remains dominant because it mimics electrical relay diagrams, making it intuitive for electricians and engineers.

**OT16** — An **RTU** (Remote Terminal Unit) is used for long-distance, low-power, or remote telemetry (e.g., pipelines). A **PLC** is used for high-speed, local, discrete control.

**OT17** — **Analog** (continuous, e.g., 4-20mA) vs. **Digital** (on/off). **4-20mA** is preferred because a reading of 0mA immediately indicates a "wire break" fault, whereas 0-20mA cannot distinguish between a zero reading and a broken wire.

**OT18** — **Asset Inventory** is the foundation of security. Use **Passive Monitoring** (sniffing traffic) to be safe. **Active Scanning** (sending probes) is dangerous because it can crash sensitive, older OT devices.

**OT19** — **MITRE ATT&CK for ICS** focuses on physical impact. Tactics: **Inhibit Response Function**, **Impair Process Control**, **Impair Safety Instrumented System**, **Unauthorized Command Message**, **Module Firmware**. It differs from Enterprise ATT&CK by focusing on the physical process rather than just data theft.

**OT20** — Use **Passive Log Collection** to avoid impacting real-time ops. Integrate with a **SIEM** with **OT-specific rules**. Staffing requires a hybrid of **IT Analysts** (threat hunting) and **OT Engineers** (process context). An unauthorized PLC firmware change should trigger an immediate high-priority alert for manual verification.
