## Application Architecture

**AA1** — A **monolith** is a single, unified unit where all components share memory and resources. **Microservices** are a collection of small, independent services communicating over a network. 
*Problems introduced:* 1. Network latency/overhead. 2. Distributed complexity (tracing/debugging). 3. Data consistency challenges (distributed transactions).

**AA2** — **Synchronous** communication requires the caller to wait for a response (e.g., REST/HTTP). **Asynchronous** communication allows the caller to continue immediately, receiving a response later (e.g., RabbitMQ/Message Queues).

**AA3** — An **API Gateway** provides application-level logic (auth, rate limiting, request transformation, routing). A **reverse proxy** primarily handles traffic routing and load balancing (L4/L7). An API Gateway cannot entirely replace a reverse proxy if the proxy is used for low-level L4 load balancing or specialized SSL termination without application awareness.

**AA4** — The **Saga pattern** manages distributed transactions by breaking them into a sequence of local transactions. 
*   **Choreography:** Each service produces/listens to events; no central controller. Best for simple workflows.
*   **Orchestration:** A central "orchestrator" tells each service what to do. Best for complex, long-running workflows.

**AA5** — **CQRS** separates read (Query) and write (Command) models. It is often paired with **Event Sourcing** (storing state as a sequence of events). This solves the problem of mismatched scaling/performance requirements between reads and writes in traditional CRUD models.

**AA6** — The **Circuit Breaker** prevents cascading failures. 
*   **States:** Closed (normal), Open (failing, calls blocked), Half-Open (testing recovery). 
*   **Difference:** A **retry with backoff** handles transient, short-lived errors. A **circuit breaker** handles systemic, long-lived failures. You use them together: retry for a few attempts, then trip the breaker if the error persists.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost/complexity; highest noisy-neighbor risk; lowest security (isolation is logical).
2. **Shared DB/Separate Schema:** Medium cost/complexity; medium security; medium noisy-neighbor risk.
3. **Separate DB:** Highest cost/complexity; highest security; lowest noisy-neighbor risk.

**AA8** — **Strong consistency** ensures all nodes see the same data simultaneously; **eventual consistency** allows temporary divergence. For inventory, use **strong consistency**. 
*Architecture:* A distributed SQL database (e.g., CockroachDB) using the **Raft/Paxos** consensus algorithm to ensure atomic updates and prevent overselling.

**AA9** — A **sidecar proxy** (like Envoy) runs alongside the application container to handle networking. In **Istio**, Envoy is the **data plane** (handles traffic), while Istio's control plane manages the configuration. **mTLS** between sidecars provides identity-based encryption and authentication, which application-level TLS lacks because it doesn't inherently verify service identity at the infrastructure layer.

**AA10** — The **Strangler Fig** pattern involves wrapping a legacy system with a proxy and incrementally replacing functionality. 
*Strategy:* 1. Place an API Gateway in front of the .NET monolith. 2. Build a new feature in .NET 8. 3. Route traffic for that specific feature to the new service via the Gateway. 4. Repeat until the monolith is "strangled" and can be decommissioned.

**AA11** — The **12-Factor App** ensures cloud-native readiness. 
*Factors:* 1. **Codebase** (one repo), 2. **Dependencies** (explicitly declared), 3. **Config** (stored in environment), 4. **Backing services** (treated as attached resources), 5. **Disposability** (fast startup/shutdown), 6. **Concurrency** (scale via process model).

**AA12** — 
*   **Kafka (Event-driven):** High throughput, decoupled, complex debugging, high ordering guarantees (via partitions), handles failures via replayability.
*   **REST (Request-driven):** Low latency, tight coupling, easy debugging, no inherent ordering, failures require immediate retry/handling.
*   *Choice:* Use Kafka for stream processing/asynchronous workflows; REST for real-time user interactions.

**AA13** — A **load balancer** distributes incoming network traffic across multiple servers. **Layer 4** works at the transport level (IP/Port). **Layer 7** works at the application level (HTTP/URL). 
*Use case:* Layer 7 is required for **path-based routing** (e.g., sending `/api` to one service and `/static` to another).

**AA14** — A **message queue** (RabbitMQ) is designed for transient task distribution (messages are deleted after consumption). A **log-based broker** (Kafka) is a persistent, append-only log where messages can be replayed. 
*Choice:* Use RabbitMQ for complex routing/task queues; Kafka for high-throughput stream processing and event sourcing.

**AA15** — A **container** virtualizes the Operating System (shares the host kernel), whereas a **VM** virtualizes the hardware (includes a full guest OS). Containers are popular because they are lightweight, start instantly, and provide high density for microservices.

**AA16** — **Stateless** services hold no client data between requests (e.g., a pure math API). **Stateful** services persist data (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — An **ORM** maps database tables to programming objects. 
*Examples:* Hibernate (Java), Entity Framework (.NET). 
*Trade-offs:* ORMs increase development speed but can introduce performance overhead and "N+1" query problems compared to raw SQL.

**AA18** — The **Bulkhead pattern** isolates resources to prevent a single failure from taking down the whole system. 
*Implementation:* Use separate **thread pools** for different service calls or deploy services into **separate hardware/clusters** so a memory leak in one doesn't starve the others.

**AA19** — **OT** relies on a central server to resolve conflicts; **CRDTs** use mathematical properties to allow local updates that converge automatically. 
*Choice:* **CRDTs** are better for offline editing because they are designed for peer-to-peer/asynchronous synchronization without a central authority.

**AA20** — Challenges include maintaining context across different languages and protocols. 
*Context:* Use **W3C Trace Context** or **B3** headers. 
*Sampling:* **Head-based** (decide at start) vs **Tail-based** (decide after seeing the whole trace). 
*Kafka:* Ensure the trace ID is injected into the **Kafka message headers** to maintain continuity.

## On-Premise Infrastructure Architecture

**OP1** — **Type 1** runs directly on hardware (e.g., VMware ESXi, Xen). **Type 2** runs on top of an OS (e.g., VirtualBox, VMware Workstation).

**OP2** — **SAN** (Storage Area Network) provides block-level storage (Fibre Channel, iSCSI) for high-performance databases. **NAS** (Network Attached Storage) provides file-level storage (NFS, SMB) for shared files.

**OP3** — **3-tier** (Core/Dist/Access) can create bottlenecks in East-West traffic. **Leaf-Spine** is a two-tier architecture where every leaf connects to every spine, providing predictable latency and massive horizontal scalability for data center traffic.

**OP4** — A HA Proxmox cluster needs 3+ nodes for **quorum**. Use **Ceph** for distributed shared storage. If a node fails, **fencing** (STONITH) ensures the failed node is truly isolated to prevent data corruption.

**OP5** — **VLAN trunking** allows multiple VLANs over one link using **802.1Q** tags. On Linux, you configure this by creating **sub-interfaces** (e.g., `eth0.10`, `eth0.20`) for each VLAN ID.

**OP6** — RAID 1 (Mirror), 5 (Parity, 1 drive loss), 6 (Double parity, 2 loss), 10 (Mirror+Striping), Z2 (ZFS double parity). 
*Choice:* For a database, **RAID 10** is best as it balances high performance (striping) with high fault tolerance (mirroring).

**OP7** — Use **Split-horizon DNS** (different records for internal vs external). **Recursive resolvers** handle client queries; **Authoritative servers** hold the truth. **Conditional forwarding** directs specific domains to specific servers. A laptop moving to VPN would switch to the internal DNS via the VPN tunnel.

**OP8** — **Root CA** (offline/highly secure) $\rightarrow$ **Subordinate CA** (issues certs) $\rightarrow$ **End-entity**. **CRL/OCSP** handle revocation. 
*Compromise:* A compromised Subordinate CA can be revoked; a compromised Root CA requires rebuilding the entire PKI from scratch.

**OP9** — **MPLS** (Reliable/Expensive), **IPsec** (Cheap/Internet), **SD-WAN** (Flexible/Hybrid), **WireGuard** (Fast/Modern). 
*Recommendation:* **SD-WAN** for 50 users/site with VoIP, as it can intelligently route latency-sensitive traffic over the best available path.

**OP10** — **iDRAC/iLO/IPMI** provide out-of-band management (accessing the server even if the OS is dead). If exposed to the internet, an attacker gains full control of the hardware.

**OP11** — **LVM** is standard volume management. **LVM-Thin** allows over-provisioning via thin provisioning. **ZFS** provides advanced features like snapshots and data integrity via Copy-on-Write.

**OP12** — A **stretch cluster** requires low latency between sites. In Ceph, use **CRUSH rules** to ensure data replicas are in different sites. A 2-site setup is risky due to **split-brain**; a 3rd site (witness) is needed for quorum.

**OP13** — **DORA**: Discover, Offer, Request, Acknowledge. If the server is unavailable, the client keeps its lease until expiration, then loses connectivity.

**OP14** — **Managed switches** support VLANs, SNMP, and Spanning Tree; **unmanaged** are plug-and-play. Managed switches are essential for enterprise security and segmentation.

**OP15** — **NTP** synchronizes clocks. Clock drift causes authentication failures (Kerberos), log correlation errors, and database consistency issues in clusters.

**OP16** — **Physical** (Hardware), **VM** (Virtual Hardware), **Container** (OS abstraction). Use **bare metal** for workloads requiring direct hardware access (e.g., high-perf GPU/NVMe) or extreme low latency.

**OP17** — **UPS** provides short-term battery power; **Generator** provides long-term power. An **ATS** automatically switches the load between the two.

**OP18** — **Active-Passive** (one standby); **Active-Active** (both load-balanced). For PostgreSQL HA: Use **Pacemaker/Corosync** to manage a **Virtual IP**. If a node fails, **STONITH** (fencing) kills the old node to prevent it from writing to the DB simultaneously.

**OP19** — **3-2-1 Rule**: 3 copies, 2 media types, 1 offsite. **RPO** (max data loss), **RTO** (max downtime). **Backup** is the data; **Disaster Recovery** is the plan to restore service. Use **immutable backups** to prevent ransomware from deleting them.

**OP20** — **802.1X** involves a **Supplicant** (client), **Authenticator** (switch), and **Auth Server** (RADIUS). **EAP-TLS** uses certificates; **PEAP** uses passwords. **MAB** allows non-802.1X devices (like printers) to connect based on their MAC address.
