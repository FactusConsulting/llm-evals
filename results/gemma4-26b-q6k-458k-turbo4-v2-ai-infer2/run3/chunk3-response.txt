## OpenTofu / Terraform

**T1** — `tofu plan` generates an execution plan, showing what changes will be made without applying them. `tofu apply` executes those changes to reach the desired state.

**T2** — State is a JSON file mapping your configuration to real-world resources. Remote state is critical for team collaboration, providing a single source of truth and enabling state locking to prevent concurrent modifications.

**T3** — `count` uses an integer index (e.g., `[0, 1, 2]`), making it fragile if items are removed from the middle. `for_each` uses a map or set of keys, making it stable because resources are identified by unique keys rather than indices. `for_each` is preferred for collections of varying items.

**T4** — This is "drift." During the next `tofu plan`, OpenTofu refreshes the state by querying the cloud API. It detects the discrepancy between the actual state and the configuration, then proposes an update to reconcile them.

**T5**
```hcl
resource "example_vm" "web" {
  for_each = toset(["web1", "web2", "web3"])
  name     = each.key
}
```

**T6** — `terraform_remote_state` creates tight coupling between modules and requires access to the entire state file (security risk). The recommended alternative is using **outputs** from one module passed as **inputs** to another, or using shared data sources.

**T7** — The `null_resource` finishes its execution, but the output is calculated before the provisioner's side-effects (like writing a file) are fully realized or visible to the provider. Fix: Use `depends_on` to ensure the resource providing the output waits for the `null_resource` to complete, or use a `local_file` resource instead of a provisioner.

**T8** — `tofu import` brings existing infrastructure under management. Its limitation is that it only updates state, not code. The `import` block (1.5+) is declarative; you define the resource in code and the block, allowing for a more seamless, repeatable transition.

**T9** — A **variable** is an input to a module (parameter). An **output** is a value returned by a module (return value).

**T10** — A provider is a plugin that allows OpenTofu to interact with specific APIs (AWS, Azure, etc.). If you run `plan` without `init`, OpenTofu will fail because it hasn't downloaded the necessary provider binaries.

**T11** — It is the dependency lock file. It should be committed to ensure every environment (CI, local, production) uses the exact same provider versions and checksums, preventing "it works on my machine" issues.

**T12** — `tofu destroy` removes all managed resources. To target one: `tofu destroy -target=resource_type.resource_name`.

**T13** — A data source is a read-only operation to fetch information from an existing resource. Example: `data "aws_ami" "latest"` to find the newest Amazon Linux ID.

**T14** — **Variables** are external inputs provided by the user. **Locals** are internal, derived values used for logic within the module. Use locals to avoid repeating complex expressions or to transform input variables.

**T15** — 
- `create_before_destroy`: Creates the new resource before deleting the old one (prevents downtime).
- `prevent_destroy`: Stops accidental deletion of critical resources.
- `ignore_changes`: Tells OpenTofu to ignore specific attribute updates (useful for auto-scaling or external tags).

**T16** — A `moved` block allows you to rename a resource or move it into a module in your code without OpenTofu thinking it needs to destroy the old one and create a new one. It updates the state mapping instead.

**T17** — The dependency graph is a DAG (Directed Acyclic Graph). **Implicit** dependencies occur when one resource references an attribute of another. **Explicit** dependencies use `depends_on`. `depends_on` forces a specific order but breaks parallelism, so use it only when implicit dependencies aren't detectable.

**T18** — 
1. **State Splitting**: Break large states into smaller ones (reduces refresh time).
2. **`-refresh=false`**: Skips API calls (faster, but risks drift).
3. **Targeting**: Use `-target` for specific fixes (not a long-term strategy).
4. **Backend Optimization**: Use a high-performance backend (S3/DynamoDB) to reduce latency.

**T19** — State locking prevents two users from running `apply` simultaneously. If a CI crashes, the lock remains. You fix it with `tofu force-unlock <LOCK_ID>`. **Risk**: If you unlock while another process is actually writing, you will corrupt the state file.

**T20** — 
1. Write the new backend configuration in your `.tf` files.
2. Run `tofu init -migrate-state`.
3. OpenTofu will detect the local state and ask to copy it to the new S3 bucket.
4. Verify by running `tofu plan` to ensure no unexpected changes are proposed and checking the S3 bucket for the `.tfstate` file.

## Ansible

**A1** — A **Playbook** is the orchestration file (the "what"); a **Role** is a reusable collection of tasks/vars/files (the "package"); a **Task** is a single action (the "step").

**A2** — `ansible_facts` is a dictionary of system info. Access OS family via `ansible_facts['os_family']`.

**A3** — `command` (no shell features/pipes), `shell` (runs through `/bin/sh`, supports pipes/redirects), `raw` (runs via SSH directly, bypasses Python). Use `command` for safety, `shell` for complexity, `raw` for bootstrapping Python.

**A4** — Idempotency means running a task multiple times results in the same state. 
- **Idempotent**: `apt: name=nginx state=present`.
- **NOT Idempotent**: `shell: echo "hello" >> /tmp/file`.

**A5**
```yaml
- name: Install htop
  package:
    name: htop
    state: present
  when: ansible_os_family == "Debian"

- name: Install epel and htop on RedHat
  yum:
    name: [epel-release, htop]
    state: present
  when: ansible_os_family == "RedHat"
```

**A6** — Order (highest to lowest): `extra_vars` > `set_fact` > `host_vars` > `group_vars` > `role defaults`.

**A7** — Use `serial: 3` in the playbook to process in batches of 3. To ensure the *first* 3 are special, you might use two plays or a specific inventory group. Use `wait_for` to ensure a port is open before proceeding.

**A8** — Use `ansible-vault encrypt_string 'my_secret_value'` and paste the resulting block into your vars file.

**A9** — **Static**: A hardcoded file (INI/YAML). **Dynamic**: A script or plugin that queries an API (AWS/GCP) to generate the host list at runtime.

**A10** — `ansible webservers -m shell -a "df -h"`

**A11** — A **handler** is a special task that only runs if a previous task reported a `changed` status. You trigger it using the `notify` keyword in a task.

**A12** — `ansible.cfg` configures Ansible behavior. Common settings: `inventory`, `remote_user`, `forks`.

**A13** — `register` captures the output of a task. 
```yaml
- shell: uptime
  register: uptime_output
- debug: msg="{{ uptime_output.stdout }}"
```

**A14** — `import_tasks` is static (processed when the playbook is parsed). `include_tasks` is dynamic (processed when the execution reaches that line). `include_tasks` allows for conditional evaluation at runtime.

**A15** — Galaxy is a hub for roles/collections. Use `ansible-galaxy install -r requirements.yml` to install them.

**A16** — `ssh` (standard), `local` (runs on control node), `network_cli` (specialized for network gear). Use `local` for management tasks and `network_cli` for routers/switches.

**A17** — `delegate_to` runs a task on a different host; `run_once` runs it once per play. 
Example: `delegate_to: localhost`, `run_once: true` to fetch a token from a remote host and use it locally.

**A18** — 
1. `forks`: Increase parallel processes (tradeoff: higher CPU/RAM on control node).
2. `pipelining`: Reduces SSH connections (tradeoff: requires `requiretty` disabled).
3. `fact caching`: Speeds up subsequent runs (tradeoff: stale data risk).
4. `Mitogen`: Highly optimized SSH plugin (tradeoff: complexity/installation).

**A19** — `{{ }}` (expression), `{% %}` (logic/control), `{# #}` (comment).
```jinja2
upstream nginx_backend {
{% for server in backend_servers %}
    server {{ server.ip }}:80 {% if server.healthy %}# healthy {% endif %}
{% endfor %}
}
```

**A20** — 
1. `serial: 1` (one by one).
2. `pre_tasks`: Remove server from Load Balancer.
3. `tasks`: Deploy app.
4. `post_tasks`: `uri` module to check health; if OK, add back to LB.
5. `block/rescue`: If deployment fails, `rescue` runs a rollback (re-installs old version).
