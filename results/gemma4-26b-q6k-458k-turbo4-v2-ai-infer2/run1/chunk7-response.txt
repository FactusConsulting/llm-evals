## Application Architecture

**AA1** — Monolith is a single, unified deployment unit. Microservices are a collection of small, independent, loosely coupled services. 
Problems introduced: 1. Network latency (inter-service calls), 2. Data consistency (distributed transactions), 3. Operational complexity (deployment/monitoring overhead).

**AA2** — Synchronous: The caller waits for a response (e.g., HTTP/REST). Asynchronous: The caller sends a message and continues (e.g., RabbitMQ/AMQP).

**AA3** — An API Gateway provides application-level logic (auth, rate limiting, orchestration), while a reverse proxy primarily handles routing and SSL termination. An API Gateway can replace a reverse proxy, but it is often used in conjunction with one to separate concerns.

**AA4** — Saga manages distributed transactions via a sequence of local transactions. 
*Choreography:* Each service produces/listens to events (decentralized). Best for simple workflows. 
*Orchestration:* A central coordinator tells services what to do. Best for complex, high-visibility workflows.

**AA5** — CQRS separates read (Query) and write (Command) models. It is paired with Event Sourcing to reconstruct state from a stream of events. This solves the problem of "impedance mismatch" where a single model cannot efficiently handle both complex writes and high-performance reads.

**AA6** — States: Closed (normal), Open (failing), Half-Open (testing recovery). 
Difference: A retry handles transient blips; a Circuit Breaker stops the bleeding during systemic failure. Use together: Retry for a single failed request, but wrap it in a Circuit Breaker to prevent cascading failure.

**AA7** — 
1. **Shared DB/Schema:** Lowest cost, lowest security (data leakage risk), highest noisy-neighbor risk.
2. **Shared DB/Separate Schema:** Medium cost/complexity, better isolation, medium noisy-neighbor risk.
3. **Separate DB:** Highest cost, highest security, lowest noisy-neighbor risk.

**AA8** — Strong consistency is required. Use an RDBMS (e.g., PostgreSQL) with ACID compliance or a distributed consensus store (e.g., Etcd/Zookeeper) using the Raft protocol to ensure all nodes agree on inventory counts before confirming a sale.

**AA9** — A sidecar is a helper process running alongside a service. In Istio, Envoy is the sidecar (Data Plane) that intercepts traffic, while the Control Plane (Istiod) manages configuration. mTLS between sidecars ensures identity and encryption without requiring the application to manage certificates.

**AA10** — Use the Strangler Fig pattern: Place a proxy/gateway in front of the monolith. New features are built in .NET 8. Existing features are migrated one by one. Once a feature is moved, the proxy routes traffic to the new service instead of the monolith.

**AA11** — 12-Factor methodology ensures cloud-native readiness. 
Factors: 1. Codebase (one repo per app), 2. Dependencies (explicitly declared), 3. Config (stored in environment), 4. Backing services (treated as attached resources), 5. Build/Release/Run (strict separation), 6. Processes (stateless). These ensure portability, scalability, and automation.

**AA12** — 
*   **Kafka (Event-driven):** High decoupling, high scalability, complex debugging, high ordering guarantees (per partition), excellent failure handling (replayable).
*   **REST (Request-driven):** Tight coupling, lower scalability, easy debugging, no ordering guarantees, harder failure handling.
*   **Choice:** Use Kafka for high-throughput, asynchronous workflows; use REST for immediate, synchronous user interactions.

**AA13** — A load balancer distributes traffic across multiple servers. 
*L4:* Operates at Transport layer (IP/Port). 
*L7:* Operates at Application layer (HTTP/Headers). 
*Use case:* L7 is required for path-based routing (e.g., `/api` goes to Service A, `/images` goes to Service B).

**AA14** — A Message Queue (RabbitMQ) is for transient task distribution (message is deleted after consumption). A Log-based Broker (Kafka) is a persistent append-only log (messages can be replayed). Pick RabbitMQ for complex routing/tasking; pick Kafka for high-throughput stream processing.

**AA15** — A container shares the host OS kernel, making it lightweight and fast to start. A VM includes a full guest OS, making it heavy. Containers are popular because they offer high density and rapid deployment.

**AA16** — Stateless: No local data (e.g., a calculator service). Stateful: Maintains context (e.g., a database). Stateless services scale horizontally easily because any instance can handle any request.

**AA17** — ORM maps objects to database tables. Examples: Hibernate (Java), Entity Framework (.NET). 
*Trade-offs:* ORMs increase development speed but can introduce performance overhead and "N+1" query problems; raw SQL offers maximum control and performance.

**AA18** — Bulkhead isolates resources to prevent one failure from taking down the whole system. Implementation: Use separate thread pools for different service calls or deploy critical services in dedicated, isolated hardware/clusters.

**AA19** — OT requires a central server to resolve conflicts (complex). CRDTs use mathematical properties to ensure convergence without a central authority (simpler for P2P). For offline editing, **CRDTs** are superior because they allow local updates that merge seamlessly upon reconnection without a central coordinator.

**AA20** — Challenges: Context propagation (passing TraceID/SpanID via headers like W3C Trace Context). 
*Sampling:* Head-based (decide at start) vs Tail-based (decide after seeing full trace). 
*Kafka:* Ensure continuity by injecting trace headers into the Kafka message headers so the consumer can continue the trace.

## On-Premise Infrastructure Architecture

**OP1** — Type 1: Runs directly on hardware (e.g., ESXi, Xen). Type 2: Runs on an OS (e.g., VirtualBox, VMware Workstation).

**OP2** — SAN (Storage Area Network): Block-level storage (Fibre Channel, iSCSI). Used for databases/VM disks. NAS (Network Attached Storage): File-level storage (NFS, SMB). Used for shared files/folders.

**OP3** — 3-tier: Core, Distribution, Access. Leaf-Spine: A two-tier architecture where every leaf connects to every spine. It solves the "east-west" traffic bottleneck in modern DCs by providing predictable, low-latency paths between servers.

**OP4** — 3+ nodes for quorum. Use Ceph or iSCSI for shared storage. Use a fencing agent (STONITH) to isolate failed nodes. During failure, the cluster loses quorum if a majority isn't met; if quorum is maintained, the remaining nodes fence the failed node and restart its VMs.

**OP5** — 802.1Q allows multiple VLANs on one link via tagging. On Linux, configure sub-interfaces (e.g., `eth0.10`, `eth0.20`) to handle different VLAN tags on a single physical NIC.

**OP6** — 1 (Mirror), 5 (Parity), 6 (Double Parity), 10 (Mirror+Stripe), Z2 (ZFS parity). For a database: **RAID 10** is best as it provides high performance (striping) and high fault tolerance (mirroring).

**OP7** — Use Split-horizon DNS to serve different IPs for internal vs external queries. Use Recursive resolvers for clients, Authoritative for your zones. Use DNSSEC to sign zones. When a laptop moves to VPN, the VPN gateway directs it to the internal DNS/Recursive resolver.

**OP8** — Root CA (Offline/Master) $\rightarrow$ Subordinate CA (Issuing) $\rightarrow$ End-entity. CRL/OCSP checks revocation. A compromised Subordinate CA affects only its issued certs; a compromised Root CA invalidates the entire PKI.

**OP9** — MPLS (Expensive/Reliable), IPsec (Cheap/Internet), SD-WAN (Flexible/Managed), WireGuard (Fast/Mesh). For 50 users/site with VoIP, **SD-WAN** is recommended for its ability to prioritize traffic and manage multiple paths.

**OP10** — Out-of-band management (iDRAC/iLO) allows access even if the OS is crashed. If exposed to the internet, attackers can gain full hardware control, bypass OS security, and wipe the server.

**OP11** — LVM: Traditional block management. LVM-Thin: Space-efficient, thin-provisioned. ZFS: Combined filesystem/volume manager with advanced snapshots/integrity. LVM-Thin is best for high-density VMs; ZFS is best for data integrity.

**OP12** — Use a 3-site setup or a 2-site setup with a "witness" node in a 3rd location to prevent split-brain. Ceph requires low latency (<10ms). 2-site Ceph is risky because if the link breaks, both sides might try to claim ownership (split-brain).

**OP13** — DORA: Discover, Offer, Request, Acknowledge. If the server is down, the client uses an APIPA address (169.254.x.x).

**OP14** — Managed switches allow VLANs, Spanning Tree, and SNMP. Unmanaged are "plug-and-play." Managed switches are essential for security and traffic control in enterprises.

**OP15** — NTP synchronizes clocks. Drift causes authentication failures (Kerberos), log correlation issues, and database transaction errors.

**OP16** — Physical (Hardware), VM (OS-level virtualization), Container (Process-level). Run on bare metal for high-performance/low-latency workloads (e.g., high-frequency trading or massive databases).

**OP17** — UPS provides short-term battery power; Generator provides long-term power. An ATS automatically switches the load to the generator when utility power fails.

**OP18** — Active-Passive (Standby) vs Active-Active (Both running). For PostgreSQL HA: Use Pacemaker/Corosync to manage a Virtual IP (VIP). If the primary fails, Corosync detects it, STONITH fences the old node, and the VIP moves to the standby.

**OP19** — 3-2-1: 3 copies, 2 media, 1 offsite. RPO (how much data you can lose) and RTO (how long you are down). Backup is a copy of data; DR is the plan to restore service. Use immutable backups to prevent ransomware from deleting your copies.

**OP20** — Supplicant (Client), Authenticator (Switch), Auth Server (RADIUS). EAP-TLS (Cert-based) is most secure. MAB (MAC Authentication Bypass) allows non-802.1X devices (like printers) to connect based on their MAC address.
