## Cloud Infrastructure Architecture

**CL1** — **IaaS** (Infrastructure as a Service): Provides raw compute, storage, and networking (e.g., AWS EC2). **PaaS** (Platform as a Service): Provides a managed platform for deploying code (e.g., Azure App Service). **SaaS** (Software as a Service): Provides a complete software product (e.g., Microsoft 365).

**CL2** — **Shared Responsibility Model**: The provider manages the "security *of* the cloud" (hardware, global infra); the user manages "security *in* the cloud" (data, config).
* **IaaS VMs**: Provider handles physical/hypervisor; User handles OS, patching, and apps.
* **Managed Kubernetes**: Provider handles Control Plane; User handles worker nodes, pods, and network policies.
* **SaaS (M365)**: Provider handles almost everything; User handles identity, data, and access configuration.

**CL3** — **VPC**: A private logical network. **Subnet**: A range of IP addresses within a VPC. **Security Group (SG)**: Instance-level firewall (stateful). **NACL**: Subnet-level firewall (stateless). **Layering**: Traffic enters VPC $\rightarrow$ Subnet (NACL) $\rightarrow$ Instance (SG). **Stateful (SG)**: Remembers connection state (return traffic allowed automatically). **Stateless (NACL)**: Requires explicit rules for both inbound and outbound.

**CL4** — **Landing Zone**: A pre-configured, multi-account environment. **OUs (Organizational Units)**: Logical groupings of accounts (e.g., Prod vs. Dev). **Guardrails**: Service Control Policies (SCPs) that restrict actions. **Shared Networking**: Using Transit Gateway (AWS) or Hub-and-Spoke (Azure) to centralize inspection/egress. **Single-account problem**: High blast radius, difficult to manage limits, and lacks clear cost/security boundaries.

**CL5** — **IaC**: Managing infra via machine-readable files.
* **Terraform/OpenTofu**: Provider-agnostic, HCL-based, industry standard.
* **Pulumi**: Uses general-purpose languages (Python, TS); best for devs.
* **CloudFormation/Bicep**: Cloud-native (AWS/Azure); best for deep integration within one provider.
* **Crossplane**: K8s-native; treats cloud resources as K8s objects.

**CL6** — **HPA**: Scales pods based on CPU/RAM. **VPA**: Adjusts pod resource requests/limits. **Cluster Autoscaler**: Adds/removes nodes. **KEDA**: Event-driven autoscaling (e.g., scale based on Kafka lag). **KEDA vs HPA**: Use KEDA when scaling depends on external metrics (queue depth, stream lag) rather than just resource utilization.

**CL7** — **DR Strategy**:
* **RPO/RTO**: RPO (Max data loss), RTO (Max downtime).
* **Active-Active**: Both regions serve traffic (Low RTO/RPO, high cost). **Active-Passive**: One region idle (Higher RTO).
* **Replication**: Sync (No data loss, high latency) vs Async (Low latency, potential data loss).
* **DNS**: Route53/Traffic Manager for failover.
* **DR Types**: **Pilot Light** (Minimal core services running), **Warm Standby** (Scaled-down version running), **Multi-site Active-Active** (Full capacity in both).

**CL8** — **GitOps**: Using Git as the single source of truth for desired state. **ArgoCD** (K8s-native, pull-based, visual) vs **FluxCD** (Lightweight, modular, pull-based). **Secrets**: Use Sealed Secrets (encrypted in Git), External Secrets Operator (fetches from Vault), or Vault. **Drift**: The controller detects the difference between Git and the cluster and automatically overwrites the manual change to match Git.

**CL9** — **Architecture**: Use **StatefulSet** for stable network IDs/storage. Use **PV/PVC** with a **Local Persistent Volume** class for low latency. Use a **Headless Service** for direct pod addressing. Use **Init Containers** to prepare the filesystem. Mount **ConfigMaps** as volumes for specific paths. Implement **Pod Disruption Budgets** to ensure availability during maintenance.

**CL10** — **Service Account**: K8s identity. **Workload Identity**: Mapping a K8s identity to a Cloud identity. **IRSA**: AWS-specific implementation of this mapping. **Bad Practice**: Mounting long-lived IAM keys in pods is a massive security risk (leakage). **Workload Identity Federation** uses short-lived OIDC tokens to exchange K8s identity for cloud permissions.

**CL11** — **Object (S3/Blob)**: Unstructured data, highly durable, accessed via API. **Block (EBS/Managed Disk)**: Low-latency, attached to a single VM, used for OS/DBs. **File (EFS/Azure Files)**: Shared filesystem, multiple instances can mount it. **Durability**: Usually 11 nines (Object). **Availability**: Depends on replication across AZs.

**CL12** — **Zero-Trust K8s**: **Network Policies** (L3/4 isolation), **Service Mesh** (mTLS/L7), **Pod Identity** (no static keys), **Admission Controllers** (OPA/Kyverno for policy enforcement), **Image Signing** (Cosign), **Runtime Security** (Falco for anomaly detection). **Difference**: Traditional security relies on a "hard shell" perimeter; Zero-Trust assumes the network is compromised and verifies every request/identity.

**CL13** — **CDN**: A distributed network of edge servers that cache content closer to users. **Services**: AWS CloudFront, Azure Front Door. **Use Case**: Use a CDN for static assets (images, JS) to reduce latency and origin load; serve directly only for highly dynamic, non-cacheable data.

**CL14** — **Region**: Geographic area. **AZ**: One or more discrete data centers within a region. **Multi-AZ**: Protects against data center failure. **Zonal**: Tied to one AZ. **Regional**: Available across all AZs in a region.

**CL15** — **Managed DB**: Provider handles patching, backups, HA, and scaling. **User** handles schema, query optimization, and access control.

**CL16** — **IAM**: **Users** (individuals), **Groups** (collections of users), **Roles** (assumable identities), **Policies** (JSON permissions). **Least Privilege**: Granting only the minimum permissions required for a task. Apply via granular, resource-based policies.

**CL17** — **Serverless**: Event-driven compute without managing servers. **Comparison**: Lambda (AWS), Functions (Azure), GCF (Google). **Cold Starts**: Latency during initial container spin-up. **Poor fit**: Long-running processes, high-performance computing, or workloads requiring constant, predictable low latency.

**CL18** — **Ingress**: L7 routing. **Gateway API**: Next-gen, role-oriented (Infrastructure vs App dev). **LB Annotations**: Cloud-specific tweaks. **Mesh Ingress**: Handles mTLS/L7 at the mesh level. **TLS Termination**: Can happen at the LB, Ingress Controller, or Mesh. **Gateway API** is preferred for better separation of concerns and scalability.

**CL19** — **Cost Optimization**:
* **Commitment**: Reserved Instances/Savings Plans for predictable loads.
* **Spot**: Use for fault-tolerant/stateless workloads.
* **Right-sizing**: Match instance size to actual usage.
* **Tiering**: Move old data to S3 Glacier/Archive.
* **FinOps**: Implement tagging, showback (reporting costs to teams), and chargeback (billing teams). Use tools like AWS Cost Explorer or Azure Cost Management.

**CL20** — **Multi-Cloud**: Use **Kubernetes** as the abstraction layer, **Terraform** for IaC, and **Identity Federation** (OIDC) to link identities. **Networking**: VPN or Interconnect (DirectConnect/ExpressRoute). **Trade-off**: Multi-cloud increases complexity and cost significantly; it is only justified for extreme high availability or regulatory requirements, not just to "avoid lock-in."

## OT Infrastructure Architecture

**OT1** — **Purdue Model**:
* **L0**: Physical process (sensors/actuators).
* **L1**: Basic Control (PLCs/RTUs).
* **L2**: Supervisory Control (HMIs/SCADA).
* **L3**: Site Operations (Historians/MES).
* **L4**: Business Logistics (ERP/Corporate).

**OT2** — **IT vs OT**: IT focuses on Confidentiality; OT focuses on Availability and Safety. **Patching**: You cannot patch OT blindly because it may cause downtime or instability in real-time processes; patches must be tested in a lab first.

**OT3** — **IDMZ**: A buffer zone between IT and OT. **Traffic**: Only specific, proxied data (e.g., via a historian or jump host) should cross. **Direction**: IT $\rightarrow$ OT is highly restricted. **Danger**: Direct L4 $\rightarrow$ L1 connectivity allows an attacker to bypass all controls and manipulate physical processes directly.

**OT4** — 1. **Modbus TCP** (L1/L2), 2. **OPC UA** (L2/L3), 3. **EtherNet/IP** (L1/L2), 4. **PROFINET** (L1/L2), 5. **MQTT** (L3/Cloud).

**OT5** — **Data Diode**: Hardware-based, physically allows data to flow in only one direction (unhackable one-way). **Firewall**: Software-based, bidirectional, can be misconfigured or exploited. Use a diode for high-security telemetry export.

**OT6** — **Flow**: Sensor $\rightarrow$ PLC $\rightarrow$ Historian $\rightarrow$ Edge Gateway $\rightarrow$ MQTT Broker $\rightarrow$ Cloud. **Boundary**: Place the IDMZ/Firewall between the Historian (L3) and the Edge Gateway/Cloud connection.

**OT7** — **Zone**: A grouping of assets with similar security requirements. **Conduit**: A communication path between zones. **Model**: [Corp Zone] $\rightarrow$ (Conduit) $\rightarrow$ [Eng Workstation Zone] $\rightarrow$ (Conduit) $\rightarrow$ [SCADA Zone] $\rightarrow$ (Conduit) $\rightarrow$ [PLC Zone] $\rightarrow$ (Conduit) $\rightarrow$ [SIS Zone (Isolated)].

**OT8** — **Strategy**: Implement VLANs for segmentation, place firewalls between zones, use a Jump Host for remote access, and use a "Parallel Deployment" approach (monitor the new network alongside the old) to avoid downtime during transition.

**OT9** — **SIS** (Safety) vs **BPCS** (Process Control). **IEC 61511** governs functional safety. **SIS Isolation**: If an attacker reaches the SIS, they can disable safety shutdowns. **Ransomware on SIS**: Could lead to catastrophic physical failure/explosion.

**OT10** — **PLC**: Localized control. **DCS**: Plant-wide, integrated control. **SCADA**: Supervisory/monitoring. They can coexist: PLCs handle the field, DCS manages the process, SCADA provides the overview.

**OT11** — **Remote Access**: Use a Jump Host in the IDMZ, require MFA, record all sessions, and use time-limited, just-in-time access. **Direct RDP to HMI** is unacceptable as it bypasses all security layers.

**OT12** — **Response**: 1. Detect via IDS/Anomaly detection. 2. Identify affected assets. 3. Isolate the compromised segment. 4. Coordinate with the control room to ensure a safe manual shutdown if needed. **Operator Role**: The operator's priority is physical safety and process stability, not IT security.

**OT13** — **HMI**: Interface for operators to visualize and control the process. **Eng Workstation**: Used for configuring/programming PLCs/DCS.

**OT14** — **Historian**: A database for time-series process data. **L3 Historian**: Local to the plant. **L4 Historian**: Aggregated data for business analysis.

**OT15** — **Ladder Logic**: A visual programming language for PLCs. It remains dominant because it is intuitive for electricians/engineers and highly reliable for deterministic control.

**OT16** — **RTU**: Designed for remote, low-power, wide-area telemetry (e.g., pipelines). **PLC**: Designed for high-speed, local, deterministic control.

**OT17** — **Analog** (4-20mA/0-10V) vs **Digital** (On/Off). **4-20mA** is preferred because if the wire breaks, the signal goes to 0mA, allowing the system to detect a "wire-break" fault (unlike 0-20mA).

**OT18** — **Asset Inventory**: You cannot protect what you don't know exists. **Discovery**: **Passive** (sniffing traffic) is safe for OT. **Active** (scanning) is dangerous because it can crash sensitive legacy PLCs.

**OT19** — **MITRE ATT&CK for ICS**: 1. **Impair Process** (e.g., changing setpoints), 2. **Inhibit Response** (e.g., disabling alarms), 3. **Denial of Service**, 4. **Unauthorized Command Execution**, 5. **Module Firmware Modification**. **Difference**: Focuses on physical impact/process disruption rather than just data theft.

**OT20** — **Converged SOC**: Collect logs via passive monitoring (to avoid crashing PLCs), integrate into a SIEM, use OT-specific rules (e.g., "New PLC detected"), and use a triage workflow where OT engineers validate alerts. **Firmware Alert**: Treat as a critical incident; it implies a potential attempt to gain permanent control.
