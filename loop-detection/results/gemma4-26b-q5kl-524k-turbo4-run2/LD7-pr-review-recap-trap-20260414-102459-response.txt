### Security & Reliability Risks

* **Ephemeral Signing Key:** The `jwtSecret` is generated randomly in `init()` every time the application starts. This causes two critical issues:
    1. **Session Loss on Restart:** All existing user tokens become invalid every time the service restarts.
    2. **Distributed Inconsistency:** In a multi-instance/load-balanced environment, each instance will generate a different secret, meaning a token issued by Instance A will be rejected by Instance B. The secret must be loaded from a persistent, shared configuration or environment variable.
* **Refresh Token Revocation:** The PR removes the Redis dependency, but `GenerateRefreshToken` produces a random string that is not stored anywhere. Without a persistent backend to track these tokens, you lose the ability to revoke refresh tokens or implement a blacklist, significantly weakening the security model.
* **Unchecked Error in `init`:** `rand.Read(jwtSecret)` is called without checking the error return value. While rare, failure to populate the secret would lead to predictable or empty keys.

### Implementation Issues

* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys is a bad practice in Go. This can lead to collisions with other middlewares. Use unexported, custom types for context keys to ensure type safety and isolation.
* **Fragile Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` is highly sensitive to formatting. If the `Authorization` header is malformed (e.g., missing the space or the "Bearer" prefix), the resulting `tokenStr` will be incorrect.
* **Hardcoded Signing Method:** The signing method `HS256` is hardcoded in `IssueToken`. While acceptable for now, it would be better to allow for configuration or transition to asymmetric signing (RS256) if the architecture evolves.
