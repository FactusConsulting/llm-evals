**Status: Request Changes**

**Issues:**
- **cache/cache.go:20**: Goroutine leak. The `evict` goroutine runs an infinite loop with no mechanism (such as a `context.Context` or a `stop` channel) to terminate it. This will cause goroutines to leak indefinitely every time a new `Cache` instance is created and subsequently discarded.
- **cache/cache.go:53-60**: Performance bottleneck / Lock contention. The `evict` method holds the mutex for the entire duration of the map iteration. For large caches, this will block all other operations (`Set`, `Get`, `Delete`) for a significant amount of time during every eviction cycle.

**Nits:**
- **cache/cache.go:52**: The eviction interval is hardcoded to one minute via `time.Sleep(time.Minute)`, which prevents users from controlling the frequency of cleanup relative to their specific TTL needs.
- **cache/cache.go:38**: In `Get`, checking expiration after releasing the lock can result in returning stale data if a concurrent update occurs between the unlock and the expiry check. It is safer to perform the expiry check while holding the lock.
