### Critical Issues & Risks

* **Ephemeral Secret (Scaling/Persistence):** The `jwtSecret` is generated inside `init()` using `rand.Read`. This means all existing tokens become invalid every time the service restarts and makes horizontal scaling impossible, as multiple instances will each generate their own unique secret. How do we plan to manage a persistent, shared secret across instances?
* **Lack of Revocation Mechanism:** By removing the Redis dependency, we lose the ability to immediately invalidate access. Since JWTs are valid for 24 hours, how will we handle user logouts, password changes, or account compromises before the token expires?
* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys in `AuthMiddleware` is unsafe and can lead to collisions with other middlewares. We should use custom unexported types for these keys.
* **Incomplete Refresh Token Logic:** `GenerateRefreshToken` creates a random string but lacks any implementation for storage, association with a user, or validation logic. Where will these be persisted and verified?
* **Fragile Header Parsing:** In `AuthMiddleware`, `strings.TrimPrefix(authHeader, "Bearer ")` does not verify that the header actually starts with the expected prefix. If a client sends an incorrect format, it may result in unexpected behavior during parsing.

### Questions

* Do we intend to move to asymmetric signing (e.g., RS256) to allow different services to verify tokens without sharing the private key?
* Is there a planned secondary store (like a database or cache) specifically for a JWT blacklist to address the revocation issue?
