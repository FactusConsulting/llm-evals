### Security & Architecture Risks

* **Ephemeral Signing Secret**: The `jwtSecret` is generated randomly within an `init()` function. This causes two critical failures:
    1. **Service Restarts**: Every time the application restarts, all existing JWTs become invalid because the new instance will have a different secret.
    2. **Distributed Inconsistency**: In a multi-instance deployment (e.g., Kubernetes), each pod will generate its own unique secret. A token issued by Instance A cannot be validated by Instance B, making horizontal scaling impossible.
* **Lack of Revocation Mechanism**: By removing the Redis dependency and moving to stateless JWTs, there is no mechanism to revoke tokens. If a user logs out or a token is compromised, it remains valid until its expiration (`ExpiresAt`). How do we handle immediate revocation?
* **Refresh Token Persistence**: While `GenerateRefreshToken` creates an opaque string, the removal of Redis leaves no clear storage layer for these tokens. Without a persistent store, how does the system verify if a refresh token is legitimate or associated with a specific user?
* **Symmetric Key Risk**: Using HS256 requires every service that validates the token to possess the same secret used to sign it. For better security in distributed systems, consider using RS256 (asymmetric) so services only need the public key for validation.

### Code Quality & Implementation Issues

* **Context Key Collisions**: The middleware uses raw strings (`"userID"` and `"role"`) as context keys. This is anti-pattern in Go and can lead to collisions. These should be defined as unexported custom types to ensure type safety and prevent accidental overwrites.
* **Error Handling in Middleware**: In `AuthMiddleware`, when `ValidateToken` returns an error, the response is sent via `http.Error(w, "unauthorized", 401)`, but the function continues execution unless explicitly returned. *Correction: Looking at the code, there are returns present, so this is fine.*
* **Hardcoded Claims Keys**: The use of magic strings for JSON tags in the `Claims` struct is acceptable, but ensure they align with any existing frontend/client expectations during this migration.
