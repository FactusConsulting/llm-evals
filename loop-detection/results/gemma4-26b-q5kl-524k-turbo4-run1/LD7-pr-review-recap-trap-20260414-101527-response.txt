### Security & Reliability

* **Session Invalidation on Restart:** The `jwtSecret` is generated randomly in `init()`. This means every time the service restarts, all existing JWTs become invalid, forcing all users to re-authenticate. This defeats the purpose of stateless JWTs and creates a significant availability issue.
* **Lack of Secret Management:** Because the secret is generated in-memory and not loaded from a persistent source (like an environment variable or secret manager), it is impossible to rotate the secret without invalidating all sessions, and it is impossible to share the same secret across multiple instances of the service.
* **Unchecked Entropy:** In `init()`, the error returned by `rand.Read(jwtSecret)` is ignored. If the system's entropy source fails, the secret could be predictable or zeroed out.
* **Refresh Token Persistence:** The `GenerateRefreshToken` function creates a random string, but since the Redis dependency was removed, there is no mechanism shown to store or validate this token. How is a refresh token mapped back to a user without a data store?

### Implementation & Code Quality

* **Context Key Collisions:** The middleware uses raw strings (`"userID"`, `"role"`) as context keys. This is a bad practice that can lead to collisions with other packages. Use unexported custom types for context keys to ensure type safety.
* **Authorization Header Validation:** `strings.TrimPrefix(authHeader, "Bearer ")` is used without verifying that the header actually contained the `"Bearer "` prefix. While `ValidateToken` will catch the error, the middleware should explicitly validate the scheme.
* **Hardcoded Signing Method:** The signing method `HS256` is hardcoded in `IssueToken`. If the requirements change to asymmetric signing (RS256), this will require manual updates in multiple places.
