- **Critical: JWT Secret Lifecycle**
  The `jwtSecret` is generated randomly in `init()`. This causes all active tokens to become invalid on every application restart, forcing user re-authentication. Additionally, in a multi-instance deployment, each instance will have a unique secret, preventing token validation across load-balanced nodes. The secret must be loaded from a persistent environment variable or secret manager.

- **Token Revocation Strategy**
  Removing Redis eliminates the ability to maintain a token blacklist. If a token is compromised or a user is terminated, the token remains valid for 24 hours. What is the strategy for immediate session invalidation without a stateful store?

- **Refresh Token Storage**
  `GenerateRefreshToken` is implemented, but there is no code shown for storing or validating these tokens. Without Redis, where are refresh tokens persisted? Stateless refresh tokens allow indefinite reuse if stolen.

- **Context Key Safety**
  Using string literals (`"userID"`, `"role"`) for `context.WithValue` keys risks collisions with other middleware. Define custom types for context keys to ensure type safety and prevent overwrites.

- **Initialization Error Handling**
  `rand.Read` in `init()` ignores errors. If entropy generation fails, the application may start with a nil or weak secret, leading to runtime panics or security vulnerabilities later.

- **Claim Immutability**
  Storing `Role` directly in the JWT means permission changes (e.g., demotion) will not take effect until the token expires. Is this acceptable for your security model?

- **Error Specificity**
  `ValidateToken` returns `jwt.ErrSignatureInvalid` when the claims type assertion fails, masking the actual reason (e.g., expiration or algorithm mismatch). This hinders debugging and proper client error handling.

- **Dependency Check**
  `middleware.go` uses `strings.TrimPrefix`, but the `strings` import is not visible in the excerpt. Ensure all required packages are imported.
