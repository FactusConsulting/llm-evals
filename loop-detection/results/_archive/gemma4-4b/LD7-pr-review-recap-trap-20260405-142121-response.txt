**Review Comments**

**auth/jwt.go**

*   The `jwtSecret` is generated randomly in `init()`. What is the mechanism for securely loading or rotating this secret in a production environment? Relying on a random value generated at startup might be insufficient for long-term security.
*   The token expiration is hardcoded to 24 hours in `IssueToken`. Is there a configuration mechanism available to adjust this lifespan?
*   The `GenerateRefreshToken` function generates a random string but there is no corresponding logic shown for storing, validating, or revoking these refresh tokens. How will token invalidation (e.g., on logout or password change) be handled?
*   The `ValidateToken` function returns `jwt.ErrSignatureInvalid` explicitly if the claims check fails, but if `jwt.ParseWithClaims` returns an error other than signature invalidity (e.g., expired token, malformed token), is the specific error type being handled or just passed up?

**auth/middleware.go**

*   The middleware assumes the token is present in the `Authorization` header prefixed with "Bearer ". What is the fallback or error handling if the header is present but the prefix is incorrect?
*   The context values (`"userID"`, `"role"`) are being set directly. Are these keys globally unique within the application's context usage, or is there a risk of collision with other middleware or handlers?
*   If `auth.ValidateToken` fails, the middleware returns a generic "unauthorized" 401. Should different validation failures (e.g., expired vs. invalid signature) result in distinct HTTP status codes or error messages for better client debugging?
