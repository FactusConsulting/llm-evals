**Secret Management & Horizontal Scaling**
`jwtSecret` is generated randomly in `init()`. This means every process restart generates a new key, instantly invalidating all previously issued tokens. In a multi-instance or rolling deployment scenario, this will cause widespread authentication failures. How is the signing secret intended to be provisioned?

**Refresh Token Architecture**
`GenerateRefreshToken()` produces a cryptographically random string but provides no persistence or revocation mechanism. Without storage, refresh tokens cannot be rotated, tracked, or invalidated upon logout, which defeats their primary security purpose. How do you plan to manage refresh token lifecycle and revocation without Redis?

**Authorization Header Parsing**
`strings.TrimPrefix(authHeader, "Bearer ")` does not validate the prefix. If a client sends `Authorization: Basic xyz` or an empty string, the prefix is stripped (or left unchanged), and the malformed value proceeds to validation. Consider using `strings.HasPrefix` to strictly enforce the `Bearer` scheme before parsing.

**Context Key Type Safety**
Using string literals (`"userID"`, `"role"`) as context keys is error-prone and susceptible to collisions with other middleware or packages. Consider defining unexported typed keys (e.g., `type userIDKey struct{}`) to ensure type safety and prevent accidental overwrites.

**Ignored Crypto Error**
In `init()`, the error from `rand.Read(jwtSecret)` is silently ignored. While `crypto/rand` rarely fails, ignoring errors in cryptographic initialization is a bad practice. Consider logging or panicking if the entropy source fails.

**Redundant Validation Check**
`jwt.ParseWithClaims` already validates the signature, expiration, and other registered claims. The subsequent `token.Valid` check in `ValidateToken` is redundant and can be removed.

**Revocation Strategy**
JWTs are inherently stateless. Without a blacklist or allowlist mechanism, there is no way to force-logout users or invalidate compromised tokens before expiration. How do you intend to handle token revocation in this new architecture?
