**`auth/jwt.go`**
- **Runtime Secret Generation:** `jwtSecret` is generated randomly in `init()`. This breaks horizontal scaling, as tokens signed by one process will fail validation on another. The secret must be injected via environment variables or a secrets manager to remain consistent across deployments.
- **Unchecked `rand.Read` Call:** `rand.Read(jwtSecret)` ignores both the number of bytes read and the error. If the read fails or returns fewer than 32 bytes, the secret will be partially zeroed, weakening cryptographic strength. Add error handling and consider `io.ReadFull`.
- **Token Revocation Gap:** JWTs are stateless by design. Removing Redis eliminates the ability to invalidate tokens early (e.g., on logout, password change, or compromise). How will you implement token blacklisting or revocation without a backing store?
- **Refresh Token Lifecycle:** `GenerateRefreshToken` creates a random string but provides no storage, validation, or rotation logic. Without persistence, refresh tokens cannot be revoked or tracked, creating the same statelessness problem as access tokens.

**`auth/middleware.go`**
- **Context Key Collision Risk:** Using string literals (`"userID"`, `"role"`) as context keys is unsafe and prone to collisions with other middleware or third-party packages. Define unexported custom types for context keys to guarantee uniqueness.
- **Fragile Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` is case-sensitive and does not handle extra whitespace (e.g., `"Bearer  token"` or `"bearer token"`). Consider using `strings.HasPrefix` with case-insensitive comparison or `strings.Fields` to safely extract the token.
- **Role Staleness:** Embedding `role` in the JWT means role changes won't take effect until the token expires. Is this acceptable for your threat model, or do you need a mechanism to force re-authentication when roles are updated?
