**Security & Architecture Risks**
- **Runtime Secret Generation:** `jwtSecret` is initialized in `init()` via `crypto/rand`. This generates a new signing key on every application restart, instantly invalidating all active tokens and causing unexpected user logouts. The secret must be externally configured (env var/secret manager) and persisted across restarts.
- **Refresh Token Statelessness:** `GenerateRefreshToken` creates a stateful token, but the PR explicitly removes Redis/session storage. Without a backing store, there is no mechanism to validate, rotate, or revoke refresh tokens. This breaks the standard JWT refresh flow.
- **Distributed Secret Sync:** HS256 is symmetric. In a multi-instance deployment, all nodes must share the exact same `jwtSecret`. The current approach makes horizontal scaling impossible without external secret distribution.

**Code Quality & Go Idioms**
- **Context Key Collisions:** Hardcoded string keys (`"userID"`, `"role"`) in `context.WithValue` are prone to collisions with other middleware or packages. Use a typed context key (e.g., `type contextKey string`) or a dedicated library to prevent overwrites.
- **Weak Header Validation:** `strings.TrimPrefix(authHeader, "Bearer ")` will silently accept malformed headers (e.g., `Token abc123` or `Basic xyz`) and pass them to validation. Use `strings.HasPrefix` to explicitly reject non-Bearer schemes and return a clear 401.

**Error Handling & Validation**
- **Error Masking:** `ValidateToken` returns `jwt.ErrSignatureInvalid` when the type assertion fails. This masks the actual error returned by `jwt.ParseWithClaims` (e.g., `jwt.ErrTokenExpired` or `jwt.ErrTokenMalformed`). Return the original parsing error or wrap it to preserve the underlying cause for logging and debugging.
- **Redundant Validation:** The explicit `token.Valid` check after `jwt.ParseWithClaims` is unnecessary. The parser already validates the signature, expiration, and claims structure. If `err == nil`, the token is valid.

**Questions for Clarification**
- What is the intended expiration strategy? 24-hour access tokens are long-lived. Are short-lived access tokens paired with the refresh tokens planned?
- How will token revocation be handled if required (e.g., user logout, password change, or compromised credentials)?
- Where will the refresh tokens be persisted, and what is the TTL/rotation policy for them?
