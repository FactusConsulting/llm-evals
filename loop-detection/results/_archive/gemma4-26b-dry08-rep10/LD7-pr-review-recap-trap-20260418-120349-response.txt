### Security & Architecture
* **Secret Volatility:** The `jwtSecret` is initialized in the `init()` function. This causes two critical issues:
    * **Service Restarts:** All existing tokens will be invalidated every time the application restarts.
    * **Horizontal Scaling:** In a multi-instance deployment, every instance will generate a different secret, meaning a token issued by Instance A will be rejected by Instance B.
* **Lack of Revocation:** By removing the Redis-backed session store, the system loses the ability to immediately revoke access. How will the system handle logouts or compromised tokens without a centralized blacklist or short-lived TTL strategy?
* **Refresh Token Integration:** `GenerateRefreshToken` is implemented but currently unused. There is no logic in the middleware or the token issuance flow to handle the rotation or validation of these refresh tokens.

### Implementation Issues
* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys is a bad practice that can lead to collisions. These should be defined using custom, unexported types.
* **Middleware Prefix Validation:** The middleware uses `strings.TrimPrefix(authHeader,"Bearer ")` without verifying that the header actually started with the `"Bearer "` prefix.
* **Error Handling:** The error returned by `rand.Read(secret)` in the `init()` block is ignored.

### Questions
* How do we plan to persist or distribute the `jwtSecret` across multiple service instances?
* What is the intended lifecycle for the refresh tokens generated by `GenerateRefreshToken`?
