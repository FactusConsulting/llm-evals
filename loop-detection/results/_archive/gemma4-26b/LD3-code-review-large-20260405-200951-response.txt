    *   *Issue 1: Goroutine Leak.* The `evict` goroutine runs an infinite loop `for { ... }` and is started in `New`. There is no way to stop this goroutine (no `Close()` or `Stop()` method, no `context.Context` passed to `New`). If `Cache` objects are created and discarded, the goroutines will accumulate forever.
    *   *Issue 2: Performance/Lock Contention in `evict`.* The `evict` function holds `c.mu.Lock()` while iterating over the *entire* map. If the cache is large, this will block all `Get`, `Set`, and `Delete` operations for a significant duration, causing high latency spikes.
    *   *Issue 3: Inefficiency in `evict`.* The loop sleeps for a fixed `time.Minute`. If the TTL is small (e.g., 100ms as seen in tests), items might stay in memory for up to a minute after they expire, even though `Get` correctly returns `false`. While not a bug in correctness, it's a memory leak/bloat issue.
    *   *Issue 4: `Get` logic.* `Get` checks `time.Now().After(e.expiresAt)` *after* releasing the lock. While `e` is a copy of the struct, `e.expiresAt` is a value type, so it's technically safe from a race condition on the value itself, but the logic is slightly inconsistent with the lock scope. However, the real issue is that `Get` doesn't clean up expired keys; it just returns `false`. This is fine, but the `evict` loop is the only thing cleaning up.
    *   *Issue 5: `evict` loop sleep.* `time.Sleep(time.Minute)` is hardcoded. This makes the cache behavior unpredictable for short TTLs.
