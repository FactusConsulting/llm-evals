The `jwtSecret` is generated randomly in `init()` and never exposed or configured externally. How will this secret be managed in a production environment, especially during deployment or scaling?

The token expiration is hardcoded to 24 hours in `IssueToken`. Is there a mechanism to configure this expiration time dynamically?

The `GenerateRefreshToken` function generates a random string but there is no corresponding logic shown for storing, validating, or revoking these refresh tokens. What is the intended lifecycle management for these tokens?

The `AuthMiddleware` assumes the token is always present in the `Authorization` header prefixed with "Bearer ". What is the fallback or error handling if the header is present but malformed (e.g., missing "Bearer ")?

The `Claims` struct includes `Role`, but the validation logic in `AuthMiddleware` only checks for token validity; it does not enforce any role-based access control (RBAC) checks for specific endpoints. Where will authorization logic be applied?

The `jwtSecret` is a global variable initialized at package load time. If this service needs to run multiple instances concurrently, how is it guaranteed that all instances share the exact same secret?
