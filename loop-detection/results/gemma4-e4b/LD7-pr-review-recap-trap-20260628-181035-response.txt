The `jwtSecret` is generated randomly only once during package initialization. How is this secret managed, rotated, or securely loaded in a production environment?

The `GenerateRefreshToken` function generates a random string but there is no corresponding logic shown for storing, validating, or revoking these refresh tokens. What is the intended lifecycle for these tokens?

The `AuthMiddleware` assumes the token is always present in the `Authorization` header prefixed with "Bearer ". What is the fallback or error handling if the header is present but malformed (e.g., missing "Bearer ")?

The `Claims` struct includes `Role`, but the validation logic in `ValidateToken` does not enforce any specific role-based access control checks; this logic must be handled downstream. Is there a plan to introduce role validation within the middleware or service layer?

The current implementation of `jwtSecret` uses `crypto/rand` for initialization, which is good, but if the application restarts, a new secret will be generated, invalidating all existing tokens. How will token continuity be maintained across restarts?
