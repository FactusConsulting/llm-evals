### Security & Architecture Risks

**1. Ephemeral Secret Management**
The `jwtSecret` is initialized using `rand.Read` inside an `init()` function. This means the signing key is regenerated every time the application restarts. This will immediately invalidate all existing tokens held by users upon any deployment or service restart, forcing a global logout. Furthermore, in a distributed/multi-instance environment, different instances will have different secrets, making it impossible for one instance to validate a token issued by another.

**2. Lack of Token Revocation**
By moving from Redis-backed sessions to stateless JWTs, we lose the ability to revoke a specific user's access immediately (e.g., in the event of a compromised account or a password change). Since the token is valid until its `ExpiresAt` timestamp, there is no mechanism in this diff to blacklist tokens.

**3. Missing Algorithm Validation**
In `ValidateToken`, the key function returns the secret without verifying the signing method. An attacker could potentially use the `none` algorithm or switch from `HS256` to an asymmetric algorithm to bypass verification. We should explicitly check `if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok { ... }`.

**4. Context Key Collisions**
Using raw strings (`"userID"`, `"role"`) as context keys is anti-pattern and risks collisions with other middlewares or packages. We should define custom, unexported types for context keys to ensure type safety and prevent collisions.

**5. Error Handling in `init()`**
The `rand.Read(jwtSecret)` call in `init()` ignores the error return value. While unlikely to fail on most systems, failing to check this error during the generation of a security-critical secret is unsafe.

### Implementation Questions

**1. Refresh Token Lifecycle**
The `GenerateRefreshToken` function is present, but there is no logic provided for how these tokens are stored, validated, or rotated. Since the goal was to remove the Redis dependency, where will these refresh tokens be persisted to allow for long-lived sessions?

**2. Token Expiration Policy**
The current implementation hardcodes a 24-hour expiration. Is this duration acceptable for our security model, especially given the lack of a revocation mechanism?

**3. Authorization Context**
The middleware injects `userID` and `role` into the context. Are there plans to provide helper functions (e.g., `auth.FromContext(ctx)`) to retrieve these values safely, or will downstream handlers be expected to perform type assertions on raw context keys?
