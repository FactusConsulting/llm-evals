### Issues, Risks, and Questions

**Critical Risks**
* **Ephemeral Secret:** The `jwtSecret` is generated in `init()` using `rand.Read`. This means the secret is unique to every process instance and changes every time the application restarts. This will invalidate all active user tokens during every deployment or scaling event, forcing a global logout. The secret must be loaded from a persistent, secure configuration or environment variable.
* **Lack of Revocation Mechanism:** By moving from stateful Redis sessions to stateless JWTs, the ability to immediately invalidate a session is lost. How do we handle user logouts, password resets, or account compromises if we cannot revoke a specific token?

**Implementation Issues**
* **Context Key Collisions:** Using raw string literals (`"userID"`, `"role"`) as context keys in `AuthMiddleware` is a bad practice that can lead to collisions with other middleware or packages. These should be replaced with unexported, custom types.
* **Fragile Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` is used without verifying that the `Authorization` header actually contains the `Bearer ` prefix. If a client sends a different prefix or no prefix, the logic may attempt to validate an incorrect string.
* **Unchecked Error in `init`:** The error returned by `rand.Read(jwtSecret)` is ignored. While unlikely to fail, it is a silent failure point during startup.
* **Missing Algorithm Validation:** In `ValidateToken`, the key function should explicitly verify that the token's signing method matches the expected `jwt.SigningMethodHS256` to prevent potential algorithm-switching attacks.

**Questions**
* **Refresh Token Storage:** Since the Redis dependency was removed, where are the tokens generated by `GenerateRefreshToken` being stored? If they are intended to be stateless, how is their lifecycle and rotation managed?
