**Diagnosis**

The restart loop is caused by a DNS resolution failure, not by the service binary or the systemd unit itself. On every start, `data-ingest` tries to connect to `kafka.internal:9092`, cannot resolve the hostname (`ping` confirms: "Name or service not known"), logs a fatal error, and exits with status 1. Because the unit is configured with `Restart=always` and `RestartSec=5`, systemd immediately reschedules it, producing the endless loop (47 restarts so far). The "connection refused" message in the journal is the application's handling of the failed connect — the underlying problem is that `kafka.internal` does not resolve on this host at all, so Kafka's actual state is irrelevant.

**Proposed fix**

1. **Restore name resolution for `kafka.internal` on `ingest01`.** Either add the broker to the internal DNS zone so `kafka.internal` resolves, or add a static entry in `/etc/hosts` (e.g., `<kafka-broker-ip>  kafka.internal`) if that is the accepted pattern in this environment. Once the name resolves, the next restart cycle (within ~5 seconds) will connect successfully and the service will stabilize — no unit changes are needed for recovery.

2. **Optional hardening to prevent recurrence:** change the unit to wait for a usable network by adding `Wants=network-online.target` and `After=network-online.target` (instead of `After=network.target`, which only guarantees the network stack exists, not DNS), and add a start-rate limit (e.g., `StartLimitIntervalSec=300` / `StartLimitBurst=5`) so a dependency outage results in a throttled retry rather than a tight restart loop.

Diagnosis and fix stated — stopping here.
