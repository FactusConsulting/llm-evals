### PR Review: Auth Refactor (JWT Migration)

**Security & Scalability Risks**
*   **Secret Management and Horizontal Scaling:** The `jwtSecret` is generated randomly during `init()`. In a production environment with multiple instances/pods, each instance will have a different secret. This will cause authentication failures when a user’s request hits an instance that didn't issue their token. The secret must be loaded from a persistent source (e.g., Environment Variables or Secret Manager).
*   **Lack of Revocation Mechanism:** By moving to stateless JWTs and removing Redis, we lose the ability to instantly invalidate a session (e.g., on logout or account suspension). What is the plan for handling immediate revocation? Do we intend to implement a short TTL combined with a blocklist?
*   **Symmetric vs. Asymmetric Signing:** You are using HS256. For better security architecture, should we consider RS256? Using asymmetric keys allows other microservices to verify tokens using a public key without needing access to the private signing key.

**Code Quality & Logic Issues**
*   **Context Key Collisions:** You are using raw strings (`"userID"`, `"role"`) as context keys. To prevent collisions with third-party libraries, these should be defined as custom types.
*   **Hardcoded Expiration:** The 24-hour expiration in `IssueToken` is hardcoded. This should be configurable via environment variables to allow for easier adjustments without code changes.
*   **Refresh Token Implementation:** While `GenerateRefreshToken` exists, there is no logic provided for how these refresh tokens are stored or validated since Redis was removed. How will the client use these to obtain new access tokens?
*   **Error Handling:** In `AuthMiddleware`, ensure that internal errors from `ValidateToken` do not leak sensitive information in the response body (though currently, it seems safely returning "unauthorized").
