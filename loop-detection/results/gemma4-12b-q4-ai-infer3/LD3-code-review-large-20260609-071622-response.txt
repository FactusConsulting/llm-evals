**Status:** Request Changes

**Issues:**

*   **Resource Leak:** `cache/cache.go:27` — The goroutine started via `go c.evict()` has no mechanism to be stopped or cancelled. There is no context or quit channel provided to shut down the background worker when the cache object is no longer needed, leading to a permanent goroutine leak if multiple Cache instances are created and discarded.
*   **Performance Bottleneck (Lock Contention):** `cache/cache.go:58-63` — Holding `c.mu.Lock()` while iterating over the entire map inside the `evict` method blocks all other operations (`Set`, `Get`, `Delete`) for $O(N)$ time. As the number of keys grows, this will cause significant latency spikes across the entire application. A better approach would be to collect expired keys first or use a more granular locking strategy.
*   **Correctness / Memory Management:** `cache/cache.go:40-42` — While the code correctly identifies an expired entry during a `Get` call, it does not remove that entry from the internal map immediately. This allows "zombie" entries to persist in memory until the next 1-minute eviction cycle occurs.

**Nits:**

1.  Use `any` instead of `interface{}` to align with modern Go standards.
2.  The hardcoded `time.Minute` sleep duration in `evict()` should be configurable via the `New` constructor.
3.  Missing documentation comments on exported types (`Cache`) and methods (`Set`, `Get`, `Delete`).
