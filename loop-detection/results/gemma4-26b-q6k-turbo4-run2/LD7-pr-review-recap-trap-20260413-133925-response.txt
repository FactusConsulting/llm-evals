### Security & Implementation Issues

**`auth/jwt.go`**
* **Critical: Non-deterministic Secret Generation:** The `jwtSecret` is generated randomly in `init()`. This means every time the application restarts, all existing tokens become invalid because the signing key changes. This will cause global logout events on every deployment or server restart.
* **Critical: Hardcoded/Insecure Key Management:** The secret is stored in memory and generated at runtime without a mechanism to load a persistent key from an environment variable or secret manager.
* **Security: Weak Signing Method:** The implementation uses `HS256` (Symmetric). Since the secret is generated locally and not shared, this works for a single instance, but will fail in a distributed/load-balanced environment where different instances will have different `jwtSecret` values.
* **Security: Lack of Algorithm Validation:** In `ValidateToken`, the code does not explicitly verify that the token's header specifies `HS256`. This could leave the system vulnerable to "alg: none" attacks or symmetric/asymmetric confusion attacks depending on the library version and configuration.
* **Security: Missing Error Handling:** `rand.Read(jwtSecret)` in `init()` ignores the error return value. If the system's entropy source fails, the secret might be uninitialized or predictable.

**`auth/middleware.go`**
* **Risk: Context Key Collision:** Using raw strings (`"userID"`, `"role"`) as context keys is dangerous. These should be defined as unexported custom types to prevent collisions with other middlewares or packages.
* **Risk: Improper Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` is used without checking if the prefix actually exists. If a client sends a header that doesn't start with "Bearer ", the code will attempt to validate the raw string as a token.

### Questions
* How do you plan to synchronize the `jwtSecret` across multiple service instances to ensure horizontal scalability?
* Should we implement a mechanism to rotate keys without invalidating all active user sessions?
* Is there a requirement for token revocation (blacklisting)? Since we are moving away from Redis-backed sessions, we currently have no way to invalidate a JWT before its `ExpiresAt` time.
