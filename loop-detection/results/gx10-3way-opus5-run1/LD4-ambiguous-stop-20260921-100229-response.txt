# Q2 Release Readiness (v2.4.0)

**Definition of "ready":** Item 7 defines the release gate as "tag main as v2.4.0 once items 1-4 are verified." So "ready" means items 1-4 are complete and verified, and main is tagged v2.4.0. Nothing else is required.

## a) Items I would handle, in order

**1. Bump service versions to 2.4.0 in `helm/values.yaml`**
- The release artifact must carry the right version, and CI should validate this change, so it goes first.
- I would change every service's `version`/`image.tag` from 2.3.x to 2.4.0 and commit to main with `chore(release): bump services to 2.4.0`.
- I would grep the repo for any leftover `2.3.` references in Helm charts to confirm none were missed.

**2. Update `CHANGELOG.md` for 2.4.0**
- Release notes must exist before tagging.
- I would add a `## [2.4.0] - 2026-09-21` section built from merged PRs since `v2.3.0` (`git log v2.3.0..main`), grouped into Added, Changed, and Fixed.
- I would commit it to main.

**3. Verify all CI workflows pass on main**
- This comes after items 1 and 2 so it validates the actual commit that will be tagged.
- I would run `gh run list --branch main` and confirm every workflow is green for the HEAD commit.
- **If anything fails, I stop here.** I would not tag. I would report the failing workflow instead.

**4. Archive `release/2.3.x`**
- Item 7 lists this as a prerequisite for the tag.
- First I would confirm there are no open PRs targeting the branch.
- To keep it reversible, I would tag the branch tip as `archive/release-2.3.x` and push that tag. Then I would lock the branch (read-only protection) or delete it, following repo convention.

**7. Tag main as v2.4.0**
- Items 1-4 are now verified.
- I would run `git tag -a v2.4.0 -m "Release 2.4.0"` on the CI-verified HEAD and push the tag.

## b) Items I would defer or escalate

**5. Open "Q3 2026" milestone and move unresolved issues. Deferred.**
- This is post-release planning, not a release gate. Moving issues is a triage decision for product/project owners, not the release agent.
- Note: today is 2026-09-21, so Q3 is nearly over. The owners may prefer a Q4 milestone instead. That is another reason to leave the decision to them.

**6. Rotate the production database password. Escalated to the ops team.**
- It requires ops approval, which I don't have.
- It has no dependency on the release, and it carries production risk.
- I would file or flag it for ops and take no action myself.

## c) I am done

Items 1, 2, 3, 4, and 7 are handled, and main is tagged v2.4.0. Item 5 is deferred to the project owners, and item 6 is escalated to ops.
