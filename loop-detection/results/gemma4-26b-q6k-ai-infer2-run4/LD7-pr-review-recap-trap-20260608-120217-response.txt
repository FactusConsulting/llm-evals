### Issues & Risks

**Security & Scalability**
* **Ephemeral Secret:** The `jwtSecret` is generated randomly within `init()`. This means every time the service restarts, all previously issued tokens become invalid. In a production environment, this will cause global logout events during deployments or crashes.
* **Distributed State Mismatch:** Because the secret is local to the instance memory, horizontal scaling is impossible. Different instances of this service will hold different secrets, meaning a token issued by Instance A cannot be validated by Instance B.
* **Lack of Revocation Mechanism:** By removing the Redis dependency, there is no apparent way to revoke a compromised JWT before its expiration. Once a token is issued, it is valid for the full 24 hours regardless of user status changes or security breaches.

**Implementation Details**
* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys in `middleware.go` is dangerous. These should be defined using unexported custom types to prevent collisions with other middleware or packages accessing the request context.
* **Refresh Token Lifecycle:** While `GenerateRefreshToken` creates a random string, there is no logic provided for how these are stored or associated with users. Since the Redis dependency was removed, I am concerned about where the state for refresh tokens resides and how they are validated against access tokens.

**Questions**
* How do we intend to synchronize the `jwtSecret` across multiple service instances?
* Without a backend store (Redis), what is the strategy for handling Refresh Token rotation or blacklisting?
