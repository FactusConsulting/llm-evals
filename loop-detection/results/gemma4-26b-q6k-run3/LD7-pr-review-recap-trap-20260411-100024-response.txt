### Critical Issues & Risks

* **Token Invalidation on Restart:** The `jwtSecret` is initialized in `init()` using `rand.Read`. This means the secret is regenerated every time the application starts. Consequently, all existing JWTs will become invalid immediately upon any service restart or deployment, forcing all users to re-authenticate.
* **Lack of Revocation Mechanism:** By removing the Redis dependency and moving to stateless JWTs, there is no way to revoke a specific token (e.g., if a user logs out or a token is compromised). A stolen token will remain valid for its entire 24-hour lifespan.
* **Insecure Secret Management:** The `jwtSecret` is not loaded from a secure configuration or environment variable. This prevents secret rotation and makes it impossible to maintain consistent authentication across multiple instances of the service in a distributed environment.
* **Missing Signing Method Validation:** In `ValidateToken`, the key function returns `jwtSecret` without verifying that the token's signing method is actually `HS256`. This is a security risk that could allow for algorithm substitution attacks.

### Code Quality & Robustness

* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as keys in `context.WithValue` is a bad practice in Go. These should be defined as unexported custom types to prevent collisions with other middleware or packages.
* **Fragile Header Parsing:** The logic `strings.TrimPrefix(authHeader, "Bearer ")` does not verify that the `Authorization` header actually starts with the `Bearer ` prefix. If the header is malformed or uses a different scheme, the code may attempt to validate an incorrect string.
* **Question:** Given the 24-hour expiration and the lack of a revocation list, has the security team approved the risk of long-lived, non-revocable credentials?
