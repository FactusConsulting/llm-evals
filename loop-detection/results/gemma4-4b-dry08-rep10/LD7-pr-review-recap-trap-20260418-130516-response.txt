**PR Review: LD7 — JWT Refactor**

**Security & Configuration Risks:**

1.  **Secret Management:** The `jwtSecret` is initialized randomly within the `init()` function. This secret is critical for security. Is there a plan or mechanism to load this secret from a secure external source (e.g., configuration file, environment variable, secret manager) rather than relying on a runtime random generation?
2.  **Token Lifespan:** The token expiration is hardcoded to 24 hours in `IssueToken`. Should this duration be configurable via application settings?
3.  **Refresh Token Flow:** The `GenerateRefreshToken` function exists, but the implementation excerpt does not show how refresh tokens are issued, stored, or validated. What is the intended lifecycle and storage mechanism for these tokens?

**Implementation & Robustness Questions:**

4.  **Header Parsing:** In `AuthMiddleware`, the code assumes the `Authorization` header strictly follows the `Bearer ` prefix. How is the middleware handling cases where the header is present but malformed (e.g., missing the space, or using a different scheme)?
5.  **Error Granularity:** When `ValidateToken` fails, the middleware returns a generic "unauthorized" 401 error. Are there requirements to distinguish between specific failure modes (e.g., token expired vs. signature invalid) for logging or client-side handling?
6.  **Context Key Collision:** The middleware uses `context.WithValue` to store `userID` and `role`. Are these context keys globally unique, or is there a risk of collision with other middleware or application components that might use similar context keys?
7.  **Dependency Management:** Since the Redis dependency is removed, what is the plan for handling stateful operations (like rate limiting or user bans) that previously relied on session storage?

Please address these points before merging.
