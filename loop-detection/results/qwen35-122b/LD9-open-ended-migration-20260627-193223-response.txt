

**Risks and Prerequisites**
Primary risks involve application incompatibility due to deprecated SQL functions in Postgres 16 and extended downtime caused by the single-replica configuration during the managed upgrade. There is no failover capability during the upgrade window, meaning all traffic must stop. Data corruption is possible if the upgrade process fails mid-stream. Prerequisites include confirming psycopg2 2.9.3 compatibility (upgrade to 2.9.9+ recommended), ensuring DigitalOcean snapshot retention is enabled, and verifying Kubernetes connection poolers are configured to handle version changes. Ensure rollback procedures are documented before starting. Verify network policies allow traffic between K8s and the new DB version.

**Migration Plan**
1.  Audit the codebase for deprecated SQL functions or syntax incompatible with Postgres 16.
2.  Upgrade the application’s psycopg2 dependency to version 2.9.9 or higher in the staging branch.
3.  Provision a new DigitalOcean managed database cluster on Postgres 16 with identical specs to production.
4.  Restore the latest production snapshot to the new Postgres 16 cluster.
5.  Update the staging Kubernetes environment to point to the new Postgres 16 cluster.
6.  Execute the full integration test suite against the staging environment to validate data integrity.
7.  [HUMAN APPROVAL] Schedule a maintenance window with the operations team and stakeholders.
8.  [HUMAN APPROVAL] Notify external partners of potential payment processing delays during the window.
9.  Scale down the payments service deployment in Kubernetes to zero replicas to prevent writes during upgrade.
10. Create a final manual snapshot of the production Postgres 14 cluster.
11. [HUMAN APPROVAL] Trigger the major version upgrade on the production DigitalOcean cluster.
12. Wait for the DigitalOcean upgrade process to complete and verify cluster status.
13. Scale the payments service deployment back to one replica in Kubernetes.
14. Verify application logs for connection errors or authentication failures.
15. Execute critical payment transaction smoke tests to confirm service functionality.
16. [HUMAN APPROVAL] If tests fail, initiate rollback to the manual snapshot; if successful, close the maintenance window.

**Human Approval Notes**
Steps 7, 8, 11, and 16 require explicit human authorization before proceeding.
