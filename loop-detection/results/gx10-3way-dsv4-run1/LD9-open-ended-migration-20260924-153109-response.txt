### Key Risks and Prerequisites

- Major-version upgrade can introduce SQL behavior changes, query-plan regressions, and extension incompatibilities.
- psycopg2 2.9.3 predates PostgreSQL 16; verify it works with PG16 or upgrade to a later 2.9.x patch.
- Managed upgrade may require downtime or replica promotion; unverified backups increase rollback risk.
- Extensions, roles, grants, and custom database objects must be validated on PG16 before cutover.
- A maintenance window and rollback plan are mandatory for a payments service.

### Migration Plan

1. Create a change ticket with a rollback plan and obtain approval from the service owner and database administrator.  
2. Contact DigitalOcean support to confirm the supported upgrade path from PostgreSQL 14 to 16, expected downtime, and whether a maintenance window must be scheduled.  
3. Take a manual snapshot/backup of the current PG14 cluster and verify restore to a temporary cluster.  
4. In a staging environment, restore the latest production backup to a temporary PG16 cluster and run the full application test suite, including payment flows.  
5. Verify psycopg2 2.9.3 compatibility with PG16; if failures occur, upgrade psycopg2 to the latest 2.9.x release and re-run tests.  
6. Inventory all extensions and custom database objects; confirm each is supported on PG16 and update extension versions if needed.  
7. Freeze application deployments and database migrations during the maintenance window.  
8. Drain connections from the payments service by scaling down pods or pausing connection-pool traffic to ensure no active transactions remain.  
9. Trigger the DigitalOcean-managed upgrade to PG16, following their runbook; monitor upgrade logs and replica status.  
10. Verify data integrity after upgrade: row counts, recent transactions, balances, sequence values, and foreign-key constraints.  
11. Re-enable application connections and run smoke tests for payment creation, refunds, and reconciliation.  
12. Monitor for 24–48 hours for query-plan regressions, errors, latency spikes, and connection issues; keep the PG14 snapshot available for rollback.  
13. If critical issues arise, roll back to the PG14 snapshot and restore service; document the outcome in the change ticket.

### Approval / External Coordination

- Step 1 requires human approval from service owner and DB admin.  
- Step 2 requires external coordination with DigitalOcean support.  
- Step 9 requires DigitalOcean to execute the upgrade and may require their approval for the maintenance window.
