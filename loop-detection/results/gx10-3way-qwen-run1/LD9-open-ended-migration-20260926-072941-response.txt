Key risks and prerequisites

- DigitalOcean DBaaS major upgrade may require a maintenance window, direct upgrade path, or new cluster migration; endpoint, SSL, and replica behavior can change.
- One replica reduces HA; failover, read traffic, and connection draining must be planned.
- psycopg2 2.9.3 may not be validated for PG16; libpq, auth, SSL, and query behavior need testing.
- Payments data integrity: constraints, sequences, transactions, refunds, idempotency, collations, extensions, and logical replication must remain correct.
- Prerequisites: current DB inventory, app dependency inventory, staging clone, verified backups, rollback runbook, stakeholder approval.

Migration plan

1. Inventory the current database and application: exact PG14 version, extensions, collations, schemas, table sizes, sequences, roles, Kubernetes deployments, secrets, connection poolers, and read/write endpoints.
2. Confirm DigitalOcean upgrade path and constraints: whether direct 14 to 16 is supported, maintenance duration, replica promotion, endpoint changes, supported extensions, and PITR behavior. Requires external coordination with DigitalOcean support and platform owners.
3. Create a full backup of the production database and restore it into an isolated staging environment running PG16.
4. Upgrade application dependencies in a test image: move psycopg2 from 2.9.3 to the latest supported 2.9.x release, or psycopg3 if the codebase supports it; rebuild and scan the image.
5. Run application unit and integration tests against the restored PG16 staging database, focusing on payment authorization, capture, refund, settlement, idempotency, and migration scripts.
6. Validate database behavior: constraints, triggers, sequences, time zones, collations, SSL modes, authentication, connection pooling, failover behavior, and any extensions used by the payments service.
7. Run representative load tests and inspect slow queries, lock contention, autovacuum, index usage, connection limits, and replica lag.
8. Write the production runbook with exact commands or API calls, health checks, rollback criteria, communication plan, and timing. Requires human approval from the payments service owner, DBA/platform lead, and change advisory board.
9. Schedule a maintenance window and notify stakeholders; freeze schema changes, batch jobs, and long-running transactions before the window. Requires human approval.
10. Run pre-upgrade checks in production: confirm no active long transactions, replication lag is acceptable, disk space is sufficient, backup/PITR is healthy, and connection pools can be drained.
11. Take a final pre-upgrade snapshot and record the PITR point.
12. Upgrade the database. If DigitalOcean supports direct upgrade, trigger the upgrade and monitor the primary and replica. If direct upgrade is not supported, create a PG16 cluster, migrate data using logical replication or dump/restore, and validate before cutover. Requires human approval and external coordination.
13. Update Kubernetes configuration: connection string, secret, SSL mode, pooler settings, and any endpoint changes; perform a rolling restart of application pods.
14. Validate production immediately after cutover: smoke test payment flows, verify sequence values, constraints, error logs, latency, connection counts, and replica status.
15. Monitor for 24 to 72 hours while keeping the old cluster and backup available for rollback. If rollback is needed, restore or switch back according to the runbook. Requires human approval.
16. Decommission the old cluster only after the payments owner confirms stability and data integrity. Requires human approval.
