**Risks & Prerequisites**
- **Risks:** Cutover downtime if replica failover fails or sync lags; psycopg2 2.9.3 lacks PG 16 performance patches and may trigger deprecation warnings; DigitalOcean in-place upgrades require node restarts causing brief connection drops; PG 16 enforces stricter `pg_hba.conf` and collation defaults that may break existing queries.
- **Prerequisites:** Replica lag verified <1s; full DigitalOcean snapshot backup; staging K8s cluster mirroring production; psycopg2 upgraded to ≥2.9.9 and validated against PG 16; maintenance window approved; rollback procedure documented and tested.

**Migration Plan**
1. Verify replica sync status and confirm replication lag is under 1 second. [External Coordination: DO support if lag persists]
2. Create a manual snapshot backup of the PG 14 instance via the DigitalOcean console.
3. Provision a temporary PG 16 instance in the same region using the snapshot.
4. Run full integration and payment-processing tests against the PG 16 test instance.
5. If tests fail, update the K8s deployment to use psycopg2 ≥2.9.9 and retest. [Human Approval: Dependency change request]
6. Update K8s deployment manifests with the new PG 16 endpoint and rotate database credentials.
7. Schedule the maintenance window and broadcast the change to on-call and stakeholder channels. [Human Approval: Stakeholder sign-off]
8. Scale the payments service deployment to zero replicas to terminate all active connections.
9. Initiate the PG 14 to 16 in-place upgrade via the DigitalOcean dashboard.
10. Monitor the upgrade progress, verify instance health, replication status, and TLS configuration.
11. Update K8s secrets with the new PG 16 credentials and endpoint.
12. Scale the payments service back to production replica count and execute smoke tests.
13. Validate replica promotion readiness and monitor query latency and error rates for 30 minutes.
14. Decommission the legacy PG 14 instance after confirming 24-hour stability.
