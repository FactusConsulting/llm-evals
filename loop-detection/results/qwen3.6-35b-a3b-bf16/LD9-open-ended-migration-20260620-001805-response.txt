**Key Risks & Prerequisites**
**Risks**: Query plan regression from optimizer changes; replica sync lag causing read skew during traffic shift; connection pool exhaustion when pods reconnect; rollback complexity if logical replication diverges or data corruption occurs.
**Prerequisites**: Verified full database snapshot and logical backup; compatibility audit of extensions, custom PL/pgSQL functions, and `postgresql.conf` parameters; updated Kubernetes manifests with PG 16 connection strings; documented rollback playbook with trigger conditions; active monitoring alerts for replication lag and connection errors; DigitalOcean CLI/API credentials with cluster management permissions.

**Migration Plan**
1. Execute DigitalOcean’s compatibility validation against the production snapshot to confirm extension support, verify `pg_stat_statements` configuration, and ensure parameter parity.
2. Modify Kubernetes deployment manifests to reference the new PG 16 endpoint and upgrade `psycopg2` to 2.9.9+ in the application dependency file.
3. Provision a new PG 16 managed instance in DigitalOcean matching the current node count, storage IOPS, and VPC peering configuration.
4. Establish logical replication from the PG 14 primary to the PG 16 instance to synchronize schema objects and transactional data.
5. Validate replication lag remains below 5 seconds and audit the target instance for missing roles, tables, and custom functions.
6. [Requires Human Approval] Coordinate with the payments product owner and SRE lead to approve the maintenance window and rollback criteria.
7. Trigger the managed upgrade or replica promotion via DigitalOcean CLI, ensuring the new instance accepts read/write traffic.
8. Scale the payments service deployment to zero in Kubernetes to terminate all active database connections and clear connection pools.
9. Rotate Kubernetes secrets with the new PG 16 credentials and initiate a rolling restart of the application pods.
10. Observe pod readiness probes, connection success rates, and query execution times for a 15-minute stabilization period.
11. [Requires External Coordination] Request infrastructure team approval to terminate the legacy PG 14 cluster and release reserved storage quotas.
12. Execute the end-to-end payment processing test suite against the live PG 16 endpoint to verify transaction atomicity and idempotency.
13. [Requires Human Approval] Review application error logs and payment gateway receipts to confirm zero data loss before final cutover.
14. Update the CI/CD pipeline to include automated schema compatibility checks against PG 16 for all future deployment branches.
15. Retain the original PG 14 snapshot for 72 hours before permanent deletion to allow emergency point-in-time recovery if anomalies surface.
