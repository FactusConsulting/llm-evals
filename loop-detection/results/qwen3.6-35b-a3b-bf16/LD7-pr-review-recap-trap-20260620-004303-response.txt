### Security & Reliability
- **Ignored `rand.Read` error in `init()`**: The error from `rand.Read(jwtSecret)` is discarded. If the OS CSPRNG fails, `jwtSecret` remains all zeros, creating a catastrophic vulnerability. Since `init()` cannot return errors, you should either `panic()` on failure or log and exit, ensuring the service never starts with a weak secret.
- **Secret regeneration on restart**: Generating a new secret per process lifecycle invalidates all active tokens on every deployment/restart. This breaks token refresh flows and causes widespread auth failures during rolling updates. Load the secret from an environment variable or secrets manager, and consider asymmetric signing (RS256/ES256) if verification needs to be distributed.
- **Redundant & masking validation logic**: `jwt.ParseWithClaims` already validates the signature, expiration, and claims. The subsequent `token.Valid` check is unnecessary. Additionally, returning `jwt.ErrSignatureInvalid` on a type assertion failure masks the actual parsing error. Let `jwt.ParseWithClaims` return its error directly to preserve the original failure reason.

### Code Quality & Go Idioms
- **Unsafe header parsing**: `strings.TrimPrefix(authHeader, "Bearer ")` does not verify the prefix exists. A header like `"BearerExtra"` or `"abc"` will pass through unchanged. Add a `strings.HasPrefix` check or split on space to enforce strict format compliance before parsing.
- **Unidiomatic context keys**: Using string literals (`"userID"`, `"role"`) as context keys is unsafe and unidiomatic in Go. It risks key collisions across packages and causes panics on type assertion. Define a custom unexported type (e.g., `type contextKey string`) and use it as the key in `context.WithValue`.
- **Missing error differentiation**: The middleware returns a generic 401 for both missing headers and invalid tokens. While functionally correct, distinguishing between expired tokens (which may warrant a 401 with a refresh hint) and malformed signatures (which may indicate tampering) improves observability and client-side handling.

### Architecture & Flow Questions
- **Refresh token lifecycle**: `GenerateRefreshToken()` creates a random string but provides no mechanism for storage, validation, or expiration. How are refresh tokens persisted? How is rotation handled to prevent replay attacks? Please clarify the refresh token issuance and revocation strategy.
- **Public vs. protected routes**: The middleware unconditionally returns 401 if the `Authorization` header is missing. How are public endpoints (e.g., login, registration) handled? Ensure this middleware is only attached to protected route groups, or add an explicit allowlist/ignore logic.
