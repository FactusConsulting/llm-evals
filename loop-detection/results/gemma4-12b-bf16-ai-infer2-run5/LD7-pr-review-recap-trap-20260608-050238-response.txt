### Security & Architecture Risks

*   **Insecure Secret Management:** The `jwtSecret` is generated randomly at runtime during `init()`. In a production environment with multiple instances or containers, each instance will generate a different secret, causing valid tokens from one instance to be rejected by others. Furthermore, every application restart will invalidate all currently active user sessions. The secret must be loaded from a secure environment variable or a dedicated Secrets Manager (e.g., AWS KMS, HashiCorp Vault).
*   **Lack of Revocation Mechanism:** By moving to stateless JWTs and removing Redis, we lose the ability to instantly revoke a session (e.g., for logouts or account suspensions). Since the token remains valid until its expiration time, we need a strategy—such as a short-lived access token paired with a database-backed refresh token—to handle revocation.
*   **Hardcoded Expiration:** The 24-hour expiration in `IssueToken` is hardcoded. This should be configurable via environment variables to allow for adjustments based on security requirements without code changes.
*   **Context Key Collisions:** Using raw strings like `"userID"` and `"role"` as context keys can lead to collisions with other middlewares or third-party libraries. You should use a custom unexported type for context keys to ensure uniqueness.

### Implementation Issues

*   **Unused Refresh Token Logic:** While `GenerateRefreshToken` is implemented, it is not integrated into the `IssueToken` flow or the middleware logic. How do you plan to persist these tokens? If they are also stateless, how will we validate them against a "revoked" list?
*   **Error Masking:** In `ValidateToken`, returning `jwt.ErrSignatureInvalid` specifically when any error occurs during parsing might mask other critical issues such as expired tokens (`jwt.ErrTokenExpired`). It would be better to return the actual error from `ParseWithClaims`.
*   **Missing Authorization Header Validation:** The current middleware checks if the header exists but doesn't explicitly check if the `Authorization` header follows the standard format before trimming. A malformed header that doesn't start with "Bearer " might cause unexpected behavior depending on how `strings.TrimPrefix` handles empty results.
