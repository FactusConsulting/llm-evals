### Security & Architecture Risks

*   **Ephemeral Secret Management:** The `jwtSecret` is generated using `rand.Read` inside an `init()` function. This means the secret is regenerated every time the application restarts. This will immediately invalidate all existing tokens held by users upon any deployment or service restart, forcing a global logout. The secret should be loaded from a persistent, secure configuration or environment variable.
*   **Missing Algorithm Validation:** In `ValidateToken`, the key function returns the secret without verifying the signing method. An attacker could potentially use a "none" algorithm or switch from asymmetric to symmetric signing (if the system were expanded) to bypass verification. You should explicitly check that `t.Method` matches `jwt.SigningMethodHS256`.
*   **Lack of Token Revocation:** By moving from Redis-backed sessions to stateless JWTs, you have lost the ability to instantly revoke a user's access (e.g., in the event of a password change, account deletion, or stolen token). How do we plan to handle logout or blacklisting of compromised tokens?
*   **Context Key Collision:** Using raw strings (`"userID"`, `"role"`) as context keys in `AuthMiddleware` is error-prone and can lead to collisions with other middlewares. Please use a custom, unexported type for context keys.
*   **Error Handling in `init`:** The `rand.Read(jwtSecret)` call in `init()` ignores the error return. While unlikely to fail on most systems, failing to seed the secret properly would result in a predictable key.

### Implementation Details & Questions

*   **Refresh Token Utility:** The `GenerateRefreshToken` function is implemented, but there is no corresponding logic in the middleware or the `Claims` structure to handle the rotation or validation of these tokens. Where is the persistence layer for these refresh tokens intended to live?
*   **Token Expiration Policy:** The hardcoded 24-hour expiration in `IssueToken` is quite long for a stateless access token. Given the lack of a revocation mechanism, should we consider shorter-lived access tokens paired with the refresh tokens?
*   **Dependency Management:** The `ValidateToken` function returns `jwt.ErrSignatureInvalid` manually if the claims assertion fails, but it doesn't distinguish between an expired token and an invalid signature in the error response. This might make client-side debugging difficult.
*   **Middleware Robustness:** The `strings.TrimPrefix(authHeader, "Bearer ")` logic does not validate if the prefix was actually present. If a client sends a header without the "Bearer " prefix, `tokenStr` will contain the original header string, which will then fail parsing. It should explicitly check for the prefix.
