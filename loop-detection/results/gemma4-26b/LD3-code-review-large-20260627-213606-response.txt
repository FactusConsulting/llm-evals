**Status: Request Changes**

**Issues:**

1.  **`cache/cache.go:23` (Resource Leak):** The `evict` goroutine started in `New` runs in an infinite loop with no mechanism for termination. If `Cache` instances are created and discarded (e.g., in tests or short-lived services), these goroutines will leak indefinitely. Add a `Close()` method that uses a `context.Context` or a `chan struct{}` to signal the `evict` loop to exit.
2.  **`cache/cache.go:41` (Correctness/Race Condition):** In `Get`, the check `time.Now().After(e.expiresAt)` is performed *after* the mutex is unlocked. While this doesn't cause a data race on the map itself, it allows for a logical race where an entry could be deleted by the `evict` goroutine or another `Delete` call between the `Unlock` and the expiration check. More importantly, if the entry is expired, it remains in the map until the next `evict` cycle (which only runs every minute), leading to unnecessary memory growth.
3.  **`cache/cache.go:54` (Performance/Blocking):** The `evict` function holds the `c.mu.Lock()` for the entire duration of the map iteration. If the cache contains a large number of entries, this will block all `Set`, `Get`, and `Delete` operations for a significant amount of time every minute, causing latency spikes.

**Nits:**

1.  **`cache/cache.go:14`**: Use `any` instead of `interface{}` to align with modern Go (1.18+) idioms.
2.  **`cache/cache.go:53`**: The `evict` loop uses a hardcoded `time.Minute`. Consider making the eviction interval configurable via `New`.
