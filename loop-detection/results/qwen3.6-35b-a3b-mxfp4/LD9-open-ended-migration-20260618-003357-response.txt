**Key Risks & Prerequisites**
Risks: Extended downtime during cluster promotion or replica failover; psycopg2 2.9.3 compatibility edge cases with PG 16 replication protocols and JSONB handling; data inconsistency if replication lag exceeds tolerance during cutover; failed rollback due to stale connection pools or corrupted snapshots.
Prerequisites: Verified full snapshot backup of the PG 14 cluster; test environment mirroring production K8s topology and DO DBaaS settings; updated connection pool configuration (max connections, SSL/TLS, idle timeout); approved maintenance window and documented rollback runbook; verification of psycopg2 2.9.3 release notes for PG 16 deprecations.

**Migration Plan**
1. Provision a new DigitalOcean managed Postgres 16 cluster in the same region and private network as the existing PG 14 instance.
2. Configure firewall rules and DO network settings to allow inbound connections from the payments service K8s node CIDR.
3. Enable cross-cluster replication from the PG 14 primary to the new PG 16 cluster using DigitalOcean’s native replication workflow.
4. Monitor the replication lag metric until it consistently reads zero for a minimum of 30 minutes.
5. Update the payments service K8s deployment manifest to replace the PG 14 endpoint with the new PG 16 connection string.
6. Execute a rolling deployment of the updated K8s manifests to gradually shift traffic to the new cluster.
7. Run automated integration tests against the PG 16 endpoint to validate psycopg2 2.9.3 query execution, transaction isolation, and connection pool health metrics.
8. Promote the PG 16 cluster to primary status and terminate the replication stream to the legacy PG 14 instance.
9. Force-drain all active database connections on the PG 14 cluster and verify zero write operations for 10 minutes.
10. Capture a final immutable snapshot of the PG 14 cluster and store it in a separate DO region for disaster recovery.
11. Update the internal service mesh routing rules to permanently bind the payments service to the PG 16 endpoint.
12. Activate enhanced monitoring dashboards and alerting thresholds for connection errors, query latency, and disk I/O on the PG 16 cluster.

**Approval & Coordination Notes**
- Step 5 & 6: Requires K8s platform team approval for the deployment window and traffic shift strategy.
- Step 8: Requires senior DBA sign-off to execute cluster promotion and replication termination.
- Step 9: Requires payments service owner authorization to force-drain connections and accept brief read-only downtime.
- Step 10: Requires security/compliance approval to archive the legacy snapshot per data retention policies.
- Step 11: Requires network engineering coordination to update service mesh routing and DNS records.
