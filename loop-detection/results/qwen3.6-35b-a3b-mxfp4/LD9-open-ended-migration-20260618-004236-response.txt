**Key Risks & Prerequisites**
- **Risks:** DigitalOcean DBaaS major version upgrades trigger a brief restart/failover, causing write unavailability. The single-replica topology eliminates automatic failover redundancy, increasing exposure during the upgrade window. Simultaneous pod restarts may exhaust connection pools before new endpoints resolve. PG 16 introduces changed defaults (e.g., `password_encryption`, `jit`) and deprecated features that may break existing queries or psycopg2 2.9.3 behavior.
- **Prerequisites:** Complete automated backup with verified restore in a staging environment. Update Kubernetes secrets and configmaps with the new DB endpoint and credentials. Tune application connection pools for graceful reconnects, circuit breaking, and connection draining. Document and test the rollback procedure against PG 14. Secure stakeholder sign-off for the maintenance window.

**Migration Plan**
1. Provision a staging Postgres 16 instance on DigitalOcean and replicate production data via `pg_dump`/`pg_restore`.
2. Execute the payments service integration suite against the staging PG 16 instance to validate psycopg2 2.9.3 compatibility, query execution, and transaction isolation.
3. Update Kubernetes deployment manifests to reference the new DB endpoint and inject updated connection secrets via the cluster’s secret management system.
4. Adjust application connection pool parameters (`max_overflow`, `pool_recycle`, `pool_pre_ping`) to tolerate transient connection drops during endpoint failover.
5. Schedule a maintenance window and distribute downtime notifications to on-call engineering, SRE, and finance teams. [Requires human approval]
6. Initiate the DigitalOcean DBaaS major version upgrade from PG 14 to 16 via the control panel or REST API.
7. Monitor upgrade telemetry and verify that the primary instance transitions to the `online` state running PG 16 and that replication slots are active.
8. Force a replica sync and promote the existing replica to confirm it is fully caught up with the upgraded primary before DNS cutover.
9. Update the Kubernetes headless service DNS records or external load balancer to route traffic to the new PG 16 endpoint.
10. Restart payments service pods in a rolling fashion to establish new connections and confirm readiness/liveness probes pass.
11. Execute automated integration tests and monitor error rates, p99 latency, and replication lag for 30 minutes.
12. If metrics remain within baseline thresholds, close the maintenance window; otherwise, execute the documented rollback to PG 14.

**Approval & Coordination Notes**
- Step 5 requires explicit stakeholder approval for the maintenance window and external coordination with SRE and finance for downtime communication.
- Step 6 requires coordination with DigitalOcean support if the upgrade triggers unexpected replica sync delays or requires manual intervention.
- Step 12 requires engineering lead approval to abort the migration and trigger the rollback procedure.
