**Key Risks & Prerequisites**
Risks: Single-replica architecture eliminates automatic failover, creating a narrow maintenance window. Staggered K8s pod restarts may exhaust connection pools during cutover. PG 16 enforces stricter `pg_hba.conf` defaults and deprecates legacy `psycopg2` connection parameters. Cross-cluster replication lag or data drift could cause silent corruption.
Prerequisites: DigitalOcean API credentials with cluster management scope. Verified `psycopg2 2.9.3` compatibility with PG 16. K8s deployment manifests updated with new endpoint, connection pool limits, and readiness probes. Pre-upgrade full backup and PITR snapshot. Approved maintenance window. Confirm `psycopg2` connection string format supports PG 16 `sslmode` and `application_name` parameters.

**Migration Plan**
1. Provision a new DigitalOcean managed Postgres 16 cluster matching the PG 14 sizing, storage class, and VPC network.
2. Apply identical firewall rules to allow inbound traffic from the K8s pod CIDR and node IPs.
3. Enable cross-cluster replication from the existing PG 14 primary to the new PG 16 cluster.
4. Monitor replication lag until it stabilizes at zero for 15 consecutive minutes.
5. Update K8s deployment manifests to target the new PG 16 endpoint and increase `max_connections` to 200 to absorb connection spikes.
6. Deploy manifests using a rolling update with `maxUnavailable=0` to maintain zero-downtime availability.
7. Validate application health checks, transaction latency, and error rates against the new PG 16 instance.
8. Promote the new PG 16 cluster to primary and sever replication from the legacy PG 14 node.
9. Update K8s Secrets or ConfigMaps to permanently route all database traffic to the PG 16 endpoint.
10. Decommission the legacy PG 14 cluster after 48 hours of stable operation and verified data consistency.
11. Execute full regression test suite against PG 16 to validate query plans, `jsonb` operators, and `pg_stat_statements` metrics.
12. Archive old cluster credentials, revoke scoped DO API tokens, and update internal runbooks.

**Approval & Coordination Requirements**
- Step 8 requires on-call infrastructure engineer coordination to execute the cluster promotion safely.
- Step 11 requires QA lead and senior developer approval to sign off on regression results before final decommission.
- Step 5 requires K8s platform team approval if cluster-wide network policies or service mesh configurations are modified.
- All steps require pre-approved maintenance window sign-off from product and security stakeholders.
