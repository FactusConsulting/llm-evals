**Critical: Secret Generation & Error Handling**
- `jwtSecret` is generated randomly in `init()` on every process startup. This will immediately invalidate all existing tokens upon any deployment or restart. The signing key must be persisted and injected via environment variables or a secrets manager.
- `rand.Read(jwtSecret)` ignores the returned error. If `crypto/rand` fails, the secret defaults to all zeros, creating a severe cryptographic vulnerability. Always handle `crypto/rand` errors.

**Design Risk: Stateless Refresh Tokens**
- `GenerateRefreshToken()` produces a stateless random string, but the PR explicitly removes Redis. Without a backend store to track refresh tokens, you cannot enforce revocation, handle expiry, or prevent replay attacks. Stateless refresh tokens are generally considered an anti-pattern. How do you plan to manage refresh token lifecycle and revocation?

**Middleware: Header Parsing & Validation**
- `strings.TrimPrefix(authHeader, "Bearer ")` does not validate that the header actually contains the prefix. A header like `Basic xyz` or `Bearer` (with no token) will pass through, causing downstream validation to fail with misleading errors. Use `strings.HasPrefix` and validate the token length before parsing.

**Context Key Safety**
- Using string literals (`"userID"`, `"role"`) as context keys is unsafe and prone to collisions across packages. Define typed context keys (e.g., `type userIDKey struct{}`) to prevent accidental overwrites and improve debugging.

**Validation Logic & Error Masking**
- `jwt.ParseWithClaims` already validates the signature and expiry, returning specific errors (e.g., `jwt.ErrTokenExpired`). The manual `token.Valid` check and fallback to `jwt.ErrSignatureInvalid` is redundant and masks the actual failure reason. If `token.Valid` is false, return the original `err` from `ParseWithClaims` instead.

**Questions on Token Lifecycle**
- `IssueToken` hardcodes a 24-hour expiry. Is this configurable per environment or user tier?
- If refresh tokens are introduced, will you implement token rotation (issuing a new refresh token on each use and invalidating the old one)? Without rotation, stolen refresh tokens remain valid until expiry.
