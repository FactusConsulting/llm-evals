**Key Risks & Prerequisites**
- **Risks:** Connection pool exhaustion during cutover, replica lag causing stale reads, psycopg2 2.9.3 edge-case incompatibilities with PG 16, split-brain if failover is interrupted, extended downtime if rollback is triggered.
- **Prerequisites:** Confirm psycopg2 2.9.3 fully supports PG 16, audit all connection strings and pool limits, ensure K8s manifests support dynamic endpoint updates, verify DigitalOcean backup retention covers the migration window, secure a 30-minute maintenance window, validate that no deprecated PG 14 features are in use, and update PgBouncer configuration to match PG 16 authentication requirements.

**Migration Plan**
1. Verify psycopg2 2.9.3 compatibility with Postgres 16 and update the application dependency lockfile if patches are required.
2. Provision a new DigitalOcean Postgres 16 cluster in the same region with identical node count, storage, and configuration.
3. Configure the new cluster as a replica of the existing Postgres 14 instance using DigitalOcean’s native replication workflow and validate WAL archiving is enabled.
4. Monitor replication lag until it consistently reaches zero for 30 minutes.
5. Deploy a staging K8s namespace pointing to the new Postgres 16 replica, run full integration test suites, and execute a dry-run failover test.
6. [Requires Human Approval] Obtain sign-off from the payments product owner and on-call SRE to proceed with production cutover.
7. [Requires External Coordination] Notify downstream API consumers and internal stakeholders of the scheduled maintenance window and expected read/write interruption.
8. Scale the production K8s deployment to zero to drain all active database connections.
9. Promote the Postgres 16 replica to primary via the DigitalOcean control panel.
10. Update K8s ConfigMaps and Secrets with the new Postgres 16 endpoint, connection parameters, and verify TLS certificate rotation and DNS propagation.
11. Scale the production K8s deployment back up and verify successful connection establishment and readiness probes.
12. Route 5% of production traffic to the new cluster using a canary deployment strategy.
13. Monitor error rates, query latency, and connection pool metrics for 24 hours, executing rollback to Postgres 14 if error rate exceeds 0.5%.
14. Decommission the original Postgres 14 cluster after confirming data integrity and application stability.
