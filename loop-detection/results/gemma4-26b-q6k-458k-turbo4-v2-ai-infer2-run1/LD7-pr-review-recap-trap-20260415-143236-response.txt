### Security & Architecture

* **Ephemeral Secret & Scaling:** The `jwtSecret` is generated in `init()`. This causes all active tokens to be invalidated whenever the service restarts. Additionally, this prevents horizontal scaling; if multiple instances of the service are running, each will have a unique secret, making tokens issued by one instance invalid on others.
* **Lack of Revocation:** By removing the Redis session store, we lose the ability to revoke access. How will the system handle user logouts or the invalidation of compromised tokens before their 24-hour expiration?
* **Refresh Token Persistence:** While `GenerateRefreshToken` is implemented, there is no mechanism shown for storing or validating these tokens. Since the Redis dependency was removed, where will these be persisted and verified?

### Implementation Details

* **Context Key Collisions:** In `middleware.go`, context values are injected using raw strings (`"userID"`, `"role"`). These should use custom, unexported types to prevent collisions with other middleware or packages.
* **Hardcoded Expiration:** The 24-hour expiration in `IssueToken` is hardcoded. Is this duration appropriate for our security model?
* **Brittle Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` is used without verifying if the "Bearer " prefix was actually present. If the header is malformed (e.g., just `"Bearer"`), `tokenStr` becomes an empty string.
* **Non-deterministic Testing:** Because the `jwtSecret` is generated in `init()`, it is impossible to write deterministic unit tests for `ValidateToken` without modifying the package to allow secret injection.
