**auth/jwt.go**
- **Secret Initialization Risk**: Generating a random `jwtSecret` in `init()` means every application restart invalidates all previously issued tokens. This breaks session continuity for active users. Secrets should be persisted via environment variables or a secrets manager.
- **Refresh Token Lifecycle Gap**: `GenerateRefreshToken()` creates tokens but provides no mechanism for storage, validation, rotation, or revocation. Without a backend store, how will you handle token expiration, refresh cycles, or forced logout? Please clarify the intended architecture for refresh token management.
- **Redundant Validation**: `jwt.ParseWithClaims` already validates the signature and expiration. The subsequent `token.Valid` check is unnecessary. You can safely return `claims, nil` directly after a successful parse.

**auth/middleware.go**
- **Header Parsing Robustness**: `strings.TrimPrefix(authHeader, "Bearer ")` does not verify that the header actually contains the prefix or that a token follows it. This could result in parsing empty strings. Consider using `strings.HasPrefix` and explicit length checks before slicing.
- **Context Key Safety**: Using string literals like `"userID"` and `"role"` as context keys is unsafe and prone to collisions. Define a custom unexported type (e.g., `type contextKey string`) and instantiate keys from it to ensure type safety and prevent accidental overwrites.
- **Role Caching Concern**: Storing `role` in the request context alongside `userID` risks serving stale data if roles are updated elsewhere during the request lifecycle. Consider whether role checks should be performed at authorization boundaries rather than cached in context.
