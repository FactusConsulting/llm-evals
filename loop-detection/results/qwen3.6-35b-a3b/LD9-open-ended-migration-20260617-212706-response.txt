**Key Risks & Prerequisites**
- *Risks:* Cutover window exceeds SLA; logical replication lag causes data divergence; connection pool exhaustion during pod restarts; psycopg2 2.9.3 compatibility edge cases with PG 16 protocol changes; rollback complexity if new cluster fails validation.
- *Prerequisites:* Verified recent full backup and point-in-time recovery test; DigitalOcean API token with cluster management scope; updated Kubernetes secrets for new DB endpoint; PgBouncer/connection pool configuration ready for endpoint swap; monitoring dashboards and alerting rules verified; maintenance window approved by on-call and product stakeholders.

**Migration Plan**
1. Provision a new PG 16 cluster on DigitalOcean matching the current instance’s compute, storage, and VPC configuration.
2. Enable logical replication from the PG 14 primary to the new PG 16 cluster using DO’s native replication feature and verify initial sync completion.
3. Verify replication lag is zero and run schema/data checksums on core payment tables to ensure consistency before cutover.
4. Update Kubernetes deployment manifests to target the new PG 16 endpoint and configure graceful connection draining with a 60-second timeout.
5. Execute a staging rolling restart to validate psycopg2 2.9.3 connectivity, transaction isolation levels, and PgBouncer pool recycling under load.
6. Confirm maintenance window approval with on-call engineering and product stakeholders. (Requires human approval)
7. Halt external traffic routing and drain all active connections to the PG 14 instance via load balancer health check deregistration.
8. Promote the PG 16 cluster to primary and terminate replication streams to prevent write conflicts during the switchover.
9. Update Kubernetes secrets with the new PG 16 endpoint and initiate a production rolling restart of the payments service.
10. Run automated payment reconciliation scripts and latency/error-rate smoke tests against the live cluster to validate data integrity.
11. Resume traffic routing and monitor application metrics, database connections, and replication status for 30 minutes. (Requires coordination with SRE and monitoring teams)
12. Delete the PG 14 cluster and replica after a 7-day stability observation period to preserve rollback capability.
