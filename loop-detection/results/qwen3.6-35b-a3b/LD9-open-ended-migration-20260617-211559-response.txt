**Key Risks & Prerequisites**
Risks: Brief downtime during primary failover; query performance regression from PG 16 planner changes; connection pool exhaustion during cutover; rollback complexity if data drift occurs.
Prerequisites: Verify automated backup integrity and validate restore procedure in a sandbox; confirm psycopg2 2.9.3 compatibility (upgrade to 2.9.9+ recommended for PG 16 TLS/protocol support); provision a temporary PG 16 test cluster mirroring production extensions and collations; update Kubernetes secrets with new connection parameters; secure a maintenance window and align with SRE/on-call rotation; document rollback procedures for failed schema migrations.

**Migration Plan**
1. Execute `pg_upgradecheck` against a staging clone of the production schema to flag deprecated syntax, incompatible extensions, or collation mismatches.
2. Provision a new DigitalOcean managed Postgres 16 cluster in the same region and private network as the existing PG 14 instance.
3. Configure the new PG 16 cluster as a streaming replica of the PG 14 primary using DigitalOcean’s replication dashboard.
4. Monitor replication lag until it consistently reads zero and verify WAL archiving is functioning.
5. Update the payments service Kubernetes deployment manifest to route traffic to the new PG 16 replica endpoint, adjust `max_connections` and `statement_timeout` in the connection string, and validate the change in a staging namespace.
6. Perform a rolling restart of the payments service pods to establish active connections against the PG 16 replica, ensuring connection pools drain gracefully before pod termination.
7. Run automated integration tests and monitor application error rates, p95 latency, and database connection counts for 24 hours, comparing query execution plans against PG 14 baselines.
8. If metrics remain within baseline thresholds, initiate a manual failover in the DigitalOcean control panel to promote the PG 16 replica to primary.
9. Update the Kubernetes deployment manifest to reference the new PG 16 primary endpoint, verify TLS certificate rotation, and execute a rolling restart to re-establish connections.
10. Verify data consistency by running checksum queries against critical payment tables and confirm all services are healthy.
11. Decommission the legacy PG 14 cluster and its original replica after archiving logs and updating infrastructure-as-code templates.

**Approval & Coordination Requirements**
- Step 1: Requires lead engineer sign-off on compatibility scan results before provisioning.
- Step 5: Requires DevOps approval to merge manifest changes and validate staging rollout.
- Step 8: Requires explicit change advisory board (CAB) approval and stakeholder notification before executing manual failover.
- Step 10: Requires security/compliance sign-off before decommissioning legacy infrastructure and purging backups.
