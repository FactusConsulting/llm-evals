**`auth/jwt.go`**
- **Secret Initialization & Horizontal Scaling:** Generating `jwtSecret` in `init()` via `crypto/rand` creates a new signing key on every application restart. This immediately invalidates all active tokens and breaks horizontal scaling, as each instance will sign/verify with a different key. The secret must be loaded from environment variables or a secure configuration store.
- **Refresh Token State Management:** `GenerateRefreshToken()` produces a cryptographically random string, but there is no mechanism to persist, validate, or revoke it. Since Redis is removed, how will the system handle refresh token rotation, blacklisting, or expiration? Stateless refresh tokens are not feasible without a persistent store or a separate signing mechanism.
- **Error Masking in `ValidateToken`:** If `jwt.ParseWithClaims` fails (e.g., token expired, malformed), the original error is returned. However, if the type assertion fails or `token.Valid` is false, the function returns `jwt.ErrSignatureInvalid`. This masks the actual failure reason, making debugging and client-side error handling difficult. Return the original parsing error instead.

**`auth/middleware.go`**
- **Authorization Header Parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` does not validate the prefix. Headers like `"Bearer"` (missing space), `"Basic xyz"`, or malformed strings will pass through, causing downstream validation to fail cryptically. Add explicit prefix validation and handle case-insensitivity per RFC 6750.
- **Context Key Safety:** Using string literals (`"userID"`, `"role"`) as context keys is unsafe and prone to collisions with other middleware or packages. Define unexported, typed context keys (e.g., `type userIDKey struct{}`) to ensure type safety and prevent accidental overwrites.
- **API Response Consistency:** Returning plain text via `http.Error` for unauthorized requests may break JSON-consuming API clients. Consider standardizing on a JSON error response structure to maintain consistency across the application.
