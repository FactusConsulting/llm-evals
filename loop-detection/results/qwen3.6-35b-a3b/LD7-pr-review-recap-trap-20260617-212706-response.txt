### 🔒 Security & Configuration
- **Runtime secret generation breaks scaling:** `jwtSecret` is generated randomly in `init()` and never persisted. Any pod restart or horizontal scaling event will invalidate all existing tokens. Secrets must be injected via environment variables or a secrets manager.
- **Ignored CSPRNG error:** `rand.Read(jwtSecret)` discards the returned error. If the OS RNG fails, the secret defaults to all zeros, creating a critical cryptographic vulnerability. Always check and handle the error.
- **Unvalidated role claims:** The `Claims` struct accepts any string for `Role`. Downstream handlers could be bypassed if a malformed or tampered token contains an arbitrary role. Validate roles against an allowlist during parsing or in the middleware.

### 🏗️ Architecture & State Management
- **Missing refresh token persistence:** `GenerateRefreshToken()` creates a random string but provides no storage or revocation mechanism. Since Redis is removed, how will refresh tokens be persisted? Client-side storage defeats the security purpose of refresh tokens, as they cannot be invalidated on logout or compromise.
- **No token rotation strategy:** The secret is generated once at startup with no rotation mechanism. If the secret is ever leaked, all issued tokens remain valid until the process restarts. Plan for secret rotation and overlapping validation periods.

### 🛠️ Code Quality & Robustness
- **Untyped context keys:** `context.WithValue(r.Context(), "userID", claims.UserID)` uses raw string keys. This risks collisions with other middleware or third-party packages. Define a custom `type contextKey string` and use it consistently.
- **Weak Authorization header parsing:** `strings.TrimPrefix(authHeader, "Bearer ")` does not validate the header format. Headers like `"Bearer"` or `"Basic xyz"` will pass through and fail later. Add a strict prefix check or regex validation before attempting to parse.
- **Misleading error return:** `ValidateToken` returns `jwt.ErrSignatureInvalid` when the type assertion fails. This is semantically incorrect; the signature may be valid, but the claims type mismatched. Return the original parsing error or a custom authentication error instead.
- **Redundant validity check:** `token.Valid` is manually checked after `jwt.ParseWithClaims`, which already performs signature, expiry, and claim validation. The explicit check is unnecessary.
- **Missing claim validation:** `claims.UserID` and `claims.Role` are injected into the context without checking for empty strings or invalid formats. Propagating empty values could cause downstream panics or logic errors.

### ❓ Questions
- What is the intended storage backend and revocation strategy for refresh tokens given the removal of Redis?
- Should the middleware differentiate between expired tokens and invalid signatures in its error responses to enable client-side retry logic?
- Will the JWT secret be rotated in production? If so, how will the middleware handle validating tokens signed with previous secrets during the transition window?
