**Block**

The package does not compile due to an unused import, and the `Get` method has a race condition that can return stale or deleted values.

### Concrete Issues

1. **Compile error — `cache/cache.go:4`**  
   The `"context"` import is never used. Go compilation fails with an unused import error. Remove it.

2. **Race condition in `Get` — `cache/cache.go:36-39`**  
   The lock is released before checking `e.expiresAt`. Between the unlock and the expiry check, another goroutine can call `Delete` or `Set` for the same key, causing `Get` to return a value that was deleted or an outdated value that was overwritten. The expiry check must be performed while holding the lock, e.g.:
   ```go
   c.mu.Lock()
   e, ok := c.entries[key]
   if ok && time.Now().After(e.expiresAt) {
       ok = false
   }
   c.mu.Unlock()
   if !ok {
       return nil, false
   }
   return e.value, true
   ```

3. **Goroutine leak — `cache/cache.go:25`**  
   `New` starts an unbounded `evict` goroutine that runs forever. There is no way to stop it, and it keeps the `Cache` object alive even after it is no longer referenced, preventing garbage collection. Add a `Close` method or use a `context.Context` to cancel the goroutine.

### Nits / Style

- `cache/cache.go:53` — The eviction sleep interval is hardcoded to `time.Minute`. Consider making it configurable or deriving it from the TTL (e.g., `ttl/2`) to avoid stale entries lingering for too long.
- `cache/cache.go:35-43` — `Get` does not delete expired entries it encounters. Consider removing them opportunistically to reduce memory usage before the periodic eviction runs.
- `cache/cache.go:20-27` — The `New` function starts the eviction goroutine immediately; consider exposing a `Close` method to stop it, which also addresses the goroutine leak above.
