### Key Risks

- **Major version jump (14→16):** PG16 removed or changed behaviors from PG14 (e.g., `vacuumdb` defaults, `pg_dump` output, `hstore` operator changes). Untested queries or extensions may break.
- **psycopg2 2.9.3 predates PG16:** Verify it works against PG16; if not, upgrade to psycopg2 2.9.9+ before the migration.
- **Managed DBaaS constraints:** DigitalOcean may not support in-place major upgrades; you may need a new cluster and data migration.
- **Replica handling:** Improper failover or promotion can cause split-brain or data loss.
- **Payments service:** Downtime and data integrity are critical; rollback must be possible.

### Prerequisites

- Confirm psycopg2 2.9.3 compatibility with PG16 in a staging environment; if incompatible, bump to psycopg2 2.9.9+ and deploy.
- Verify DigitalOcean supports PG16 and determine the upgrade path (in-place vs. new cluster).
- Confirm existing backup/restore procedures work end-to-end.
- Obtain a maintenance window approval.

### Migration Plan

1. **Test psycopg2 compatibility:** Deploy the payments service against a PG16 staging cluster; run the full test suite and load tests. If psycopg2 2.9.3 fails, upgrade to 2.9.9+ and redeploy.

2. **Confirm DigitalOcean upgrade path:** Check DO docs for PG16 availability. Determine whether an in-place major upgrade is supported or whether a new cluster + migration is required.

3. **Build a PG16 staging cluster:** Create a staging cluster on PG16, migrate a copy of production data, and validate all queries, extensions, and performance against the payments workload.

4. **Take a full production backup:** Run `pg_dump` or DO's backup feature on the PG14 cluster. Verify the backup can be restored to a throwaway instance.

5. **Schedule maintenance window:** Pick a low-traffic period. Notify stakeholders and get written approval for the downtime window.

6. **Upgrade replica first (if in-place supported):** Upgrade the replica to PG16, confirm replication lag is zero, then promote it to primary. Upgrade the old primary to PG16 and reattach it as a replica.

7. **Migrate to a new cluster (if in-place not supported):** Create a PG16 cluster, migrate data using `pg_dump`/`pg_restore` or DO's migration tool, and validate row counts and constraints.

8. **Cut over:** Update Kubernetes secrets/configmaps with the new connection strings (if a new cluster was created) and roll out the change to the payments service.

9. **Verify production:** Check application health, query performance, and payment processing end-to-end. Monitor error rates and latency for at least one hour.

10. **Keep rollback ready:** Leave the old PG14 cluster running for 48 hours. If issues arise, revert the Kubernetes connection strings. After 48 hours, decommission the old cluster.

### Approval / External Coordination

- **Step 5 (maintenance window)** requires human approval from stakeholders.
- **Steps 6 and 7 (failover/cutover)** require change approval and coordination with DigitalOcean support if the upgrade is managed by DO.
- **Step 8 (Kubernetes rollout)** may require approval from the platform team.
