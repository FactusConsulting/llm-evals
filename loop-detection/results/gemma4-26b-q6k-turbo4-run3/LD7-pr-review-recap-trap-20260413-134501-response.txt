### Security & Implementation Issues

**`auth/jwt.go`**
* **Critical: Non-deterministic Secret Generation:** The `jwtSecret` is generated randomly in `init()`. This means every time the application restarts, all existing tokens become invalid because the signing key changes. This will cause global logout events on every deployment or server restart.
* **Critical: Hardcoded/Insecure Key Management:** The secret is stored in memory and generated locally. There is no mechanism to load a persistent secret from an environment variable or a secret manager (e.g., AWS KMS, HashiCorp Vault).
* **Security: Weak Entropy Check:** `rand.Read(jwtSecret)` is called without checking the error return value. If the system's entropy pool is exhausted or fails, `jwtSecret` may be partially or entirely uninitialized (all zeros), making tokens trivial to forge.
* **Security: Lack of Algorithm Validation:** In `ValidateToken`, the code does not explicitly verify that the `alg` header in the incoming JWT matches `HS256`. This leaves the system vulnerable to "alg: none" attacks or asymmetric key confusion attacks if the library version has specific vulnerabilities.

**`auth/middleware.go`**
* **Context Key Collision Risk:** Using raw strings (`"userID"`, `"role"`) as context keys is dangerous. This can lead to collisions with other middlewares or packages. Use a custom, unexported type for context keys to ensure type safety and prevent collisions.
* **Missing Error Handling:** In `AuthMiddleware`, the `strings.TrimPrefix` logic does not validate if the prefix was actually `"Bearer "`. If a client sends a malformed header without the prefix, `tokenStr` might be an empty or invalid string, which is handled by `ValidateToken`, but the logic is brittle.

### Questions & Risks
* **Token Revocation:** Since you are removing Redis/session storage, how do you plan to handle token revocation (e.g., logging out a user, banning an account, or handling compromised tokens)? Currently, tokens are valid until they expire naturally.
* **Refresh Token Implementation:** `GenerateRefreshToken` is implemented but not utilized in the middleware or the `IssueToken` flow. What is the intended lifecycle and storage strategy for these refresh tokens?
* **Scalability:** Since the secret is generated in `init()`, how will this work in a multi-instance/load-balanced environment? Each instance will have a different secret, making it impossible for a token issued by Instance A to be validated by Instance B.
