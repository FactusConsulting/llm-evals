### Security & Reliability Risks

* **Secret Volatility and Scaling:** The `jwtSecret` is generated randomly within an `init()` function. This creates two critical failures:
    1. **Service Restarts:** Every time the application restarts, all existing JWTs become immediately invalid because the secret changes.
    2. **Horizontal Scaling:** In a multi-instance deployment, each instance will generate its own unique secret. A token issued by Instance A will be rejected by Instance B, making horizontal scaling impossible. The secret must be loaded from a persistent configuration or environment variable.
* **Lack of Revocation Mechanism:** By removing the Redis dependency, there is no longer a central way to invalidate tokens. Once a JWT is issued, it remains valid until expiration. How do we handle user logouts or immediate revocation of compromised tokens without a shared data store (e.g., a blacklist)?
* **Symmetric vs. Asymmetric Signing:** The implementation uses HS256 (symmetric). For distributed architectures, consider using RS256 or ES256 (asymmetric) so that downstream services can validate tokens using only a public key, minimizing the risk if a single service's credentials are leaked.

### Implementation Issues

* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys in `context.WithValue` is dangerous and prone to collisions with other middlewares. These should be defined as unexported custom types.
* **Refresh Token Lifecycle:** While `GenerateRefreshToken` is implemented, there is no logic for storing or validating these tokens. Since the Redis dependency was removed, where are refresh tokens persisted? Without a backend store, "refreshing" an expired access token becomes impossible.

### Questions

* Given the removal of Redis, what is the intended strategy for managing token blacklists or session state?
* How will the `jwtSecret` be synchronized across multiple instances in production?
