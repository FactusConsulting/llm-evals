### Critical Issues & Risks

* **Secret Volatility:** `jwtSecret` is generated randomly in `init()`. This means every time the application restarts, the secret changes, immediately invalidating all existing user tokens. The secret must be loaded from a persistent, secure source (e.g., environment variables or a secret manager).
* **Lack of Token Revocation:** By removing the Redis dependency, you have lost the ability to revoke individual sessions. There is no mechanism provided to blacklist tokens or handle logouts effectively, which is a significant security risk if a token is compromised.
* **Broken Refresh Flow:** `GenerateRefreshToken` creates a random string, but since the Redis dependency was removed, there is no storage layer to persist these tokens or associate them with a user. This makes the refresh token functionally useless for its intended purpose.
* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys is dangerous and can lead to collisions with other middlewares. Use unexported, custom types for context keys.

### Code Quality & Security Observations

* **Silent Failure in `init`:** The error returned by `rand.Read(jwtSecret)` is ignored. If the system fails to generate entropy, the application will proceed with a zeroed or partially zeroed secret.
* **Loose Header Parsing:** The middleware uses `strings.TrimPrefix` without verifying if the `Authorization` header actually follows the `Bearer <token>` format. This could lead to unexpected behavior if the header is malformed.
* **Hardcoded Expiration:** The 24-hour token lifetime in `IssueToken` is hardcoded. This should be a configurable parameter.
* **Error Masking:** In `ValidateToken`, returning `jwt.ErrSignatureInvalid` manually if the type assertion fails might mask the actual error returned by `jwt.ParseWithClaims`.
