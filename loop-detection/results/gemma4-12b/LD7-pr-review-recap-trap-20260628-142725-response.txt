### Critical Security & Architectural Issues

*   **Ephemeral Secret Key:** The `jwtSecret` is generated in the `init()` function using `rand.Read`. This means the secret is lost every time the application restarts. Any tokens issued before a restart will immediately become invalid, causing a complete logout of all active users. This secret must be loaded from a persistent environment variable or a secret management service (e.g., HashiCorp Vault).
*   **Hardcoded Signing Method:** While `HS256` is used, the implementation lacks a mechanism to rotate keys. If the secret is compromised, there is no way to invalidate existing tokens without a full redeploy and secret change.
*   **Context Key Collisions:** Using raw strings like `"userID"` and `"role"` as context keys is unsafe and can lead to collisions with other middlewares or libraries. You should define private types for context keys (e.g., `type contextKey int`).
*   **Missing Refresh Token Logic:** The `GenerateRefreshToken` function is implemented, but there is no logic in the middleware or the `auth` package to validate, store, or rotate these tokens. Since you are removing Redis, how will refresh tokens be persisted or verified?

### Logic & Robustness Issues

*   **Error Handling in `init()`:** `rand.Read(jwtSecret)` can return an error. If it fails, the secret remains an array of zeros, making the system highly vulnerable. This should be handled during startup, and the application should fail to start if entropy cannot be gathered.
*   **Token Validation Strictness:** `jwt.ParseWithClaims` is used, but there is no check for the `alg` header. An attacker could potentially provide a token signed with a different algorithm (e.g., "none") if the library defaults aren't strictly enforced.
*   **Missing Expiration Check on Refresh Tokens:** The `GenerateRefreshToken` produces a random string but provides no mechanism to check its expiration or association with a specific user.

### Questions

*   How do we handle "Log out" functionality now that we have removed the Redis session store? Since JWTs are stateless, we currently have no way to revoke a token before it expires.
*   Is there a plan to implement a "blacklist" or a "denylist" for revoked tokens?
*   What is the strategy for handling clock skew between distributed servers when validating `ExpiresAt`?
