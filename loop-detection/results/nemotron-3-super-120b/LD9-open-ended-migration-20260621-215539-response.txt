
**Key Risks & Prerequisites**  
- SQL/psycopg2 incompatibilities between PG14 and PG16 (e.g., default behavior changes, removed casts).  
- Downtime tolerance: payments must stay available; need a rollback path.  
- Backup integrity: verified logical backup and point‑in‑time recovery capability.  
- Extension compatibility (pgcrypto, any custom extensions).  
- Network and connection‑pool sizing for the managed instance.  
- Monitoring must cover both versions during cut‑over.  
- Schema changes must be backward‑compatible to allow fast rollback.  

**Migration Plan**  
1. List all database objects (schemas, tables, indexes, extensions, functions, triggers) on the PG14 instance and save the output. [Approval: DB admin]  
2. Review psycopg2 2.9.3 release notes and run a compatibility test suite against a PG16 sandbox; confirm no test failures. [Approval: QA lead]  
3. Take a logical backup of PG14: `pg_dump --format=custom --file=payments_pg14.backup`. Store the file in an immutable object store with 30‑day retention. [Approval: Ops]  
4. Provision a managed PG16 instance of identical size, VPC, subnet, and SSL settings; note its connection string. [Approval: Infra]  
5. Deploy a canary payments pod (1 replica) pointing to the PG16 connection string via an environment variable override; keep the rest of the deployment on PG14. [Approval: Platform]  
6. Run smoke tests against the canary (health check, create payment, refund) and monitor error rates for 15 minutes. [Approval: Release manager]  
7. If smoke tests pass, generate a schema‑only dump from PG14 and apply it to PG16 to ensure structural parity. [Approval: DB admin]  
8. Load data in batches using `pg_dump --data-only --inserts | psql`; after each batch, verify row counts match source. [Approval: DB admin]  
9. Update any extensions on PG16 (e.g., `ALTER EXTENSION pgcrypto UPDATE;`). Confirm functions exist. [Approval: DB admin]  
10. Switch the Kubernetes Service/Ingress to point all payments replicas to the PG16 endpoint; retain PG14 as a read‑only standby for 30 minutes. [Approval: Platform lead]  
11. Observe latency, transaction rate, error rate, and replication lag for 30 minutes; if anomalies appear, revert the Service to PG14 and investigate. [Approval: On‑call engineer]  
12. After successful cut‑over, take a final logical backup of PG16, retain the PG14 backup for audit, and schedule de‑provision of the PG14 instance after 7 days. [Approval: Ops lead]  
13. Update runbooks, alerting thresholds, and documentation to reflect PG16; close the migration ticket. [Approval: Tech lead]
