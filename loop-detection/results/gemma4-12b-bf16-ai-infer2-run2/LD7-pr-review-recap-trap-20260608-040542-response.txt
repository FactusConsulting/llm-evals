- **Secret Persistence & Scalability:** The `jwtSecret` is initialized using `rand.Read` inside an `init()` function. This means every time the service restarts (or scales horizontally), a new secret is generated. Any existing tokens will immediately become invalid upon restart, and different instances of the service will be unable to validate each other's tokens. The secret should be loaded from a persistent environment variable or a secrets management service.

- **Refresh Token Storage:** While `GenerateRefreshToken` exists, there is no implementation shown for persisting or validating these tokens. Since the PR aims to remove the Redis dependency, how are these refresh tokens intended to be stored and verified against the user's identity?

- **Context Key Collisions:** In `AuthMiddleware`, context values are being set using raw strings (`"userID"` and `"role"`). It is best practice to use custom, unexported types for context keys to avoid collisions with other middlewares or libraries.

- **Hardcoded Expiration:** The token expiration is hardcoded to 24 hours in `IssueToken`. This should be configurable via environment variables or a configuration file to allow for adjustments without code changes.

- **Algorithm Validation:** In `ValidateToken`, the callback provided to `ParseWithClaims` does not explicitly verify that the signing method used in the header matches the expected algorithm (HS256). An attacker could potentially change the header to "none" or another algorithm if the library doesn't strictly enforce the expected type.

- **Error Handling/Logging:** The middleware returns a generic 401 error for all failures (invalid signature, expired token, missing header). Adding internal logging would help distinguish between an expired token and a malicious tampering attempt during debugging.
