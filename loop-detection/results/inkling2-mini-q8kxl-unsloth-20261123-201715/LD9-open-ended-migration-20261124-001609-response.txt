Assumptions: managed DigitalOcean Postgres 14, one replica, psycopg2 2.9.3, no existing PG16 staging. If DO offers a supported in-place major upgrade, use it; otherwise plan new-cluster cutover.

Key risks/prerequisites:
- Major-version incompatibility: extensions, SQL behavior, planner changes, removed/changed features; psycopg2 2.9.3 is old and should not be assumed compatible with PG16.
- Payments correctness: write consistency, duplicate/missed transactions, reconciliation drift, rollback safety.
- Managed-service constraints: DO may not support direct 14→16 in-place upgrade; one replica increases failover/downtime risk.
- Prerequisites: current backup/PITR verified, restore rehearsal, extension/role/grant inventory, app/DB connection inventory, staging PG16, monitoring/alerts, maintenance window, rollback plan, named approver.

Plan:
1. Confirm with DigitalOcean/account owner whether in-place major upgrade is supported; otherwise approve new-cluster cutover. Human approval required.
2. Inventory extensions, roles, grants, triggers, constraints, sequences, replication/CDC, connection poolers, and psycopg2 usage.
3. Upgrade psycopg2 to a PG16-supported release and run unit/integration tests against a PG16 staging database.
4. Create a PG16 staging cluster and restore/copy production data using backup or logical replication.
5. Run schema/data validation: row counts, checksums, financial totals, extension availability, query plans, and app smoke tests.
6. Run load/failover tests and verify rollback path from PG16 back to PG14 or re-cutover.
7. Freeze schema changes and non-critical deploys during the window; notify app, DBA, SRE, payments owner, and support. External coordination required.
8. Take final backup/PITR snapshot and verify restore before cutover.
9. Announce maintenance window and freeze writes or put payments in read-only/degraded mode if needed. Human approval required.
10. Cut over: stop app writes, point app to PG16, verify connections, health checks, transaction flow, and reconciliation.
11. Monitor error rates, latency, locks, replication/lag if applicable, and payment-critical metrics for the agreed observation period.
12. If validation fails, roll back to PG14 or re-point app; if it passes, keep PG14 read-only for the rollback period.
13. After sign-off, decommission/delete the old PG14 instance and update runbooks, dashboards, and connection strings. Human approval required.

Human approval/external coordination: DO/account owner for upgrade path, DBA for restore/cutover, payments owner for financial validation, app team for psycopg2/config changes, SRE for window/rollback, and support/comms for customer-facing notice.
