### Security & Architecture Issues

**Critical Security Risks**
* **Ephemeral Secret Generation:** The `jwtSecret` is generated using `rand.Read` inside an `init()` function. This means the secret is regenerated every time the application restarts. This will invalidate all existing tokens upon every deployment or server restart, forcing all users to re-authenticate. Furthermore, in a distributed/multi-instance environment, different instances will have different secrets, making tokens issued by one instance invalid on another.
* **Hardcoded Signing Method:** The `ValidateToken` function does not verify the signing algorithm used in the header. This leaves the system vulnerable to "alg: none" attacks or HMAC vs. RSA confusion attacks if the library/implementation doesn't strictly enforce `HS256`.
* **Lack of Token Revocation:** By moving from session cookies (stored in Redis) to stateless JWTs, there is no mechanism provided to revoke a compromised token before its 24-hour expiration.

**Implementation Flaws**
* **Context Key Collisions:** Using raw strings (`"userID"`, `"role"`) as context keys is dangerous and can lead to collisions. Use custom, unexported types for context keys to ensure type safety and prevent collisions with other middlewares.
* **Insecure Error Handling:** `ValidateToken` returns `jwt.ErrSignatureInvalid` as a fallback, but the error returned by `jwt.ParseWithClaims` might be more descriptive. The error handling in `ValidateToken` is somewhat opaque regarding why validation failed (e.g., expired vs. invalid signature).
* **Unused Code:** `GenerateRefreshToken()` is implemented but not utilized in the provided middleware or logic, and it currently lacks a mechanism to link it to a specific user or session.

**Questions**
* How do you plan to handle secret rotation or synchronization across multiple service instances?
* Is there a plan to implement a blocklist (e.g., in Redis) to handle logout/revocation, given that the current implementation is purely stateless?
* Should the `Role` be part of the JWT claims, or should it be fetched from a database to ensure real-time permission updates?
